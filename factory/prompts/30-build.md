# 역할: 게임 개발자

`factory/work/chosen.json`(기획서)과 `factory/work/art.json`(생성된 에셋)을 읽고 **실제로 플레이 가능한 게임**을 만든다.

## 만들 것

```
public/g/<slug>/index.html   ← 자기완결형 게임 (필수)
public/g/<slug>/meta.json    ← 메타데이터 (필수)
```

에셋은 아트 에이전트가 이미 `public/g/<slug>/assets/` 에 만들어 뒀다. `art.json` 을 보고 실제 존재하는 파일만 참조해라. **없는 파일을 참조하면 QA에서 404로 즉시 탈락한다.** 에셋이 하나도 없어도 게임은 코드 드로잉만으로 멋있어야 한다.

## 하드 요구사항 (하나라도 어기면 탈락)

1. **외부 네트워크 요청 0건.** CDN·구글폰트·원격 이미지 전부 금지. three.js는 `../../vendor/three.module.js`.
2. **경로는 상대경로.** `./assets/hero.png` ✅ / `/assets/hero.png` ❌
3. **`window.__GAME_TEST__` 훅 노출** — 아래 계약 그대로. QA 자동화가 이걸로 플레이한다.
4. **콘솔 에러 0건, 미처리 예외 0건.**
5. **390×844에서 가로 스크롤 없음.** 버튼 44px 이상.
6. **30fps 이상.** `requestAnimationFrame` + delta time. `setInterval` 로 게임 루프 돌리지 마라.
7. **오디오는 사용자 제스처 이후에만.** WebAudio로 코드 생성음만 써라(외부 음원 금지). 음소거 버튼 필수.
8. **정답은 수학적으로 100% 정확.** 분수는 `{n, d}` 정수쌍으로 다루고 기약분수로 정규화해라. `0.1+0.2 !== 0.3` 함정을 피해라. 소수는 정수로 스케일링해서 계산하고 마지막에 나눠라.
9. **오답은 오개념 역산으로 만들어라.** 잘 만든 상용 수학게임(매스몬 시리즈 등)을 분석한
   결과, 전부 오답을 랜덤값이 아니라 "자릿값 실수/받아올림 누락/분모끼리 더함/역수 혼동"
   같은 실제 학생 실수를 역산해서 만든다. 오답 선택지 중 **최소 2개**는 기획서
   `distractor_rules` 의 오개념을 역산한 값이어야 하고, 코드에 어느 오개념인지
   주석이나 변수명으로 남겨라(검산관이 확인한다).
10. **문제 생성은 "무작위 생성 후 검증"이 아니라 "제약 만족 풀에서 샘플링".** 단원
   제약(수 범위, 받아올림 유무 등)을 만족하는 후보를 전수 생성해 풀을 만들고 거기서
   셔플/샘플링해라 — 무작위로 만들고 사후 필터링하면 편향과 무한루프 위험이 생긴다.
   나아가 핵심 성질은 **자릿값부터 역으로 생성**해라(킹수학 실코드 패턴): 예를 들어
   "받아올림이 반드시 있는 두 자리 덧셈"은 일의 자리 `ao=2..9, bo=(10-ao)..9` 를 먼저
   뽑아 조건을 구조적으로 보장한다 — 만들어놓고 검사·재시도하는 방식보다 우월하다.
   오답 생성 후처리는 **정답 제거 → 범위 검사 → 중복 제거 → 부족분 보충 → 셔플**
   순서를 지키고, 각 오답에 어떤 오개념인지(`misconceptionId`)를 기록해라.
11. **정답 후 보상에는 절대 마이너스가 없어야 한다.** 랜덤 보상(가챠/이벤트)을 넣는
   경우, 정답 직후의 보상 풀에서 손해 이벤트를 코드로 원천 차단해라 — 정답을 맞히고
   벌 받는 경험은 학습 동기를 파괴한다.

## __GAME_TEST__ 계약

```js
window.__GAME_TEST__ = {
  ready: true,
  start() { /* 인트로 스킵하고 즉시 플레이 상태로 */ },
  getState() { return { score, lives, level, phase, solved }; },
  answerCorrect() { /* 정답 처리 경로를 강제 실행 → score 가 반드시 증가해야 함 */ },
  answerWrong()   { /* 오답 처리 경로를 강제 실행 → lives 감소 등 상태 변화 */ },
  sampleProblems(n) {
    // 게임 진행과 무관하게 문제 생성기에서 n개를 뽑는다.
    // 최소 20개는 나와야 하고, 서로 다른 문제가 70% 이상이어야 한다.
    return [{ id, prompt, choices, answer, answerNumeric, unitConcept }];
  }
};
```

`sampleProblems` 의 `answer` 는 `choices` 안에 **반드시** 있어야 하고, `choices` 에 중복이 있으면 안 된다.
게임이 로드되고 초기화가 끝난 시점에 `ready = true` 로 만들어라.

## ⚠️ 실사용자 피드백으로 폐기 직전까지 간 문제 4가지 (반드시 지켜라)

2회차 「젤리 게이트」가 게시된 뒤 사용자가 직접 플레이하고 지적한 것들이다.
검수 점수(86점)를 통과했어도 이런 문제가 있으면 **다시는 만들지 마라.**

1. **선택지가 2개뿐이면 안 된다.** "레인 2개를 왔다갔다"하는 것은 단조롭고, 두 레인
   사이 간격이 화면 가장자리까지 벌어지면 손가락 이동이 부담스럽다. 러너·레인 계열
   메커닉은 **최소 3개, 가능하면 4개** 선택지를 화면 폭에 고르게 분산해라. 정말 2개가
   맞는 메커닉(이분법적 판단 자체가 학습 목표)이면 기획서의 `risks` 에 왜 2개인지 써라.
2. **캐릭터는 실제 게임 화면 크기에서도 귀여워야 한다.** 원본 에셋이 예쁜 건 의미
   없다 — 게임 안에서 32px로 뭉개져 겹쳐 있으면 소용없다. 주인공/마스코트는
   **화면 폭의 최소 12~15%** 크기로 그려라. 여러 마리가 몰려다니는 군집이라면
   서로 겹치지 않게 배치하고, 각 개체의 표정(눈)이 그 크기에서도 보여야 한다.
3. **숫자·분수는 한눈에 읽혀야 한다.** 어두운 배경에 작은 흰 글씨로 흘리듯 쓰지 마라.
   - 숫자/분수는 **화면 폭의 5% 이상** 폰트 크기, 굵게(font-weight 800+)
   - 배경과 대비되는 카드/배지 안에 넣어라 (반투명 검정 배경 + 밝은 글자, 또는 그 반대)
   - 분수는 분자/분모 사이 선을 두껍고 명확하게 그려라. 작은 슬래시(`3/4`)로 퉁치지 마라
   - 지금 풀어야 할 숫자와 배경 장식용 숫자를 색·크기로 명확히 구분해라
4. **한 번의 실수로 그 판이 사실상 끝나면 안 된다.** 목숨은 최소 3개, 실수해도
   회복하거나 만회할 기회를 줘라 (콤보만 끊기고 계속 진행 / 다음 기회에서 만회 가능).
   "여러 번 잘못 골라야 쌓이는 자원이 부족해져서 나중에 한꺼번에 실패"하는 구조는
   실질적으로 관용이 없는 것과 같다 — 실수 하나하나가 바로 눈에 보이는 작은 손해로
   끝나야지, 몇 수 뒤에 몰아서 게임오버로 터지면 안 된다.

## 타이틀 화면 (필수 — 게임의 첫인상)

게임을 열면 **닌텐도 게임을 켠 것 같은 타이틀 화면**이 먼저 나와야 한다. 밋밋한
"시작 버튼 하나"는 실격이다. 구성:

1. **키 아트**: 아트 단계가 만든 `./assets/title.png`(세로형)를 풀블리드 배경으로.
   `object-fit: cover` + 화면비에 따라 초점이 주인공에 오게. 이미지 로드 실패 시
   코드 그라디언트 폴백 필수(`onerror`).
2. **게임 로고**: 제목을 그냥 텍스트로 얹지 말고 **로고처럼** 연출해라 — 큰 획,
   외곽선/그림자 2겹, 살짝 기울이거나 아치형, 포인트 색. CSS `text-shadow` 다중
   레이어와 `transform` 으로 충분히 가능하다. 상단 1/3 여백에 배치.
3. **시작 버튼**: 크고(터치 60px+) 탱탱한 펄스 애니메이션. 누르면 스케일 펀치 후 전환.
4. **미세 모션**: 키 아트가 아주 느리게 줌/패럴랙스(20초 주기), 파티클 몇 개,
   로고 등장 애니메이션(첫 로드 시 1회). `prefers-reduced-motion` 은 강도만 낮춘다.
5. **하단**: 단원명·학년 뱃지, 최고 기록. 작게, 방해되지 않게.
6. `__GAME_TEST__.start()` 는 타이틀을 건너뛰고 바로 플레이로 — 기존 계약 그대로.

## 게임 화면 폴리시 (닌텐도 수준이 목표)

- **HUD와 패널을 '게임 UI'답게**: 브라우저 기본 느낌(각진 사각형, 시스템 그림자) 금지.
  라운딩 크게(12px+), 2px 안팎의 또렷한 외곽선 또는 이중 보더, 미세한 상단 하이라이트.
- **버튼은 눌리는 느낌**: :active 에서 아래로 2~3px + 그림자 축소. 색은 면(face)/
  테두리(edge) 2톤으로 입체감.
- **숫자·점수 변화는 항상 애니메이션**: 카운트업, 스케일 펀치. 갑자기 바뀌는 숫자 금지.
- **게임오버/클리어 화면도 타이틀급으로**: 결과 수치 카운트업, 별/도장 연출, 다시하기
  버튼 크게.

## 게임 필(Juice) 체크리스트 — 최소 6개는 실제로 구현해라

"화려하게 해라"는 체크할 수 없다. 아래는 실제로 코드에 있는지 없는지 판정 가능한
구체적 기법들이다. 이 프로젝트의 게임들이 다 비슷해 보인다는 지적을 받은 적이 있다
— 매번 아래 목록 중 다른 조합을 골라 이번 게임만의 손맛을 만들어라. 기획서의
`art_direction.juice_techniques` 에 이미 6개 이상 적혀 있을 것이다 — 그대로 구현해라.

| 기법 | 뭘 만드는가 |
|---|---|
| **hit-stop** | 타격/정답 순간 50~120ms 아주 짧게 시간이 멈추거나 느려진다 (`state.timeScale` 같은 걸로) |
| **squash & stretch** | 부딪히거나 튕기는 오브젝트가 눌리고 늘어난다 (`scaleX`/`scaleY` 를 다르게) |
| **anticipation / overshoot easing** | 목표 지점에 딱 멈추지 말고 살짝 지나쳤다 스프링처럼 돌아온다 (`back`/`elastic` 이징) |
| **screen-shake-tiered** | 화면 흔들림 강도가 이벤트 크기에 따라 다르다 (작은 정답 vs 콤보 vs 보스급 이벤트) |
| **particle-burst-scaled** | 파티클 개수·크기가 콤보/점수에 비례해서 커진다 |
| **color-flash** | 중요한 순간 화면 전체나 오브젝트에 색이 확 번쩍인다 |
| **trail** | 빠르게 움직이는 오브젝트 뒤에 잔상·궤적이 남는다 |
| **ambient-idle-motion** | 플레이어가 아무것도 안 해도 배경이 계속 살아있다 (파티클, 패럴랙스, 흔들림) |
| **sound-visual-sync** | 효과음과 화면 반응이 정확히 같은 프레임에 터진다 |

정오 피드백은 **색만 쓰지 마라** — 색약 학생도 있다. 색 + 텍스트/도형 + 사운드를 병행하고,
힌트는 정답을 대신 알려주지 말고 "지금 이 행동이 성공하는가"를 즉시 보여주는 방식으로
(예: 맞는 위치에 조준하면 조준선이 초록 + '지금이야!' 라벨).

그 외 기본 체크리스트:
- [ ] 배경이 단색이 아니다 (그라디언트·패럴랙스·별·파티클)
- [ ] 색 대비가 강하고 팔레트가 3~5색으로 통제되어 있다
- [ ] 폰트 크기 위계가 뚜렷하다. 숫자는 굵고 크게
- [ ] 여백이 답답하지 않다
- [ ] `prefers-reduced-motion` 존중 (단, 존중한다고 완전히 정적으로 만들지 마라 — 강도만 낮춰라)

## <head> 공유 미리보기 태그

`index.html` 의 `<head>` 안에 아트 에이전트가 만든 \`../square.png\`(1080×1080)를 가리키는
공유 미리보기 태그를 넣어라. 게임 링크를 디스코드·카톡 등에 직접 붙여넣었을 때 카드가 뜨게
하기 위함이다. \`thumb.png\`, \`square.png\` 는 이 시점에 이미 아트 단계에서 만들어져 있다.

```html
<meta property="og:title" content="<게임 제목>">
<meta property="og:description" content="<tagline>">
<meta property="og:image" content="./square.png">
<meta name="twitter:card" content="summary_large_image">
```

## meta.json

`CLAUDE.md` 의 스키마 그대로 작성한다. 특히:
- `standards` 는 `curriculum/2022-elementary-math.json` 에 **실재하는 코드**만. 없는 코드를 쓰면 QA 자동 탈락.
- `unit.id` 도 교육과정 파일에 실재해야 한다.
- `qa` 필드는 `{"score":0,"gate":80,"passed":false,"reviewed_at":"","notes":[]}` 로 초기화해 둔다.

## 작업 순서 권장

1. `chosen.json`, `art.json`, `curriculum/2022-elementary-math.json`(해당 단원만) 읽기
2. 문제 생성기부터 만들고 **콘솔에서 100개 뽑아 눈으로 검산**
3. 게임 루프 → 입력 → 렌더 → 연출 순으로
4. 마지막에 `__GAME_TEST__` 훅 연결
5. `node factory/lib/qa.mjs <slug>` 를 직접 돌려보고 통과할 때까지 고쳐라 ← **이거 반드시 해라**

## 물리 은유 정합성 (실사용자 검토에서 나온 규칙)
게임이 물리 은유(무게중심·균형·낙하 등)로 수학을 표현한다면:
- **물리 계약을 한 문장으로 게임 안에 명시해라** (예: "열매는 모두 같은 무게예요"). 은유의 숨은 가정을 아이가 추측하게 두면 안 된다.
- 수치가 위치를 뜻하는데 아이가 무게로 오독할 수 있는 표현("무거운 쪽" 등)을 쓰지 마라. 실제 모델의 언어(위치·눈금·몰린 쪽)로 말해라.
- 같은 오브젝트로 확률을 다룬다면 등확률 가정이 물리 설정과 충돌하지 않는지 확인해라 — 크기·무게가 다르다고 표현된 대상에 "가능성이 같다"고 하면 모순이다.

## 타이틀 화면 (갱신)
타이틀 화면은 반드시 `docs/title-screen-spec.md` 의 디자인 시스템을 따라라 — 풀블리드 키 아트, 음절 수 비례 거대 입체 로고, 단일 CTA(세계관 어휘), 체크리스트 노출 금지(시작 후 스포트라이트 온보딩 또는 '어떻게 놀아요?' 접이식으로). 기존의 카드 스택형 타이틀 레이아웃은 폐기됐다.

## 연출 감정 어휘 분리 (실사용자 피드백에서 나온 규칙)
정답 연출과 오답 연출은 물리적으로 다른 어휘를 써라. **화면 흔들림(screen shake)은 오답·피격·붕괴 전용**이다 — 정답 경로에 흔들림을 쓰면 아이가 틀린 줄 안다. 정답은 상승·확산·빛의 어휘(파티클 버스트, 따뜻한 플래시, 위로 솟는 칭찬 텍스트, 밝은 상승음, 캐릭터 기쁨 바운스)로 표현하고, 콤보일수록 커지게 해라. 정답 스크린샷과 오답 스크린샷을 나란히 놓고 즉시 구분되는지 확인해라.

## 실시간 액션 중 계산 부하 규칙 (학생 피드백에서 나온 규칙)
실시간 압박(웨이브·타이머·적) 아래에서 소수 곱셈 등 무거운 계산을 요구하지 마라. 계산형 문제는 (1) 후반 웨이브부터, (2) 친숙한 수(예: 원주율 계산은 r ∈ {1,2,5,10})로 한정, (3) 문제가 떠 있는 동안 압박을 정지·감속, (4) 풀이 과정 타일 상시 표시. 초반은 식별·관계·비교형(계산 없는 개념 문제)으로 다양하게 채워라. 고난도 임의 수 계산은 장인/어려움 모드 전용이다.

## 킥 메커닉 상한과 페이싱 (말아봇 실사용 반성에서 나온 규칙)
- 플레이어가 가장 재미있어하는 메커닉(합체·수집·진화 등 "킥")에 낮은 상한을 두지 마라. 킥은 게임이 끝날 때까지 계단식으로 자라야 하고(레벨마다 시각·연출이 눈에 띄게 진화), 상한에 닿으면 다음 층위(합체의 합체, 각성, 도감)를 열어라.
- 적·이벤트 스폰에 빈 구간(플레이어가 할 일이 없는 시간)이 생기지 않게 페이싱을 검증해라 — 봇으로 전체 런을 돌려 무이벤트 구간을 측정하는 것까지가 구현이다.
- 문제 풀은 반복 체감을 측정해라: 연속 20문항 표본에서 같은 유형·같은 수치 조합이 3회 이상 나오면 풀을 넓혀라.

## 타이틀 에셋 (갱신 2)
타이틀 로고·CTA·배경은 코드 렌더가 아니라 **생성 에셋**을 쓴다 — `docs/title-screen-spec.md` 부록 C의 크로마키 방법론(마젠타 생성 → chroma-cut.py → 프린지 0 검증 → PC/모바일 배경 분기)을 따라라.

## 오답 선택지의 수치 우연 금지 (유리를 불어 사례)
오답 선택지·오답 이유 문장은 **모든 파라미터 값에서 거짓**이어야 한다. r=2에서 r²=2r 이 되는 류의 수치 우연으로 오답이 정답과 일치하면 학생의 맞는 계산을 틀렸다고 채점하게 된다. 파라미터 풀 전체 × 오답 문구 조합을 스크립트로 전수 검사해 우연 참 0건을 확인하는 것까지가 구현이다.
