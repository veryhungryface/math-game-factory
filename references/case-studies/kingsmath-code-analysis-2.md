## 1. 확률킹

### 무엇을 게임화했나

화면의 A/B에 서로 다른 확률 사건을 보여 주고, 중앙 50%를 왕복하는 바늘을 더 가능성이 큰 쪽에서 멈추게 한다. 즉 수학 판단에 순수 객관식 클릭이 아니라 타이밍 조작을 한 겹 씌웠다.

```js
const isAWin = this.currentProblem.A.prob > this.currentProblem.B.prob;
if (isAWin && this.needlePos < 50) isCorrect = true;
else if (!isAWin && this.needlePos >= 50) isCorrect = true;
```

— `sources2/확률킹.html` L1194-L1197

정답을 맞히면 점수가 1 오르고 틀리면 1 내리며, 점수가 높아질수록 바늘 속도가 빨라진다(`baseSpeed = 1.2 + score * 0.25`, L1156). 수학 난이도가 오르는 것이 아니라 **조작 난이도**가 오른다.

### 0·1/2·1 수준의 ‘가능성’인가

아니다. 사건을 `(경우의 수)/(전체 경우의 수)`로 계산하여 1/8, 1/6, 1/3, 3/8, 2/5, 3/5 같은 여러 값을 직접 비교하고, 결과에 소수 첫째 자리 퍼센트를 공개한다.

```js
coin: (n) => ({ total: Math.pow(2, n), ... }),
dice: (n) => ({ total: Math.pow(6, n), ... }),
...
const probVal = numerator / denominator;
const percent = (probVal * 100).toFixed(1);
```

— L940-L943, L997-L1003

동전 3개에서 모두 앞면은 1/8, 앞면 1개는 3/8, 적어도 뒷면 하나는 7/8로 하드코딩한다(L961-L967). 주사위 2개도 합 7은 6/36, 합 짝수는 18/36, 같은 눈은 6/36, 합 12는 1/36이다(L976-L982). 이는 5-2 ‘가능성’을 직관 언어로 분류하는 수준보다 **중학교식 고전적 확률 계산에 가까운 콘텐츠**다.

특히 불가능(0)과 확실(1) 사건은 정상 사건 풀에 없다. 0%는 동률 처리의 인위적 fallback에서만 생기며, 100% 사건은 전혀 없다. 그러므로 0·1/2·1의 세 기준점을 반복 경험시키는 설계가 아니다.

### 이론적 확률과 실험 빈도를 다루나

- 이론적 확률: 다룬다. 동전/주사위/구슬/가위바위보 사건을 표본공간 크기와 유리한 경우 수로 즉시 계산한다.
- 실험 빈도: 전혀 다루지 않는다. 동전을 실제로 여러 번 던지거나 주사위를 반복 시행하는 배열, 시행 횟수, 빈도 누적 상태가 없다.
- 화면의 `승리 확률`도 실험적 승률이 아니다. 단순히 `score * 10%`로 표시한 진행도다.

```js
const percent = this.score * 10;
this.ui.probText.innerText = `${t('winRate')}: ${percent}%`;
```

— L1228-L1231

따라서 우리 공장에서 가능성 게임을 만들 때 이 소스를 그대로 모델로 삼으면 안 된다. 쓸 부분은 ‘두 상황 비교’뿐이다. 새 게임은 `불가능–~아닐 것 같다–반반–~일 것 같다–확실` 같은 언어/위치 척도와 실제 반복 시행이 이론값 근처로 모이는 장면을 핵심 루프로 삼아야 한다.

### 중요한 결함

동률 문제를 최대 10번 재생성한 뒤에도 동률이면 B의 내부 확률과 표시만 0으로 바꾼다.

```js

if (A.prob === B.prob) { B.prob = 0; B.display = "0%"; }
```

— L1017-L1026

B의 사건 문장은 그대로이므로, 예를 들어 실제로는 1/3인 사건을 0%라고 가르칠 수 있다. 교육 게임에서 재생성 실패를 **정답 데이터 변조로 해결한 반패턴**이다. 동률도 정식 문항으로 허용하거나, 후보를 전수 생성해 확률이 다른 쌍만 뽑아야 한다.

## 2. 소수점 이동킹

### 게임 구조

설정에서 소수/자연수, 확대/축소, 혼합을 고르고, 각 선수는 좌우 버튼으로 `shift`를 -6~6 사이에서 바꾼다. 표시값은 항상 `base × 10^shift`다.

```js
p.shift += dir;
if (p.shift > 6) p.shift = 6;
if (p.shift < -6) p.shift = -6;
inner.innerHTML = getFormattedNumber(p.base, p.shift);
```

— `sources2/소수점_이동킹.html` L1230-L1245

문제의 배율은 10, 100, 1000, 10000 또는 1/10, 1/100, 1/1000, 1/10000이고(L1049-L1051), 소수는 먼저 정수 `raw`와 소수 자릿수 `dp`를 뽑아 `raw / 10^dp`로 만든다(L1059-L1069). 이는 ‘자릿값부터 생성’ 패턴의 약한 변형이다.

### 부동소수점 함정을 어떻게 피했나

완전히 피한 것이 아니라 **양쪽 계산을 같은 방식으로 정규화하여 비교 안정성을 높였다.**

```js
base = parseFloat((raw / Math.pow(10, dp)).toPrecision(15));
ans  = parseFloat((base * mul).toPrecision(15));
...
const playerVal = parseFloat((p.base * Math.pow(10, p.shift)).toPrecision(15));
const isCorrect = (playerVal === correctAnsVal);
```

— L1069-L1070, L1297-L1298

정답과 사용자 값 모두 15자리 유효숫자로 한 번 문자열화했다가 숫자로 되돌린다. 올바른 이동에서는 `mul`과 `10^shift`가 같은 10의 거듭제곱이므로 두 경로가 같은 값으로 정규화되어 엄격 동등 비교가 실용적으로 작동한다.

하지만 정수 mantissa/scale 모델은 아니다. 여전히 `0.1`, 나눗셈, 곱셈이 IEEE-754를 거치며, 매우 작은/큰 값은 `toString()`에서 지수 표기로 바뀔 수 있다. 공장에서는 다음처럼 더 강하게 가져가는 편이 낫다.

- 값: `{digits: 1234, scale: 2}` → 12.34
- 소수점 이동: `scale -= shift`만 변경
- 비교: `(digits, scale)` 정규형끼리 비교
- 표시: 문자열에 0과 소수점을 삽입하며 숫자로 왕복하지 않기

이 소스에서 재사용할 핵심은 `base`를 공유하고 선수별로 `shift`만 저장하는 상태 모델, 그리고 문제 타입 선택을 `all_mix → dec_up/dec_down/nat_up/nat_down`으로 먼저 해소하는 두 단계 라우팅(L1030-L1047)이다.

## 3. 킹네모 디펜스

### 실제 콘텐츠 스위칭 구조

요청상 여러 5-2/6-2 단원에 매핑된 게임이지만 인라인 출제 엔진에는 단원 ID, 학년, 분수, 소수, 어림 프로필이 없다. 실제 스위치는 점수로 정해지는 `currentLevel` 하나뿐이다.

```js
let complexity = 1;
if (levelIdx === 1) complexity = 2;
else if (levelIdx >= 2) complexity = 3;
let ops = ['+', '-'];
if (complexity === 3) ops = ['+', '-', '*', '/'];
```

— `sources2/킹네모_디펜스.html` L1055-L1060

- 레벨 0: 덧셈/뺄셈, 작은 범위
- 레벨 1: 덧셈/뺄셈, 피연산자 범위 확대
- 레벨 2 이상: 곱셈/나눗셈과 연산자 빈칸 추가
- 레벨 3~17: 콘텐츠는 그대로이고 적 속도와 생성 주기만 계속 상승

레벨 테이블도 `reqScore`, `speed`, `spawnRate`만 바꾼다(L961-L979). `generateProblem(currentLevel)` 호출 하나로 콘텐츠를 받는다(L1218-L1234). 즉 **다단원 콘텐츠 스위칭 엔진이 아니라, 단일 사칙연산 생성기에 난이도 숫자를 주입한 구조**다. 넓은 교육과정 매핑은 코드로 뒷받침되지 않는다.

### 좋은 생성 패턴

빈칸 위치를 네 종류로 바꾸고, 먼저 빈칸 정답을 정한 뒤 식을 역산한다.

```js

if (op === '+') { a = ...; b = c_val - a; }
else if (op === '-') { b = ...; a = c_val + b; }
...
text = `${a}${op}${b}=🔲`;
```

— L1064-L1072

이는 1탄의 ‘정답/자릿값부터 제약 생성’과 같은 계열이다. 나눗셈은 `a = c_val * b`로 역산해 나누어떨어지게 만든다. 연산자 빈칸에서는 가능한 모든 연산자를 `answers` 배열에 넣어 복수 정답도 인정한다(L1093-L1103). 이 부분은 견고하다.

### 게임 메커닉과 콘텐츠 결합

입력한 키와 정답이 맞는 적 중 기지에 가장 가까운 적만 자동 조준한다(L1172-L1187). 틀린 키는 단순 감점이 아니라 180프레임 키보드 잠금이다(L1188-L1196). 여러 문제가 동시에 떠 있어 **한 키가 어느 적을 해결할지 우선순위를 공간 위험도로 정하는 구조**가 새롭다.

공장 반영 시 콘텐츠 전환은 `levelIdx`가 아니라 다음과 같은 명시 프로필이 필요하다.

```js
profile = {
  curriculumId: '6-2-2',
  generator: decimalDivision,
  answerCodec: decimalString,
  misconceptionRules: [...],
  pacing: { speed, spawnRate }
}
```

현재 소스처럼 속도 레벨과 수학 단원을 한 숫자에 겹치면 매핑 검증이 불가능하다.

## 4. 분수 캐치킹

### 실제 학습 내용

피자 그림을 보고 진분수/가분수/대분수의 자연수·분자·분모 슬롯에 1~9 숫자 버블을 끌어다 놓는다. 분수 곱셈/나눗셈을 계산하지 않는다. 그러므로 5-2/6-2 분수 연산 단원 매핑에는 ‘분수 표현 복습’ 정도의 간접 관련만 있다.

const d = Math.max(digits[0], digits[1]);
...
} while (n % d === 0);
...

1. 정확히 6면인지 확인한다.
2. 각 면의 `(긴 변, 짧은 변)` multiset이 목표의 여섯 면과 같은지 확인한다(L1216-L1222).
3. 두 사각형이 **전체 변 길이를 정확히 공유**할 때만 힌지로 등록한다(L1224-L1238).
4. 0번 면에서 BFS하여 모든 면이 연결되었는지 확인하고 spanning tree를 만든다(L1241-L1253).
5. 그 트리대로 Three.js 부모-자식 그룹을 구성하고, 평면 방향에 따라 ±90° 회전한다(L1266-L1279).
6. 완전히 접힌 세계 좌표에서 면 중심끼리 거리가 0.2 미만이면 겹침으로 본다(L1293-L1306).

따라서 미리 알려진 11개 정육면체 전개도 패턴과 대조하는 방식이 아니라, 학생의 자유 작도를 받아 **2D 인접 그래프를 3D로 전방 시뮬레이션**하는 방식이다.

### 우리 네모공장과의 비교

현재 작업공간에는 ‘네모공장’ 소스가 없어 코드 대 코드의 확정 비교는 할 수 없다. 다만 비교 축은 명확하다.

- 네모공장이 11개 정육면체 net의 정규형/회전·대칭 canonical key를 대조한다면: 전개도킹은 전혀 다른 방식이다. 임의 치수 직육면체까지 다루는 3D 접기 시뮬레이션이다.
- 네모공장이 각 면의 3D pose를 전파하고 최종 법선·격자 셀 점유를 검사한다면: 큰 방향은 같지만 전개도킹이 훨씬 약한 판정이다.

### 판정의 약점

- 최종 검사는 면 **중심점 거리만** 본다. 면이 부분 교차하거나 같은 평면에서 일부 겹치되 중심이 다르면 놓칠 수 있다.
- 접힌 결과가 목표 직육면체의 여섯 경계면을 정확히 한 번씩 덮는지, 법선이 ±X/±Y/±Z 한 쌍씩인지, 모서리가 닫혔는지 검사하지 않는다.
- 인접 그래프에 추가 힌지/사이클이 있어도 BFS spanning tree에 포함되지 않은 힌지는 접기 제약에서 버린다.
- 면 방향은 `getSortedPair`로 없앤다. 자유 회전 허용에는 유리하지만, 최종 목표 축과의 일관성은 별도 검증하지 않는다.
- 3D 판정 자체가 외부 Three.js/OrbitControls CDN에 의존한다(L18-L21). 네트워크가 없는 실제 실행 환경에서는 인라인 로직만으로 작동하지 않는다.

공장판 판정기는 이 소스의 설명 가능한 단계별 오류(`면 수/크기/연결/접힘 충돌`)는 유지하되, 3D pose를 정수 격자 basis로 계산하고 `법선+평면좌표+점유 사각형`의 정확 교차 및 목표 여섯 면 커버를 검사해야 한다.

## 6. 어림킹

### 올림/버림/반올림 생성과 자리 표현

**없다.** 소스 전체에 올림, 버림, 반올림, ‘○의 자리에서’, ‘○의 자리까지’ 문항 문자열이나 그에 대응하는 생성 모드가 없다. 메뉴는 기본 수, 큰 수, 소수, 분수, 각도, 원 넓이, 원주, 소수 나눗셈, 랜덤이다.

```html
<button ...>기본(0~100)</button>
<button ...>큰 수</button>
<button ...>소수</button>
<button ...>분수</button>
...
```

— `sources2/어림킹.html` L348-L358

따라서 이 파일은 문제의 함정인 ‘어느 자리에서 처리하느냐’와 ‘어느 자리까지 남기느냐’를 해결한 참고 사례가 아니다. 5-2-1 전체에 매핑했더라도 실제로는 **수직선 위치 어림**만 구현했다.

공장 문구 규칙은 별도로 고정해야 한다.

- `천의 자리에서 반올림` → 천의 자리 숫자를 보고 처리하므로 결과는 만의 자리 단위가 된다. 교과서 문맥에서 오해가 매우 쉽다.
- `천의 자리까지 나타내도록 반올림` → 천의 자리까지 남기므로 백의 자리에서 판단한다.
- 생성 스키마에는 자연어만 저장하지 말고 `decisionPlace`와 `retainedPlace`를 분리하고 둘 중 하나를 canonical prompt style로 선택해야 한다.

### 실제 게임의 어림 방식

각 문제는 `[start,end]`와 정확한 `target`을 만들고, 선수가 수직선에서 0~1 위치를 고른다. 결과는 값의 절대 오차가 아니라 구간 폭에 대한 상대 오차다.

```js
const targetRatio = (problem.target - problem.start) / range;
let diffRatio = Math.abs(p.currentPos - targetRatio);
if (diffRatio < 0.03) rankKing;
else if (diffRatio < 0.08) rankGood;
else if (diffRatio < 0.15) rankOkay;
```

— L980-L1018

좋은 점은 단위와 규모가 다른 문제도 동일한 오차비로 평가한다는 것이다. 그러나 `large` 모드도 특정 자리에서 어림한 답을 만드는 게 아니라 임의 정수를 수직선에 배치한다(L894-L900).

또한 분수 결과 표시는 선수의 연속 위치를 100분의 몇으로 반올림해 분수로 바꾼다(L996-L1009). 문제 분모와 무관하므로 ‘내 선택’이 원래 분수 격자에 스냅되지 않는다. 여기의 `Math.round/floor/ceil`은 표시·타이머용이지 올림/버림/반올림 학습 로직이 아니다.

## 7. 원킹

### 실제 콘텐츠

무작위 시작각의 1/4 원호와 양 끝점을 주고, 두 선수가 나머지 원을 손으로 이어 그린다. 즉 6-2 원의 둘레와 넓이를 계산하는 게임이 아니라 원의 형태/중심/반지름 감각을 겨루는 작도 게임이다.

```js
const startAngle = currentArcStartAngle;
const endAngle = currentArcStartAngle + 0.5 * Math.PI;
ctx.arc(p.cx, p.cy, p.radius, startAngle, endAngle);
```

— `sources2/원킹.html` L739-L758

### 채점 알고리즘

모든 획의 모든 점에서 중심까지 거리를 재고 목표 반지름과의 평균 절대 오차를 정확도로 바꾼다.

```js
const dist = Math.sqrt((pt.x-p.cx)**2 + (pt.y-p.cy)**2);
totalError += Math.abs(dist - R);
...
let accuracy = 100 - (avgError / R * 100);
```

— L859-L882

여기에 두 페널티를 뺀다.

- 길이: 그려야 할 3/4 원 길이 `1.5πR`의 70%보다 짧으면 감점(L884-L888)
- 연결: 첫/마지막 점을 주어진 두 끝점에 양방향으로 대응시킨 최소 gap이 `0.4R`보다 크면 감점(L890-L905)

최종 점수는 `accuracy - lengthPenalty - gapPenalty`를 0~100으로 자른다(L907-L914). 픽셀 유사도 대신 **의미 있는 기하 특성 세 개로 분해한 설명 가능한 휴리스틱**이다.

주의할 점은 여러 획을 단순 concat하고 획 경계에서도 이전 점과 다음 점 거리를 `pathLength`에 더한다는 것이다(L861, L869-L877). 떨어진 두 획 사이의 순간이동이 실제 그린 길이처럼 계산되어 길이 부족 페널티를 회피할 수 있다. 획별 길이를 따로 합쳐야 한다.

## 8. 나눗셈 채점킹

### 학생이 채점자가 되는 역전 구조

게임은 문제를 풀어 답을 입력하게 하지 않는다. 이미 답이 적힌 시험지를 보여 주고, 학생이 손으로 원(O) 또는 빗금(X 역할)을 그려 그 답의 옳고 그름을 판정한다. 시작 전 모든 선수가 두 제스처를 연습해야 본 게임으로 넘어간다(L2355-L2407).

제스처 인식은 복잡한 ML이 아니라 폐쇄도와 직선성 휴리스틱이다.

```js
if (closure < diag * 0.55 && pathLen > diag * 1.3) return 'circle';
const straightRatio = pathLen / Math.max(closure, 1);
if (straightRatio < 1.4 && closure > diag * 0.55) return 'slash';
```

— `sources2/나눗셈_채점킹.html` L2095-L2111

판정의 진실표는 명료하다.

```js
const mark = type === 'circle' ? 'O' : 'X';
const isRight = (mark === 'O' && row.isCorrect) ||
                (mark === 'X' && !row.isCorrect);
```

— L2563-L2571

학생은 계산 결과뿐 아니라 **타인의 답을 검증**해야 한다. 옳다고 본 이유와 틀렸다고 본 이유를 모두 활성화하고, 교사 역할·빨간 펜 제스처가 콘텐츠와 자연스럽게 결합한다.

### 문제와 오답 생성

먼저 몫 `n`, 나누는 수 `dan`, 나머지 `r`를 정하고 피제수를 역산한다.

```js
const r = remainderMode === 'with' ? getInt(0, dan - 1) : 0;
const a = dan * n + r;
```

— L2040-L2044

오답은 완전 랜덤이 아니라 다음 오개념을 반영한다.

- 몫 ±1/±2 또는 임의 한 자리
- 몫은 맞고 나머지만 틀림
- `몫-1, 나머지+나누는 수`로 값은 같지만 나머지 조건을 위반

```js
qCands = [n-2, n-1, n+1, n+2, random];
...
pool.add(fmtAns(p.n - 1, p.r + p.dan));
```

— L2047-L2058

마지막 후보는 `a = d*q+r` 값 자체는 보존하면서 `0 ≤ r < d` 규칙을 위반시키므로 1탄의 ‘오개념 역산 오답’이 가장 선명하게 반복된 사례다.

시험지마다 50~90%의 정답률을 먼저 뽑고 각 행을 옳거나 틀리게 만든다(L2075-L2089). 따라서 전부 O 또는 전부 X를 긋는 전략을 막으면서 시험지의 ‘학생 실력’도 매번 다르게 보인다.

### 채점킹 템플릿으로 분리할 경계

재사용 가능한 흐름은 다음과 같다.

1. `makeProblem(config)` — 참인 문제와 canonical answer 생성
2. `getWrongCandidates(problem, misconceptionRules)` — 의미 있는 거짓 답 생성
3. `buildSheet()` — 정오 비율을 샘플링해 제시 답 합성
4. `calibrateGestures()` — O/빗금 입력 연습
5. `grade(mark, row.isCorrect)` — 도메인과 무관한 진실표
6. 정답이면 다음 행, 오판이면 3초 freeze(L2595-L2601, L2619 이후)
7. 시간제는 성공 수, 시험지제는 목표 완료자의 시간 우선으로 랭킹(L2718-L2731)

덧셈·분수·소수·측정 단위 등 다른 채점킹은 1~2만 교체하고 3~7을 공유할 수 있다.

단, 이 파일의 실제 수학은 2~9단 자연수 나눗셈과 자연수 나머지다. 6-1/6-2 분수·소수 나눗셈을 생성하는 코드는 없으므로 해당 단원 매핑은 콘텐츠 범위를 과장한다.

## 1탄 패턴의 반복 여부

### 1. 자릿값/정답부터 제약 생성 — 반복됨

- 소수점 이동킹: `raw` 정수와 `dp`를 먼저 뽑아 표시 소수를 만든다.
- 킹네모 디펜스: 빈칸 정답을 먼저 고르고 피연산자를 역산한다.
- 나눗셈 채점킹: 몫·나머지를 먼저 고르고 피제수를 `d*q+r`로 만든다.
- 분수 캐치킹: 숫자 풀을 먼저 뽑고 min/max와 나머지 조건으로 분수 유형을 보장한다.
- 전개도킹: 목표 치수에서 필요한 여섯 면 multiset을 먼저 만든다.

즉 ‘표면 문제를 랜덤 조립한 뒤 검증’보다 **정답 불변량에서 외형을 파생**하는 패턴이 여전히 강하다.

### 2. 오개념 역산 오답 — 선택적으로 반복됨

- 가장 강한 사례는 나눗셈 채점킹의 몫 인접 오답, 나머지 오답, `r ≥ d` 함정이다.
- 킹네모 디펜스는 자유 입력이라 오답 후보가 없지만, 나눗셈 문제를 역산해 유효 정답을 보장한다.
- 확률킹/소수점 이동킹/분수 캐치킹/전개도킹/어림킹/원킹은 명시적 오개념 distractor를 만들지 않는다.
- 분수 캐치킹의 1~9 버블은 decoy지만 오개념 기반은 아니다.

### 3. 설정 주입 엔진 — 형태를 바꿔 반복됨

- 소수점 이동킹: `difficulty → modeType → generator branch`
- 분수 캐치킹: `selectedTypes`, 동일/개별 문제, 시간, 선수 수를 생성과 진행에 주입
- 나눗셈 채점킹: 선택 단, 나머지 모드, 시간/시험지 모드, 선수 수를 주입
- 어림킹: 모드가 `[start,end,target,type]` 문제 객체를 바꿈
- 킹네모 디펜스: 설정 UI가 아니라 점수 레벨을 주입하지만, 단원 프로필로 분리되지 않아 불완전
- 전개도킹/원킹/확률킹은 수학 콘텐츠 설정 폭이 좁다.

## 공장 반영 신규 패턴

### A. 비교 판단에 운동 기술을 얹는 ‘판단+타이밍’

확률킹은 답 버튼 대신 왕복 바늘을 쓴다. 수학 판단을 끝낸 뒤 운동 타이밍을 요구해 긴장감을 만든다. 다만 조작 실패가 개념 실패로 기록되는 문제도 있으므로, 공장에서는 `mathDecision`과 `timingExecution`을 별도 로그로 남겨야 한다.

### B. 공유 문제열 + 선수별 커서

분수 캐치킹의 `sharedProblems[player.solvedCount]`는 속도가 다른 동시 플레이에서도 같은 n번째 문제를 보장한다. 공장 공통 멀티플레이 모듈로 승격할 가치가 크다. 무한 확장은 마지막 문제와 같은 분모/유형 반복을 피하는 국소 제약 생성기로 처리한다.

### C. 자유 산출물은 ‘불변량 → 연결 → 시뮬레이션 → 충돌’로 판정

전개도킹은 자유 작도를 객관식으로 축소하지 않고, 면 multiset·연결성·3D 접기·충돌의 단계로 판정한다. 공장에서는 이를 일반화하되 마지막 단계는 중심점 휴리스틱이 아니라 정확한 격자 점유로 강화한다. 실패 이유를 단계별로 돌려주는 것도 함께 표준화한다.

### D. 채점자 역할 역전

나눗셈 채점킹의 가장 큰 신규 패턴이다. `문제 풀기`를 `제시 답 검증하기`로 뒤집으면 동일 연산을 다른 인지 활동으로 만든다. 이 패턴의 품질은 무작위 오답이 아니라 오개념 오답 라이브러리에 달려 있다.

### E. 입력 제스처 사전 보정(calibration gate)

채점킹은 본 게임 전에 각 선수에게 원/빗금을 실제로 그리게 하고 모두 통과해야 시작한다. 터치·필기·음성 게임은 튜토리얼을 설명 화면으로 끝내지 말고 **입력 인식 성공을 시작 조건**으로 삼는 것이 안전하다.

### F. 연속값 평가는 절대 오차보다 정규화 오차

어림킹은 서로 다른 구간을 `(선택-정답)/(end-start)`로 정규화해 공통 등급 임계값을 쓴다. 단위가 다른 추정 게임에 재사용 가능하다. 다만 학습 목표가 특정 허용오차를 요구하면 상대 오차와 교과 기준을 분리해야 한다.

### G. 생성 프로필과 페이싱 프로필 분리

킹네모 디펜스의 실패에서 얻는 패턴이다. `levelIdx` 하나로 수학 범위와 적 속도를 같이 바꾸지 않는다.

```text
ContentProfile  = 단원, 수 범위, 연산, 표현, 오개념, 답 codec
PacingProfile   = 제한시간, 속도, 스폰율, 페널티, 콤보
SessionSettings = 선수 수, 공유 seed, 모드
```

이 세 층을 분리해야 “여러 단원에 매핑됨”을 테스트로 증명할 수 있다.

### H. 확률/가능성 게임은 이론 모델과 실험 모델을 이중 상태로

확률킹의 공백을 보완하는 신규 공장 규칙이다.

```text
event.theoretical = favorable / total
experiment = { trials, successes, history }
languageBand = classify(theoretical)  // 불가능, 반반, 확실 및 중간 언어
```

한 라운드는 먼저 가능성 언어/위치를 예측하고, 실제 시행을 여러 번 돌려 빈도 막대를 누적하며, 마지막에 이론값과 실험값의 차이를 비교해야 한다. 5-2에서는 분수 계산을 정답 입력으로 요구하지 말고 0·1/2·1의 기준 사건을 충분히 포함해야 한다.

### I. 자리 문구는 데이터 모델에서 둘로 분리

어림킹에는 해당 기능이 없다는 사실 자체가 경고다. 공장 표준은 다음 필드를 강제해야 한다.

```text
roundingMode: ceil | floor | halfUp
decisionPlace: 어느 자리 숫자를 보고 처리하는가
retainedPlace: 결과에서 마지막으로 남는 자리
promptConvention: AT_PLACE | TO_PLACE
```

문구 렌더러와 계산기는 같은 필드에서 파생하고, `AT_PLACE`와 `TO_PLACE`의 기대 결과가 다른 회귀 테스트를 둔다. 자연어 문자열에서 계산 의미를 역추론하면 안 된다.

### J. 교육용 생성 실패는 데이터 변조가 아니라 재샘플/명시 상태

확률킹의 동률을 0%로 바꾸는 처리는 금지 패턴이다. 후보 풀이 작으면 가능한 문항을 사전 열거하고, 필터 결과가 비면 `tie` 문항을 명시적으로 렌더하거나 생성 실패를 상위 레이어로 돌려야 한다.

---

## 최종 제안 우선순위

1. 가능성 게임은 확률킹의 UI 껍데기만 참고하고, 0·1/2·1 언어 분류 + 반복 시행 빈도 누적의 새 엔진으로 다시 설계한다.
2. 전개도 판정은 전방 시뮬레이션 방향을 채택하되 중심점 충돌을 정확 점유/법선/폐합 검사로 교체한다.
3. 올림·버림·반올림 공장 스키마에 `decisionPlace`/`retainedPlace`를 분리하고 두 한국어 문구 convention을 회귀 테스트한다.
4. 소수점 이동은 문자열 mantissa/scale 모델로 재구현하고, 이 소스의 동일 계산 경로 아이디어만 유지한다.
5. 다단원 게임은 콘텐츠 프로필과 페이싱 프로필을 분리한다. 현재 킹네모 디펜스식 레벨 숫자 하나로는 단원 매핑을 보장할 수 없다.
6. 채점킹은 공통 템플릿으로 추출하고, 단원별 오개념 후보 생성기만 플러그인으로 교체한다.
