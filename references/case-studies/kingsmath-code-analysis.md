# 킹수학 게임 소스 오프라인 분석

## 분석 범위와 판정 기준

- 대상은 `sources/` 아래의 다섯 `index.html`이며, 요청 조건에 따라 외부 JS의 내용은 조회하거나 추정하지 않았다.
- 코드 인용의 행 번호는 제공된 원본 HTML 기준이다.
- **확인**은 인라인 코드가 직접 증명하는 사실, **UI 계약**은 HTML의 문구·DOM ID가 드러내는 상태/기능, **확인 불가**는 구현이 외부 JS에만 있는 경우다.
- 중요한 데이터 결손: `king_vs.html`은 게임 HTML이 아니라 서버의 **404 응답(총 7행, 196B)** 이다. 따라서 학급대항전 내부 구현은 이 자료에 없다.

## 1. 분수팡킹 — `kingpangpang.html`

### 1) 문제 생성기

**확인 불가.** 인라인 JavaScript는 Google Analytics 초기화뿐이며, 게임 로직은 마지막의 외부 파일 하나에 위임한다.

```html
<!-- kingpangpang.html:398 -->
<script src="game.js"></script>
```

HTML에는 “7단계”와 “분수 공”이라는 콘텐츠 구조만 보인다.

```html
<!-- kingpangpang.html:80, 284-285 -->
<div><strong>7단계를 모두 정복</strong>하고 명예의 전당에 이름을 올려보세요!</div>
분수 공을 터뜨리면 유용한 이모지 아이템이 떨어집니다!
<span class="sub-en">Pop fraction balls to collect powerful items!</span>
```

따라서 분수의 분자·분모 범위, 기약분수 여부, 동치분수 생성 여부, 하드코딩/알고리즘 여부는 판정할 수 없다.

### 2) 오답 선택지

**확인 불가.** 선택지 DOM이나 오답 배열이 없고, 보이는 조작은 작살 발사형 액션 게임이다. 오답 선택지형 게임이 아닐 가능성은 높지만 실제 충돌/분수 매칭 규칙은 `game.js`에 있어 단정할 수 없다.

### 3) 정답 판정과 분수 처리

**확인 불가.** 분수 비교가 문자열인지, `numerator/denominator` 구조인지, 교차곱인지, 실수 변환인지 인라인 코드에 없다. 게임 제목만으로 “분수 처리” 구현을 역추정하면 안 된다.

### 4) 게임 상태 구조

상태 변수 자체는 외부 `game.js`에 있지만, UI 계약으로 다음 상태가 드러난다.

- 모드: 1P / 2P 협동, 2P일 때 닉네임 두 개.
- 진행: 총 7스테이지, 스테이지 보너스와 누적 점수, 클리어 후 3초 전환.
- 생명: 하트 회복, 최대 5개. 2P에서는 쓰러진 팀원 부활.
- 일시 상태: 12초 더블 작살, 4초 시간 정지, 전체 공 1단계 분할.
- 종료/기록: 최종 점수, 최고 기록, 7단계 완주자 Top 100.

```html
<!-- kingpangpang.html:86-96 -->
<button ... id="tabMode1P">🎮 1인용 ...</button>
<button ... id="tabMode2P">👥 2인용 협동 ...</button>

<!-- kingpangpang.html:156-175 -->
<div class="val" id="stageClearScore">+1,000</div>
<div class="val" id="stageClearTotal">1,000</div>
...
<div class="stage-timer-bar" id="stageTimerBar"></div>

<!-- kingpangpang.html:293-325 -->
12초간 작살을 동시에 2발까지 발사합니다.
4초간 모든 분수 공의 움직임이 멈춥니다.
하트 +1 회복 / 쓰러진 팀원 즉시 부활 (최대 5개)
화면의 모든 공을 즉시 1단계 하위 분수로 쪼갭니다.
```

콤보의 존재는 HTML에서 확인되지 않는다. 목숨 감소 조건도 “분수 공에 부딪힘” 문구 외에는 알 수 없다.

### 5) 교실용 장치

학급 단위 관리 기능은 없지만, 한 기기에서 2명이 협동할 수 있게 입력을 분리한다.

```html
<!-- kingpangpang.html:363-393 -->
<!-- Left Panel: 1P Controls (A, D, W) -->
...
<!-- Right Panel: 2P Controls (◀, ▶, ▲ / Space) -->
```

두 플레이어 닉네임을 별도로 받으며, 팀원이 쓰러졌을 때 생명 아이템으로 부활시키는 협동 설계가 있다. 다만 팀 수, 학생 명단, 반별 점수 집계 같은 학급대항전 기능은 아니다.

### 6) 아키텍처·품질·사운드/이펙트

- HTML은 `canvas#gameCanvas`(960×640), 모달/HUD DOM, 외부 `style.css`, 외부 `game.js`로 구성된 단일 엔진 셸이다.
- 사운드는 `button#btnSound`라는 UI 계약만 보이고 구현/API는 `game.js` 안이라 확인 불가다.
- 이펙트는 별도 모듈 흔적 없이 canvas 엔진 또는 CSS에 함께 들어갔을 가능성만 있다. 이를 사실로 단정할 수는 없다.
- 장점: 1P/2P 터치 패널, 키보드 키 라벨, pause/help/fullscreen 등 교실의 전자칠판·태블릿 사용성을 HTML에서 명확히 설계했다.
- 단점: 게임 규칙과 상태가 한 외부 `game.js`에 몰린 형태라면 결합도가 높을 수 있으나, 파일 내용이 없으므로 실제 코드 품질 평가는 제한적이다.

## 2. 트로피 탈출킹 — `king_trophy.html`

### 1) 문제 생성기

**하드코딩 문제 목록이 아니라, 10개의 교육과정 단원별 알고리즘 생성기다.** 각 항목은 `{ name, gen: function(){...} }`이며 난수를 범위 제약에 맞춰 뽑는다. `ri(min,max)` 구현은 외부 `mathkit.js`라 경계 포함 여부는 함수명만으로는 확정할 수 없지만, 호출 문맥은 양 끝을 포함하는 정수 난수로 설계되었다고 읽힌다.

교육과정 범위 자체를 먼저 차단한다.

```js
/* king_trophy.html:22-26 */
1학년 : 100까지의 수 / 한 자리 수의 덧셈과 뺄셈 / 받아올림·받아내림이
        없는 두 자리 수의 덧셈과 뺄셈
2학년 : 세 자리 수 / 받아올림·받아내림이 있는 두 자리 수의 덧셈과 뺄셈 /
        곱셈구구
※ 나눗셈·분수·소수는 3학년 이상이라 저학년에서는 한 문제도 내지 않는다.
```

단원별 제약은 다음과 같다.

1. 한 자리 덧셈: `a=1..8`, `b=1..(9-a)`로 합을 9 이하로 제한.

   ```js
   /* :47 */
   var a = ri(1, 8), b = ri(1, 9 - a), s = a + b;
   ```

2. 한 자리 뺄셈: `a=3..9`, `b=1..a-1`로 양의 차 보장.

   ```js
   /* :55 */
   var a = ri(3, 9), b = ri(1, a - 1), s = a - b;
   ```

3. 10 모으기/가르기: `s=10-a`; 같은 수 관계를 덧셈의 빈칸과 뺄셈 두 표상으로 50:50 제시.

   ```js
   /* :63-69 */
   var a = ri(1, 9), s = 10 - a;
   if(Math.random() < 0.5){
     return { q: a + ' + ? = 10', a: String(s), ... };
   }
   return { q: '10 − ' + a, a: String(s), ... };
   ```

4. 받아올림 덧셈: `a=5..9`, `b=11-a..9`, 따라서 합 11~18.

   ```js
   /* :74 */
   var a = ri(5, 9), b = ri(11 - a, 9), s = a + b;
   ```

5. 두 자리+한 자리, 받아올림 없음: 일의 자리 `o=1..5`, `b<=9-o`.

   ```js
   /* :82-83 */
   var t = ri(2, 8), o = ri(1, 5), b = ri(1, 9 - o);
   var a = t * 10 + o, s = a + b;
   ```

6. 두 자리−한 자리, 받아내림 없음: `o=5..9`, `b<o`.

   ```js
   /* :91-92 */
   var t = ri(2, 9), o = ri(5, 9), b = ri(1, o - 1);
   var a = t * 10 + o, s = a - b;
   ```

7. 두 자리 덧셈, 받아올림 필수: 일의 자리 합이 적어도 10이 되도록 `bo>=10-ao`.

   ```js
   /* :100-102 */
   // 일의 자리 합이 반드시 10을 넘도록 자리별로 만든다
   var ao = ri(2, 9), bo = ri(10 - ao, 9);
   var a = ri(1, 7) * 10 + ao, b = ri(1, 7) * 10 + bo, s = a + b;
   ```

   주석의 “10을 넘도록”은 코드상 **10 이상**이다. `ao+bo===10`도 허용한다.

8. 두 자리 뺄셈, 받아내림 필수: `ao<bo`, 동시에 `at>bt`.

   ```js
   /* :110-113 */
   var ao = ri(0, 7), bo = ri(ao + 1, 9);
   var at = ri(3, 9), bt = ri(1, at - 1);
   var a = at * 10 + ao, b = bt * 10 + bo, s = a - b;
   ```

9. 쉬운 구구: 단은 `[2,5,3]`, 곱하는 수는 2~9.
10. 어려운 구구: 단은 `[6,7,8,9]`, 곱하는 수는 2~9.

   ```js
   /* :122, :130 */
   var a = [2, 5, 3][ri(0, 2)], b = ri(2, 9), s = a * b;
   var a = [6, 7, 8, 9][ri(0, 3)], b = ri(2, 9), s = a * b;
   ```

헤더 주석은 2학년 범위로 “세 자리 수”도 적지만, 실제 10개 `gen`에는 세 자리 수 읽기·계산 문제가 없다. 즉 문서화한 교육과정 범위와 실출제 커버리지 사이에 공백이 있다.

### 2) 오답 선택지

**단순 랜덤 숫자가 아니라 오개념 역산 후보가 중심**이며, 정답 주변 `±1`을 보조로 섞는다. 모든 단계가 `wrongs(String(s), candidates)`를 호출한다. `wrongs`의 중복 제거, 범위 필터, 셔플 방식은 외부 `mathkit.js`라 확인 불가다.

대표 패턴:

- 연산자 혼동: 뺄셈 문제에 `a+b`.
- 받아올림 누락: `s-10`.
- 잘못된 자릿값: `23+4 → 63`에 해당하는 `a+b*10`.
- 잘못된 자릿값: `47-3 → 17`에 해당하는 `a-b*10`.
- 받아내림 없이 자리별 큰 수−작은 수: `flip`.
- 구구 한 칸 밀림: `a*(b-1)`, `a*(b+1)`.

```js
/* :57-58 */
// 대표 실수: 빼야 하는데 더함
w: wrongs(String(s), [a + b, s + 1, s - 1, b])

/* :85-86 */
// 대표 실수: 십의 자리에 더해 버림 (23 + 4 → 63)
w: wrongs(String(s), [a + b * 10, s + 10, s - 1, s + 1])

/* :114-117 */
// 대표 실수: 받아내림 없이 각 자리에서 큰 수 - 작은 수 (52 − 27 → 35)
var flip = Math.abs(Math.floor(a / 10) - Math.floor(b / 10)) * 10
         + Math.abs((a % 10) - (b % 10));
return { ..., w: wrongs(String(s), [flip, s + 10, s - 10, s + 1]) };

/* :124 */
w: wrongs(String(s), [a * (b - 1), a * (b + 1), a + b, s + 1])
```

주의할 품질 이슈도 있다. 예컨대 정답이 1인 문제에서 `s-1`은 0이 될 수 있고, 후보끼리 중복되거나 정답과 같아질 수 있다. 이것을 `wrongs()`가 정리하는지는 외부 코드 없이는 알 수 없다. 생산 공장에서는 생성 후 `정답 제외 → 범위 검증 → 중복 제거 → 부족분 보충 → 셔플`을 명시적으로 보장해야 한다.

### 3) 정답 판정·부동소수점·분수

생성기는 정답을 모두 `String(s)`로 정규화한다.

```js
return { q: a + ' + ' + b, a: String(s), w: wrongs(String(s), [...]) };
```

그러나 실제 클릭 답과 `a`를 어떻게 비교하는지는 외부 `engine.js`에 있다.

```html
<!-- :136-137 -->
</script>
<script src="engine.js"></script>
```

- 이 버전은 모든 산술이 정수 덧셈/뺄셈/곱셈이므로 부동소수점 함정 자체를 회피한다.
- 주석상 분수·소수·나눗셈을 출제하지 않으므로 분수 처리 로직도 없다.
- 문자열 정답은 표시/비교 형식을 통일하는 장점이 있지만, 엄격 비교인지 숫자 변환 비교인지는 알 수 없다.

### 4) 게임 상태 구조

점수·콤보·목숨·타이머의 실제 변수는 `engine.js`에 있어 확인 불가다. 인라인에는 게임 난이도/물리 설정과 콘텐츠 단계만 주입된다.

```js
/* :38-42 */
run: 1.35, jump: -4.15, grav: 0.16, climb: 0.9, jetSpeed: 1.25, jetBurn: 0.21,
shotSpeed: 1.25,
monsters: 'static',
hazards:  'none',
dangerNote: '... 떨어지거나 거미에 닿을 때만 목숨이 줄어요.',
```

즉 저학년판은 이동 속도를 낮추고, 몬스터를 정지시키며, 환경 위험을 제거하는 **난이도 설정 객체**를 사용한다. 목숨이 있다는 것은 문구로 확인되지만 초기 목숨 수, 감점, 콤보, 제한시간은 확인할 수 없다.

### 5) 교실용 장치

학급/팀/학생 명단 관리 기능은 인라인에 없다. 대신 `badge: 'GRADE 1-2'`, `gradeName: '초급'`, `curriculum` 배열로 학년군 콘텐츠를 엔진에 주입하는 교사용 콘텐츠 분리가 핵심이다.

### 6) 아키텍처·품질·사운드/이펙트

가장 뚜렷한 공용 재사용 구조다.

```html
<script src="mathkit.js"></script>
<script>
window.KING = { ... curriculum: [...] };
</script>
<script src="engine.js"></script>
```

- `mathkit.js`가 `ri`, `wrongs` 같은 수학 유틸을 제공하고, 페이지는 `window.KING` 설정/교육과정만 선언하며, `engine.js`가 게임 실행을 맡는 **설정 주입형 공용 엔진** 패턴이다.
- 장점: 학년 버전을 만들 때 엔진을 복제하지 않고 속도·위험·문항 생성기만 바꿀 수 있다. 주석도 교육과정 의도를 코드 가까이에 둬 유지보수성이 좋다.
- 단점: `window.KING` 전역, `var`, 축약 키 `q/a/w`, 익명 함수가 많아 스키마 검증과 타입 안정성이 없다. `ri`/`wrongs`의 계약도 이 파일만으로 불투명하다.
- 사운드/이펙트 구현은 이 HTML에 전혀 드러나지 않아 평가 불가다.

```html
<h1>Not Found</h1>
<p>The requested URL was not found on this server.</p>
</body></html>
```

### 1~4) 생성기·오답·판정·게임 상태

모두 **분석 불가**다. 스크립트, UI, 데이터 구조가 한 줄도 없다.

### 5) 여러 팀/학생 관리 방식

**분석 불가이며, 존재한다고 추론할 근거도 없다.** 팀 배열, 학생 객체, 점수판, 로컬 저장, 네트워크 동기화, QR 입장 등의 어떤 구현도 제공 파일에 없다. 이 질문에 답하려면 올바르게 저장된 `king_vs` index와 그 인라인 스크립트가 필요하다.

### 6) 아키텍처·품질·사운드/이펙트

분석 불가. 다만 수집 파이프라인 관점에서는 HTTP 오류 본문을 `.html` 소스로 저장한 실패 사례다. 자동 수집 시 최소한 다음 검증이 필요하다: HTTP 2xx 확인, `<title>404`/`<h1>Not Found` 차단, 최소 파일 크기, 예상 게임 루트 DOM 또는 script 존재 확인.

## 4. 뱅뱅텐킹 — `king-bangbang.html`

### 1) 문제 생성기

전통적인 문항/선택지 게임이 아니라 **발사되는 1~9 숫자 구슬과 현재 목표 합을 맞추는 상태형 퍼즐**이다. 규칙은 인라인 HTML에 자세히 적혀 있지만 숫자 구슬의 분포, 다음 구슬 생성, 보너스 목표(12·11·13…) 순서는 외부 JS에 있다.

```html
<!-- :100-101, :169-172 -->
<div class="tagline">...<b>합 10</b>을 만들어 터뜨려라</div>
...
붙어 있는 <b>두 개</b>의 합이 <b>목표 합(기본 10)</b>이 되면 터집니다.<br>
<span class="eq">1+9</span> ... <span class="eq">5+5</span><br>
<b>3개 이상을 더하는 건 안 됩니다.</b> (1+2+7 ✗)
```

```html
<!-- :355-367 -->
<script src="js/rules.js?v=2.1"></script>
<script src="js/track.js?v=2.1"></script>
<script src="js/ball.js?v=2.1"></script>
<script src="js/cannon.js?v=2.1"></script>
...
<script src="js/main.js?v=2.1"></script>
```

따라서 “하드코딩 배열인가 알고리즘인가”는 판정할 수 없다. 다만 DOM에 `#next-ball-num`과 `#target-value`가 있어 엔진이 “다음 구슬”과 “목표 합”을 별도 상태로 관리한다는 UI 계약은 확실하다.

### 2) 오답 선택지

선택지 자체가 없다. 플레이어가 조준/발사 위치를 선택하고, 인접한 정확히 두 수가 목표 합인지가 성공/실패를 결정하는 유형이다. 따라서 랜덤 오답이나 오개념 역산 배열은 해당되지 않는다. “조준 확인”과 “한 방 레이더”는 오답 선택지가 아니라 즉시 피드백/힌트다.

```html
<!-- :265-271 -->
<span>조준 확인<small>지금 쏘면 터지는 자리면 조준선이 초록색</small></span>
...
<span>한 방 레이더 (◆)<small>3개 이상 터뜨릴 수 있는 자리 표시</small></span>
```

### 3) 정답 판정·부동소수점·분수

실제 판정 코드는 외부 `rules.js` 등에 있어 확인 불가다. 인라인 규칙상 판정 모델은 “인접한 정확히 두 정수의 합 === 목표 정수”이며 입력 범위는 1~9이므로 부동소수점과 분수 문제는 구조적으로 없다. 같은 숫자 덩어리는 맞은 짝과 함께 전체 폭발하고, 롤백 후 다시 목표 합이 되면 연쇄 판정한다는 규칙만 확인된다.

```html
<!-- :179-191 -->
짝이 된 구슬이 <b>같은 숫자 뭉치</b>의 일부라면 <b>뭉치 전체가 함께 폭발!</b>
...
이어진 자리에서 또 10이 되면 <b>연쇄 폭발</b>이 일어납니다.
```

조커가 “필요한 숫자로 변신”할 때 어떤 우선순위를 쓰는지는 외부 코드라 알 수 없다.

### 4) 게임 상태 구조

구체 변수는 외부지만 UI/규칙이 매우 풍부한 상태 계약을 드러낸다.

- 점수와 최고점, 명예의 전당까지 1,000점 진행률.
- 웨이브와 플레이 시간. 20초마다 웨이브 상승.
- 콤보 미터/배너, 최대 연쇄, 최대 같은 숫자 연결 수.
- 4의 배수 웨이브에서 목표 합 변경 및 점수 2배.
- 목숨은 없다. 선두 구슬이 블랙홀에 닿는 위치 기반 게임오버다.
- 발사 쿨다운 약 0.8초.

```html
<!-- :35-47, :61-65 -->
<span class="hud-value" id="hud-score">0</span>
<div class="hof-fill" id="hud-hof-fill"></div>
<div class="hud-chip" id="hud-wave">W1</div>
<div class="hud-chip time" id="hud-time">0:00</div>
<div id="combo-meter" class="combo-meter"></div>
<div id="combo-display" class="combo-banner"></div>

<!-- :206-208 -->
20초마다 웨이브가 올라가며 속도·난이도가 상승합니다.<br>
4의 배수 웨이브에서는 <b>목표 합이 12·11·13…으로 바뀌고 점수 2배</b>가 됩니다.

<!-- :233-234 -->
맨 앞 구슬이 트랙 끝 블랙홀에 닿으면 종료됩니다.
```

점수 계산식 전체는 보이지 않지만 “같은 숫자 3개 이상 폭발마다 +8점”은 명시되어 있다.

### 5) 교실용 장치

개인 닉네임/랭킹형이지 팀/학생 명단형은 아니다. 교실 친화 요소는 전자칠판 키보드(← → Space), 터치/마우스 조준, 진동, 조준 도움/힌트, 다국어 UI, 일시정지다. 한 기기의 접근성은 좋지만 학급 점수 합산 기능은 확인되지 않는다.

### 6) 아키텍처·품질·사운드/이펙트

다섯 소스 중 가장 모듈 경계가 세분화되어 있다.

```html
<script src="js/i18n-data.js?v=1.0"></script>
<script src="js/i18n.js?v=1.0"></script>
<script src="js/lang-ui.js?v=1.0"></script>
<script src="js/audio.js?v=2.1"></script>
<script src="js/rules.js?v=2.1"></script>
<script src="js/track.js?v=2.1"></script>
<script src="js/ball.js?v=2.1"></script>
<script src="js/cannon.js?v=2.1"></script>
<script src="js/effects.js?v=2.1"></script>
<script src="js/director.js?v=2.1"></script>
<script src="js/profanity.js?v=2.1"></script>
<script src="js/leaderboard.js?v=2.1"></script>
<script src="js/main.js?v=2.1"></script>
```

- 도메인별 분리(`rules`, `track`, `ball`, `cannon`, `effects`, `director`)는 재사용·테스트에 유리한 흔적이다. 단, ES module이 아닌 전역 script의 순서 의존성은 잠재적 약점이다.
- `?v=2.1` 캐시 버스팅, `data-i18n` 기반 번역, 금칙어와 리더보드의 별도 모듈은 운영 서비스 수준의 관심사 분리다.
- 사운드는 `audio.js`로 분리하고 BGM/SFX를 각각 토글한다. 효과는 `effects.js`, 화면은 canvas, 위험/콤보/웨이브 오버레이는 DOM/CSS를 혼합한다.
- 진동/햅틱도 설정으로 노출한다. 실제 Web Audio, 파일 preload, 진동 API 호출 방법은 외부 코드라 확인할 수 없다.

## 5. 터치터치 배수킹 — `smart_touchtouch.html`

### 1) 문제 생성기

미션 숫자의 배수를 만드는 게임이라는 규칙만 있고, 미션 숫자를 어떤 범위/분포/중복 방지로 고르는지는 외부 `game.js`에 있다.

```html
<!-- :58-59 -->
<div class="mission-hero-label">이번 미션</div>
<div class="mission-hero-num"><span id="mission-num">2</span>의 배수!</div>

<!-- :140-143 -->
<script src="i18n.js"></script>
<script src="audio.js"></script>
<script src="game.js"></script>
```

따라서 하드코딩 배열/알고리즘 생성 여부, 수 범위, 같은 미션 연속 방지 등은 확인 불가다.

### 2) 오답 선택지

선택지형이 아니다. 플레이어의 누적 터치 수 자체가 응답이다. 따라서 랜덤/오개념 역산 오답은 해당되지 않는다.

### 3) 정답 판정·부동소수점·분수

판정 구현은 외부 `game.js`라 직접 인용할 수 없다. 다만 사용자에게 공개된 성공 규칙은 명확하다.

```html
<!-- :131-134 -->
<div class="rule-item">... 미션 숫자가 나와요 (예: 3의 배수)</div>
<div class="rule-item">... 5초 안에 화면을 빠르게 터치!</div>
<div class="rule-item">... 터치 수가 <b>10번 이상</b> &amp; 미션 숫자의 배수면 성공!</div>
<div class="rule-item">... 터치 수는 계속 <b>이어져요</b>! 다음 미션도 누적해서 터치!</div>
```

상식적으로는 `touchCount >= 10 && touchCount % mission === 0` 형태겠지만, 실제 코드가 없으므로 이것은 **설명에 기반한 예상식일 뿐 코드 판독 결과가 아니다.** 값이 정수 터치 횟수와 정수 미션이므로 부동소수점/분수 함정은 없다.

### 4) 게임 상태 구조

UI 계약상 상태는 `mission`, 누적 `touchCount`, 라운드 `timer`(5.0초), 마지막 성공 점수, 실패 수식/사유, 닉네임/랭킹이다.

```html
<!-- :62-71 -->
<span id="live-touch-count">0</span>
<small>누적 터치</small>
...
<div id="timer-bar-fill" class="timer-bar-fill"></div>
<span id="timer-text" class="timer-bar-text">5.0</span>

<!-- :92-101 -->
<div class="equation-line" id="result-equation"></div>
<div class="fail-reason" id="result-reason"></div>
...
<div class="final-score-label">최종 점수 (마지막 성공 기록)</div>
<div class="final-score" id="result-score">0</div>
```

- 점수는 “마지막 성공 기록”으로 정의되어 있어 누적 터치 수 또는 마지막 성공 배수값을 보존하는 구조로 보이지만 정확한 대입식은 확인 불가다.
- 콤보와 목숨 UI는 없다. 한 라운드 실패가 즉시 게임 종료로 이어지는 구조를 결과 화면이 시사하지만 이벤트 코드는 확인할 수 없다.
- 24시간 Top 100과 결과 Top 3를 별도 표시한다.

### 5) 교실용 장치

팀 관리 기능은 없다. 대신 시작 화면의 QR 확대, 최대 8자 닉네임, 모바일 터치 최적화(`user-scalable=no`, `viewport-fit=cover`), 24시간 랭킹은 학생들이 각자 기기로 빠르게 참가하고 경쟁하는 형태에 맞춰져 있다. QR이 어떤 URL을 담는지는 외부 코드/라이브러리 호출이 없어 확인 불가다.

### 6) 아키텍처·품질·사운드/이펙트

- DOM 화면을 `screen-start`, `screen-game`, `screen-result`로 나눈 간단한 상태 화면 구조다.
- 번역(`i18n.js`), 사운드(`audio.js`), 게임(`game.js`)을 분리한다. `data-i18n`/`data-i18n-attr`는 HTML을 번역 키의 원천으로 사용한다.
- QR은 CDN의 `qrcode.min.js`를 사용하므로 오프라인 실행 시 라이브러리가 캐시되지 않았다면 QR 기능이 깨진다. 이는 “완전 오프라인 패키지” 관점의 약점이다.
- 효과는 `round-toast`, timer bar 등 DOM/CSS 기반 흔적이 있으나 애니메이션 실행 코드는 `game.js`라 확인 불가다.
- UI와 규칙 문구는 간결하지만, 수학 규칙(미션 범위/공정성/연속 중복 방지)이 외부 코드에 감춰져 HTML만으로는 검증성이 낮다.

## 공통 아키텍처 비교

### 공용 유틸·재사용 흔적

1. **트로피 탈출킹:** `mathkit.js → window.KING 설정 → engine.js`의 명백한 공용 엔진/수학 유틸 구조.
2. **뱅뱅텐킹:** i18n, audio, rules, 물리 객체, effects, director, profanity, leaderboard를 도메인별로 분해.
3. **터치터치 배수킹:** i18n/audio/game의 가벼운 3분할.
4. **분수팡킹:** style/game의 큰 단위 분리만 확인.
5. **학급대항전:** 404라 비교 불가.

다른 게임들이 같은 파일을 실제로 공유한다는 증거는 없다. 예를 들어 여러 게임에 `audio.js`라는 이름이 있지만 경로와 내용이 없으므로 동일 모듈이라고 단정할 수 없다.

### 코드 품질 총평

- 수학 생성 품질은 트로피 탈출킹이 가장 검증 가능하고 좋다. 범위를 무작위로 뽑는 데 그치지 않고 받아올림/받아내림을 자리별 조건으로 강제하며 오답도 오개념을 반영한다.
- 운영/UI 아키텍처는 뱅뱅텐킹이 가장 세분화되어 있다. 반면 고전 `<script>` 나열은 로딩 순서와 전역 의존성을 숨긴다.
- 나머지는 게임 핵심이 외부 코드여서 현재 자료만으로 내부 품질을 평가할 수 없다. “HTML이 정교하다”와 “게임 로직이 견고하다”는 별개다.
- 모든 게임 공통의 검증 개선점은 명시적 콘텐츠 스키마, 생성 후 불변조건 검사, seed 가능한 RNG, 순수 함수 단위 테스트, 판정 함수와 표시 형식의 분리다.

### 사운드·이펙트 비교

- 분수팡킹: sound toggle만 확인; canvas + DOM toast/buff bar.
- 트로피 탈출킹: 인라인 증거 없음.
- 뱅뱅텐킹: `audio.js`와 `effects.js`를 분리하고 BGM/SFX/진동을 독립 설정; canvas + DOM overlay 혼합.
- 터치터치 배수킹: `audio.js` 분리, toast/timer DOM 이펙트.
- 학급대항전: 확인 불가.

## 우리 공장 빌드 프롬프트에 반영할 구현 패턴 5개

아래 문장은 그대로 빌드 프롬프트의 요구사항으로 옮길 수 있는 수준으로 작성했다.

### 패턴 1. 단원 제약을 만족하도록 “자리부터” 생성하라

실제 코드:

```js
// 일의 자리 합이 반드시 10을 넘도록 자리별로 만든다
var ao = ri(2, 9), bo = ri(10 - ao, 9);
var a = ri(1, 7) * 10 + ao, b = ri(1, 7) * 10 + bo, s = a + b;
```

빌드 프롬프트 반영:

> 문제를 만든 뒤 단원 조건을 사후 검사하며 재시도하지 말고, 받아올림/받아내림/나머지/약수 등 핵심 성질을 만족하도록 자릿값·인수를 먼저 생성하라. 각 생성기는 `assert` 가능한 불변조건과 학년별 수 범위를 함께 선언하라.

이 방식은 무한 재시도와 조건 누락을 줄인다. 단, 위 코드의 주석은 “10을 넘도록”이 아니라 실제로 “10 이상”이므로 프롬프트에는 자연어와 수식의 일치를 검사하라는 조건도 넣어야 한다.

### 패턴 2. 오답을 학생 오개념의 역함수로 만들고 후처리하라

실제 코드:

```js
// 대표 실수: 십의 자리에 더해 버림 (23 + 4 → 63)
w: wrongs(String(s), [a + b * 10, s + 10, s - 1, s + 1])

// 대표 실수: 받아내림 없이 각 자리에서 큰 수 - 작은 수 (52 − 27 → 35)
var flip = Math.abs(Math.floor(a / 10) - Math.floor(b / 10)) * 10
         + Math.abs((a % 10) - (b % 10));
```

빌드 프롬프트 반영:

> 오답을 임의의 근처 숫자로만 만들지 말고, 연산자 혼동·받아올림 누락·자릿값 오배치·단 한 칸 밀림처럼 해당 단원의 대표 오개념을 식으로 역산하라. 생성 후에는 정답 제거, 범위 검사, 중복 제거, 필요한 개수 보충, Fisher–Yates 셔플을 순서대로 수행하고 각 오답에 `misconceptionId`를 기록하라.

### 패턴 3. 수학 콘텐츠를 공용 엔진에서 분리한 설정 주입 구조를 써라

실제 코드:

```html
<script src="mathkit.js"></script>
<script>
window.KING = {
  id: 'low',
  run: 1.35,
  monsters: 'static',
  hazards: 'none',
  curriculum: [ /* 단원별 gen */ ]
};
</script>
<script src="engine.js"></script>
```

빌드 프롬프트 반영:

> 게임 물리·화면·입력·점수 엔진과 학년별 수학 콘텐츠를 분리하라. 새 게임 변형은 `GameConfig`와 `CurriculumUnit[]`만 교체해 만들고, 스키마 검증을 통과해야 시작되게 하라. 전역 `window` 대신 ES module export/import와 명시적 타입을 사용하라.

이 패턴은 “한 엔진 × 여러 학년/단원” 생산 라인에 직접 맞는다.

### 패턴 4. 게임 상태를 화면 ID와 함께 관찰 가능하게 설계하라

실제 코드:

```html
<span class="hud-value" id="hud-score">0</span>
<div class="hud-chip" id="hud-wave">W1</div>
<div class="hud-chip time" id="hud-time">0:00</div>
<div id="combo-meter" class="combo-meter"></div>
<div id="combo-display" class="combo-banner"></div>
...
<span class="stat-num" id="over-max-combo">0 CHAIN</span>
```

빌드 프롬프트 반영:

> 상태를 `phase, score, combo, lives, wave, elapsedMs, remainingMs, currentProblem, lastResult`의 단일 명시적 모델로 관리하라. HUD, pause, result 화면은 같은 상태의 파생 뷰여야 하며 안정적인 DOM ID 또는 테스트 셀렉터를 제공하라. 타이머는 렌더 프레임 수가 아니라 monotonic clock을 기준으로 하고 pause 시 정확히 동결하라.

뱅뱅텐킹처럼 현재값과 최종 통계(최대 연쇄, 플레이 시간)를 함께 보여주면 교사와 학생 모두 진행을 이해하기 쉽다.

### 패턴 5. 교실 입력·협동·피드백을 1급 기능으로 넣어라

실제 코드:

```html
<button ... id="tabMode2P">
  👥 2인용 협동
  <span class="btn-sub-en">2P Co-op</span>
</button>
...
<!-- Left Panel: 1P Controls (A, D, W) -->
<!-- Right Panel: 2P Controls (◀, ▶, ▲ / Space) -->
```

그리고 즉시 수학 피드백:

```html
<span>조준 확인
  <small>지금 쏘면 터지는 자리면 조준선이 초록색</small>
</span>
```

빌드 프롬프트 반영:

> 키보드·마우스·멀티터치를 모두 지원하고, 한 기기 2인 모드에서는 키 충돌이 없는 독립 키맵과 별도 닉네임/생명 상태를 제공하라. 정오 피드백은 색만 쓰지 말고 텍스트·도형·사운드를 병행하며, 힌트는 정답을 대신하지 않고 “현재 행동이 성공하는가”를 즉시 알려주게 하라. 학급 모드가 필요하면 `teams[]`, `students[]`, turn/score aggregation을 UI와 분리된 상태 모델로 추가하라.

`king_vs.html`이 404라 실제 학급대항전 패턴은 추출하지 못했다. 따라서 마지막 문장의 팀/학생 모델은 제공 코드 인용이 아니라, 결손을 보완하기 위한 공장 요구사항이다.

## 최종 권고

가장 재사용 가치가 큰 것은 트로피 탈출킹의 **교육과정 제약 생성 + 오개념 오답 + 설정 주입 엔진** 조합이고, 제품 아키텍처는 뱅뱅텐킹의 도메인 모듈 분리가 참고할 만하다. 분수팡킹과 터치터치 배수킹은 UI/게임 규칙의 계약만 학습할 수 있으며 핵심 판정 코드는 분석 대상에 없다. 학급대항전은 현재 파일이 404이므로 올바른 원본을 다시 확보하기 전에는 어떤 내부 패턴도 주장하면 안 된다.
