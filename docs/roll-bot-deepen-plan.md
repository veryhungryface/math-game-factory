# 말아봇 심층 검토 + 몰입 재설계 스펙

> 대상: `public/g/roll-bot/index.html` 현재본(3,298행)  
> 규범: `factory/prompts/30-build.md` 200~203행 — 킥은 게임 끝까지 계단식 성장, 상한 뒤 다음 층위 제공, 무이벤트 구간 봇 측정, 20문항 반복 체감 검증  
> 범위: 분석·설계만. 이 문서는 코드 변경을 포함하지 않는다.

## 0. 결론 요약

1. Lv3+ 합체가 막히는 직접 원인은 스폰 운이 아니라 `canMerge`, 합체 후보 집계, 자비 후보 판정에 반복된 하드코딩 `level < 3`이다. 공격 스펙과 도감도 3단계만 정의되어 있어 Lv3이 명백한 종착점이다.
2. 적 공백은 웨이브 자체보다 계산 문제(`wrap`, `area`) 중 `spawnT=1.6`을 매 프레임 다시 넣고, 웨이브 시간을 멈추며, 기존 적도 8% 속도로 낮추는 로직에서 생긴다. 쉬움 웨이브 4+의 75%가 `wrap` 후보라 연속 공백이 구조적으로 잦다.
3. 문제 풀은 총 163개지만 티어 3의 32개가 모두 같은 `wrap` 템플릿이고, 쉬움 후반은 이를 75% 가중한다. 현재 방지 규칙은 “같은 kind 3연속”만 막으므로 20문항 안의 누적 반복은 막지 못한다.

재설계의 중심은 **정상 진화 Lv1~Lv5 + Lv5×Lv5 각성체**다. 크기만 키우지 않고 실루엣·장식·표정·투사체·합체 연출을 단계마다 바꾸며, 웨이브별 진화 보정으로 한 런에서도 Lv4~5가 보이게 한다.

계산 중에는 피해 압박을 계속 멈추되 “안전 대기선에 먼지가 모이는 연출”을 발생시킨다. 계산 종료 뒤 대기열을 간격을 두고 투입하여 긴장–이완은 유지하고, 의미 있는 화면 이벤트의 최대 공백을 2.2초 이하로 제한한다.

### 1.2 왜 Lv3부터 합체가 안 되는가

직접 원인은 **상한**이며, 스폰 부족이나 드래그 판정 문제가 아니다.

- `canMerge(a,b)`가 같은 종류·같은 레벨이어도 `a.level < 3`일 때만 참을 반환한다(`1680~1682`). 따라서 Lv3 두 개를 정확히 포개도 입력 경로 `2983~2984`가 합체를 호출하지 않는다.
- 합체 가능 쌍 탐색도 Lv3을 선제 제외한다(`1693~1698`). 합체 글로우와 힌트가 이 결과를 쓰므로 Lv3 쌍은 시각적으로도 후보가 아니다(`2333~2335`).
- 자비 스폰용 집계는 `level >= 3`을 제외한다(`1683~1689`), `wouldMergeWith`도 Lv3 이상을 거부한다(`1707~1713`). 따라서 자비 시스템 역시 Lv3 쌍을 만들 의도가 없다.
- 합체 실행은 레벨을 단순히 1 올린다(`1781~1790`). 그러나 공격 데이터 배열은 각 종류마다 3칸뿐이고(`1367~1370`), 발사 시 `level-1`로 배열을 조회한다(`2092~2104`). 상한 조건만 지우면 Lv4부터 `dmg`, `cd`가 `undefined`가 되어 전투가 깨진다.
- 결과 도감도 각 타입 Lv1~3만 만든다(`2200~2205`). `dex`는 런 시작 때 초기화된다(`2161`); 현재 도감은 장기 수집이 아니라 그 판의 체크리스트다.

따라서 구현 시 한 곳의 숫자만 바꾸면 안 된다. `MAX_NORMAL_LEVEL`, 합체 판정, 후보 집계, 공격 스펙, 렌더, 도감, 테스트 픽스처를 한 계약으로 올려야 한다.

### 1.3 현재 레벨별 실제 시각 차이

| 레벨 | 크기 | 장식/실루엣 | 표정 | 공격 연출 | 합체 순간 |
|---|---|---|---|---|---|
| Lv1 | 반지름 계수 0.87 | 종류별 기본 입체도형 | 동일 얼굴 | 종류별 기본 탄환 | 공통 연출 |
| Lv2 | 0.96 | Lv1과 동일 | 동일 얼굴 | 탄 피해·쿨다운만 상승 | 공통 연출의 세기만 레벨 비례 |
| Lv3 | 1.05 | Lv1과 동일 | 동일 얼굴 | 탄 피해·쿨다운·일부 크기/관통만 상승 | 종착점, 다음 합체 불가 |

근거: 크기는 `0.78 + level*0.09`뿐이며(`2323`), 본체는 같은 `drawSolid`, 얼굴은 같은 `drawFace`를 사용한다(`2347~2354`). 공격 종류는 타입에 고정되고(`1367~1370`), 레벨은 수치 및 탄 크기/관통 정도만 바꾼다(`2095~2104`). 합체는 공통 사운드·파티클·칭찬이며 세기만 `1.15 + level*0.28`이다(`1784~1789`). 교사의 “합친 로봇이 더 멋지게”라는 기대를 충족하기에는 숫자 배지와 약 9% 크기 증가밖에 없다.

### 1.4 현재 교착 방지 3겹과 보존해야 할 계약

현 구조의 장점은 그대로 보존한다.

1. **주문 보정:** 빈 칸이 2개 이하일 때 합체를 풀 종류를 문제 `target`으로 선호하고, 1개 이하이면 강제한다(`861~868`).
2. **보상 보정:** 빈 칸 1개 이하이면 실제 생성 로봇의 종류·레벨을 자비 후보로 덮어쓴다(`1764~1776`). 빈 칸 2개일 때는 종류만 맞추고 Lv1을 준다.
3. **막힘 탈출:** 선반이 꽉 차고 합체 쌍이 없으면 최저 레벨 출고를 안내한다(`1703~1705`, `1801~1831`, `1862~1868`, `2365~2391`). 이미 꽉 찬 상태에서 정답 보상이 오면 손해 대신 전체 공격을 한다(`1765~1766`, `1793~1799`).

재설계 원칙은 “자비 로직이 **정상 Lv1~5만** 합체 후보로 보고, 각성체는 완성품으로 보며, 각성체 때문에 선반이 막히면 기존 출고가 항상 열리는 것”이다.

## 2. 합체 킥 증폭 설계

### 2.1 상태 계약

```text
MAX_NORMAL_LEVEL = 5
canMerge(a, b) = sameType && sameLevel && !a.awakened && !b.awakened

Lv1 + Lv1 -> Lv2
Lv2 + Lv2 -> Lv3
Lv3 + Lv3 -> Lv4
Lv4 + Lv4 -> Lv5
Lv5 + Lv5 -> Lv5 각성체(awakened=true, formId는 타입별 1개)
각성체 + 무엇이든 -> 합체 불가, 출고 가능
```

- `level`은 1~5 정수로 유지하고 각성 여부를 별도 불리언으로 둔다. `level=6`처럼 섞으면 배열 인덱스, 도감 표시, 자비 판단에서 다시 상한 오류가 나기 쉽다.
- `dexKey`는 `type:level:normal|awakened`처럼 충돌 없는 키로 바꾼다. 기존 `t+l` 형식(`1667`)은 현재는 우연히 안전하지만 확장성이 약하다.
- 모든 레벨 상수 비교는 한 곳의 `isMergeableStage(robot)`를 통하도록 한다. `3`을 여러 함수에 반복하지 않는다.
- 각성체는 자비 후보와 `mergeCounts`에서 제외하되 `occupiedCount`, 출고 후보, 공격에는 포함한다.

### 2.2 레벨별 시각·전투 진화표

크기는 슬롯 겹침 때문에 보조 수단으로만 쓴다. 실루엣과 공격 문법이 한눈에 레벨을 말해야 한다.

|---|---|---|---|---|---|
| Lv1 조립체 | 기준 0.88 | 무광 본체, 볼트 2개 | 둥근 눈, 약한 좌우 흔들림 | 원기둥 단발 리벳 / 원뿔 단발 스파이크 / 구 단일 물방울 | 작은 톱니 8개가 위로 솟음 |
| Lv2 작업체 | 0.96 | 하단 컬러 링, 작은 안테나 | 눈동자가 목표를 추적 | 리벳 2연발 느낌 / 스파이크 꼬리 잔상 / 구탄 작은 스플래시 | 두 실루엣이 자석처럼 당겨지고 링 점등 |

타입별 각성 이름은 `황금 원기둥봇`, `혜성 원뿔봇`, `무지개 구봇`으로 고정한다. 새 랜덤 등급이나 가챠는 추가하지 않는다.

### 2.3 권장 전투 수치

기존 Lv1~3의 역할을 보존하면서 배열을 5칸으로 확장한다.

| 타입 | 피해량 Lv1→5 | 쿨다운 Lv1→5 | 고레벨 역할 |
|---|---|---|---|
| 원기둥 | `1, 2, 4, 6, 9` | `.60, .50, .42, .36, .32` | 빠른 단일/버스트, Lv4부터 3번째 탄 관통 |
| 원뿔 | `2, 4, 7, 10, 14` | `1.00, .85, .70, .62, .55` | 느린 고피해 관통, 관통 수는 `2,3,4,5,6` |
| 구 | `1, 2, 4, 6, 8` | `.85, .72, .60, .52, .46` | 광역·연쇄, 범위와 연쇄 대상 수로 성장 |

각성은 별도 `ultimateEvery=5`를 사용한다. 기본 탄의 수치만 크게 올려 전장을 즉시 지워 버리면 적이 사라져 다시 공백이 생기므로, 각성체 1기의 평균 DPS는 같은 타입 Lv5의 1.20~1.25배로 제한하고 “보이는 변화”를 범위·색·궤적에 둔다.

### 2.4 합체 순간 연출 타임라인

정답 연출 규범(`30-build.md:194~195`)에 맞춰 화면 흔들림을 쓰지 않는다.

| 시간 | 연출 | 구현 조건 |
|---:|---|---|
| 0~80ms | 두 로봇에 흰 외곽선, 드롭 지점 스냅 | 입력 즉시 성공을 알린다. |
| 80~220ms | 원본 둘이 중심을 한 바퀴 120° 돌며 85%로 축소 | 원본 슬롯은 즉시 비워 중복 판정을 막는다. |
| 220~360ms | 톱니·타입 문양이 위로 퍼지고 본체 실루엣이 한 단계 바뀜 | 적 이동만 35%로, 문제·입력은 막지 않는다. |
| 360~520ms | 새 장식이 차례로 장착, 밝은 상승 아르페지오 | Lv4·Lv5·각성만 단계명 도장을 띄운다. |
| 520~700ms | 오버슈트 바운스 후 정상 크기, 첫 강화탄 즉시 1발 | 보상 체감을 전투 결과로 연결한다. |

- 일반 합체는 0.52초, Lv5는 0.62초, 각성은 0.70초 이내다.
- `prefers-reduced-motion`에서는 회전을 제거하고 180ms 크로스페이드 + 장식 점등으로 줄이되 진화 정보는 유지한다.
- 긍정 연출은 상승·확산·빛만 쓴다. 흔들림은 피격에 남긴다.

### 2.5 Lv4~5 도달 가능성 보정과 자비 시스템 호환

5칸 선반, 3타입, 8웨이브에서 순수 Lv1 이진 합체만으로 Lv5 하나를 만들려면 같은 타입 Lv1 16개가 필요하다. 현 문제 타깃 분산 상태에서는 상한만 늘려도 대부분 Lv3에서 끝나므로 다음 보정을 추가한다.

1. `mergeDebt`를 “마지막 합체 뒤 정답 로봇 수”로 센다. 4개가 쌓였거나 웨이브가 끝났는데 합체 후보가 없으면, 다음 보상 1회를 `twinCore`로 예약한다.
2. `twinCore`는 선반의 **가장 높은 미짝 정상체**와 같은 타입·같은 레벨을 준다. 단, 현재 웨이브 해금 상한을 넘지 않는다: W1~2 Lv1, W3~4 Lv2, W5~6 Lv3, W7~8 Lv4.
3. 이 예약은 즉시 선반에 꽂지 않고 다음 정답 보상에 적용한다. 빈 칸이 없으면 기존 전체 공격을 유지하고 예약은 소비하지 않는다. 선반 교착 출고가 일어난 다음 정답에 다시 시도한다.
4. 기존 1겹 주문 보정은 `twinCore.type`을 선호한다. 2겹 보상 보정은 `twinCore.level`까지 정확히 적용한다. 3겹 출고/전체 공격은 그대로 최종 안전망이다.
5. 자비 우선순위는 `교착 탈출 > 예약 twinCore > 일반 미짝 보정 > 랜덤 Lv1`이다. 각성체는 모든 미짝 계산에서 제외한다.

목표 분포는 정상 정답률 80%·평균 2.5초/문제 봇 500런 기준으로 `Lv3 도달 ≥95%`, `Lv4 ≥80%`, `Lv5 ≥35%`, `각성 5~15%`다. 각성은 희귀하되 관찰 불가능해서는 안 된다. 수치가 낮으면 `mergeDebt` 임계값만 4→3으로 낮추고 전투 수치를 건드리지 않는다.

## 3. 페이싱 감사와 새 곡선

### 3.1 현재 무이벤트 구간의 확정 원인

일반 문제 중 적 생성 간격은 다음 식이다(`2792~2796`).

```text
interval = max(0.55, 1.9 - 0.17*(wave-1)) * random(0.85, 1.20)
```

| 웨이브 | 현재 생성 간격 범위(초) | 평균(초, 근사) |
|---:|---:|---:|
| 1 | 1.62~2.28 | 1.95 |
| 2 | 1.47~2.08 | 1.77 |
| 3 | 1.33~1.87 | 1.60 |
| 4 | 1.18~1.67 | 1.42 |
| 5 | 1.04~1.46 | 1.25 |
| 6 | 0.89~1.26 | 1.08 |
| 7 | 0.75~1.06 | 0.90 |
| 8 | 0.60~0.85 | 0.73 |

이 식 자체는 공백의 주원인이 아니다. 문제는 `wrap` 또는 `area`가 뜨면:

- `spawnT=1.6`을 매 프레임 덮어써 새 적이 절대 생성되지 않는다(`2782~2789`).
- `waveT` 증가와 다음 웨이브 판정도 `else` 안에 있어 멈춘다(`2787~2796`). 계산이 오래 걸리면 12초 웨이브가 벽시계 기준으로 무한히 늘어난다.
- 기존 적은 정상의 8% 속도로만 움직인다(`2798`). 로봇은 계속 발사하므로 남은 적을 정리한 뒤에는 화면에 위협이 완전히 사라진다(`2799~2805`).
- 쉬움 W4+ 티어 구성은 `[3,3,3,2]`이고(`793~800`), 티어 3의 32개가 전부 `wrap`이다. 즉 후반 주문의 기대 75%가 이 정지 경로다. 연속 두 번의 `wrap`은 현재 로테이션에서도 허용된다(`838~857`).

따라서 교사 피드백의 “적들이 안 나오는 구간”은 의도한 이완이 과도하게 구현된 결과다.

### 3.2 새 페이싱 상태기계

압박 시간과 시각 이벤트 시간을 분리한다.

```text
combatClock: 비계산 문제에서만 1.0배, 계산 문제에서 0.15배
eventClock:  항상 1.0배
spawnLane:   active | staging | release
```

- **active:** 기존처럼 실제 적을 생성하고 전진시킨다.
- **staging(계산 중):** 2.0초마다 최대 2기까지 “안전 대기선”에 먼지 실루엣을 등장시킨다. 대기 적은 작업대로 내려오지 않고, 공격 판정도 없으며, 컨베이어에서 꿈틀거리고 숫자 `대기 1/2`를 보인다. 기존 적 이동은 8%가 아니라 20%로 하되 안전선 아래로는 내려오지 못하게 clamp한다. 계산 압박은 여전히 없다.
- **release(계산 종료):** 대기 적을 0.45초 간격으로 하나씩 실제 레인에 풀어 준다. 동시에 새 랜덤 스폰을 하지 않아 순간 폭증을 막는다. 대기열이 비면 active로 돌아간다.
- 계산 문제가 새로 연속 등장해도 대기열의 작은 움직임·코어 점등·로봇 조준이 계속되어 “아무것도 없음”이 되지 않는다.

### 3.3 12초 웨이브 내부 긴장–이완 곡선

| 전투 시각 | 구간 | 목표 감정 | 생성 규칙 | 보장 이벤트 |
|---:|---|---|---|---|
| 0.0~1.2초 | 예고 | 숨 고르기 + 대비 | 새 적 1기를 0.7초에 텔레그래프, 1.2초에 진입 | 웨이브 번호 + 다음 적 아이콘 |
| 1.2~5.0초 | 상승 | 리듬 형성 | 표의 현 웨이브 평균보다 10% 느리게 | 최대 스폰 공백 2.1초 |
| 5.0~9.5초 | 압박 | 합체 효용 확인 | 현 평균, W4+는 `big/fast` 교대 쿼터 | 4초마다 특수 적 1기 이하 |
| 9.5~11.0초 | 해소 | 성장 체감 | 새 스폰 30% 감소, 남은 적 정리 | 마지막 적에 금빛 테두리 |
| 11.0~12.0초 | 마침표 | 다음 판 기대 | 새 스폰 없음, 남은 적은 보너스 표적 | “다음 웨이브: 빠른 먼지” 예고 카드 |

계산 중에는 이 표의 `combatClock`이 15%로만 흐르므로 난이도 규범을 지킨다. 다만 `eventClock`으로 staging 이벤트가 계속 발생한다. 웨이브 전환 시 기존 `spawnT`를 물려받지 말고 첫 텔레그래프를 0.7초로 명시적으로 초기화한다.

### 3.4 페이싱 안전 한도

- 화면에 `enemySpawn`, `stagingSpawn`, `shotHit`, `enemyKill`, `merge`, `waveCue`, `problemResolve` 중 하나도 없는 **의미 이벤트 공백은 최대 2.2초**다.
- 계산 중 피해 가능 이벤트 공백은 측정 대상이 아니며, 대신 `stagingSpawn|stagingPulse` 공백을 최대 2.0초로 측정한다.
- 실제 적 동시 수는 모바일에서 8기, 대기열은 2기로 제한한다. 초과 스폰은 지연하지 말고 다음 슬롯에 재예약하여 프레임 부하를 평탄화한다.
- 각성 궁극기로 모든 적이 사라졌을 때는 다음 active 스폰을 0.8초로 당긴다. 강한 보상이 오히려 공백을 만들지 않게 한다.

## 4. 문제 반복 감사와 확장 스펙

### 4.1 현재 풀의 정확한 크기와 유형 분포

현재 생성기 함수를 동일 JS 문맥에서 실행해 집계한 값이다. 풀 구성 근거는 `394~778`, 합성은 `781~788`이다.

| 티어 | 현재 개수 | kind별 구성 | 주 사용 구간 |
|---:|---:|---|---|
| 1 | 16 | `spin 6`, `parts 10` | W1 중심, W2~3 일부 |
| 2 | 51 | `net 4`, `read 19`, `radia 11`, `scale 5`, `compare 6`, `views 6` | W2~3 중심, 쉬움 후반 25% |
| 3 | 32 | `wrap 32` | 쉬움 W4+ 75%, 어려움 W4+ 75% |
| 4 | 64 | `wrap 46`, `area 18` | 어려움 W4+ 25% |
| 합계 | **163** | `wrap 78`이 전체의 47.9% | 명목 크기에 비해 후반 실효 유형이 좁음 |

중요한 세부 원인:

- 티어 3은 친숙한 반지름 4개 × 높이 4개 × 반지름/지름 표기 2개로 32개를 만들지만(`683~692`), 질문 문장과 풀이 행동은 전부 “맞는 옆면 띠 고르기”다.
- 티어 4도 임의 반지름 `wrap` 46개 + 옆면 넓이 `area` 18개뿐이다(`694~733`). 숫자는 달라도 인지 행동은 두 가지다.
- 티어는 중복 가중 배열에서 매번 섞어 고른다(`793~800`, `841~845`). 원소 `[3,3,3,2]`가 동일 티어 백을 공유하므로 티어 3을 자주 소진한다.
- 현재 반복 차단은 최근 두 `kind`가 같을 때 다음 한 번만 같은 kind를 피한다(`838~857`). “세 번 연속”은 막지만 `wrap, wrap, read, wrap, wrap`과 같은 누적 피로는 허용한다.

### 4.2 연속 20문항 표본

기본 QA와 같은 방식으로 웨이브 1→8을 반복하고 쉬움 모드에서 20개를 뽑았다(`3101~3117`). 5개 독립 표본의 결과:

- `wrap`은 표본마다 **5, 8, 7, 7, 6회**였다. 모든 표본에서 규범의 “같은 유형 3회 이상” 기준을 넘었다.
- 가장 심한 표본은 kind 분포가 `wrap 8, parts 4, read 4, spin 2, radia 1, views 1`이었다. 10개 kind 중 실제로 6개만 보였다.
- `wrap` 2연속은 자주 발생했고, 한 표본에서는 20문항 안에 2연속 묶음이 세 번 나왔다. 현재 규칙상 예상된 결과다.
- 원뿔 높이 읽기 풀은 수치 조합이 9개여도 prompt 문자열이 동일하다(`499~511`). 5개 중 2개 표본에서 정확히 같은 prompt가 2회 나타났다. 학생은 그림 속 숫자보다 첫 문장을 먼저 보므로 반복으로 느낀다.
- 정확히 같은 `wrap` 수치 조합은 티어 백이 32개라 20문항 표본에서 재등장하지 않았지만, **같은 인지 행동과 문장 골격**이 5~8회 반복되는 것이 주된 반복 지점이다. 검증 키를 prompt 문자열만으로 잡으면 이 문제를 놓친다.

### 4.3 새 분류 키

각 문제에 아래 메타를 추가한다.

```js
{
  tier: 1..4,
  kind: 'wrap',
  variant: 'choose-net' | 'complete-formula' | 'find-error' | 'inverse-radius' | ...,
  target: 'cyl' | 'cone' | 'sph',
  paramKey: 'r=2|h=6|dia=0',
  misconceptionIds: ['diameter-as-width', 'missing-times-two']
}
```

반복 검증 키는 세 층이다.

- **행동 유형:** `tier + kind + variant`
- **문장/수치 조합:** `variant + paramKey`
- **로봇 보상:** `target`

### 4.4 풀 확장 목표

4티어 난이도 구조와 계산 부담 규칙은 유지한다.

| 티어 | 유지/추가 variant | 파라미터 풀 | 목표 문항 수 | 계산 압박 |
|---:|---|---|---:|---|
| 1 | 기존 `spin`, `parts` + `odd-one-out`(성질이 다른 설계도), `match-shadow`(입체–정면 실루엣) | 문장 변형 2종씩, 3타입 균형 | 32 이상 | 없음 |
| 2 | 기존 7종 + `sort-properties`, `true-false-reason`, `match-net-part` | 반지름/지름 수치와 그림 방향을 교차 | 84 이상 | 없음 |
| 3 | 기존 `choose-net` 외 `complete-formula`, `find-error`, `inverse-radius`, `compare-two-wraps`, 원뿔 `height-debug`, 구 `view-reason` | 친숙수 `r∈{1,2,5,10}`만, 높이 6종, 표기 2종; 타입 목표 비율 `cyl 60 : cone 18 : sph 18` | 96 이상, variant당 12 이상 | `isCalc` 문항만 staging, 풀이 타일 표시 |
| 4 | `choose-net-hard`, `area`, `find-error-hard`, `missing-dimension`, `two-step-compare` | 기존 임의 r 유지, 제약 만족 전수 풀 | 120 이상, variant당 18 이상 | 어려움 모드 전용, staging |

티어 3 신규 예:

1. `complete-formula`: `2 × 3.14 × □ = 31.4`에서 친숙한 반지름을 고른다. 오답은 `지름 대입`, `×2 누락`을 역산한다.
2. `find-error`: 완성된 띠 설계 3개 중 “2를 빠뜨린 설계”를 찾아 수리한다. 답은 오류 카드가 아니라 올바른 수정식까지 고르게 한다.
3. `inverse-radius`: 띠 가로 6.28/12.56/31.4/62.8cm에서 반지름을 찾는다. 3.14 나눗셈을 새로 요구하지 않도록 상시 공식 타일과 대응표를 보인다.
4. `compare-two-wraps`: 계산하지 않고 반지름 배 관계로 두 띠 중 더 긴 것을 고른다. 기존 티어 2 `compare`와 달리 실제 전개도 두 개의 적합 여부를 판단한다.
5. `height-debug`/`view-reason`: 원뿔의 모선–높이 오류를 고치거나 구의 방향별 모습을 근거와 짝짓는다. 후반에도 원뿔·구 보상이 끊기지 않게 하되 3.14 계산은 추가하지 않는다.

모든 신규 오답은 `정답 제거 → 범위 검사 → 중복 제거 → 부족분 보충 → 셔플` 계약(`645~658`)을 그대로 거치고 `misconceptionId`를 기계 판독 가능한 영문 키로 저장한다.

### 4.5 로테이션 규칙

단일 티어 백 대신 계층형 딜러를 사용한다.

1. 웨이브가 허용하는 티어 가중치는 유지한다. 단, `[3,3,3,2]`를 그대로 섞지 말고 장기 비율 카운터로 75:25를 맞춘다.
2. 선택된 티어 안에서 최근 6문항에 가장 적게 나온 `variant`를 우선한다. 같은 variant는 최대 2연속, 20문항 최대 4회다.
3. variant 안에서는 `paramKey` 셔플백을 사용한다. 같은 `variant+paramKey`는 백 소진 전 재사용 금지, 연속 20문항 최대 1회다.
4. 같은 prompt 골격은 20문항 최대 2회다. 원뿔 높이 읽기처럼 숫자만 달라지는 항목은 promptTemplateId를 따로 두어 센다.
5. `target`은 슬라이딩 9문항에서 각 타입이 최소 2회 나오게 하되, 선반 자비가 요청한 타입은 이 할당을 1회 선점할 수 있다. 자비 때문에 같은 variant 제한을 깨지는 않는다; 해당 타입을 지원하는 다른 variant를 찾고, 없을 때만 티어 1단계 완화한다.
6. 강제 폴백 순서는 `같은 tier·다른 variant → 인접 tier·같은 target → 허용 tier 전체`다. 현재처럼 타입 후보가 없다고 전체 풀에서 임의 항목을 뽑아 난이도 구조를 건너뛰는 폴백(`851~853`)은 제거한다.

20문항 합격 기준:

- 서로 다른 `variant+paramKey` 비율 ≥ 90%
- 같은 variant 3연속 0회, 같은 variant 20문항 5회 이상 0회
- 같은 promptTemplateId 3회 이상 0회
- 각 허용 티어가 설정 비율에서 ±10%p 이내
- 오답 선택지 중 최소 2개가 명시적 `misconceptionId` 보유

## 5. 추가 몰입 루프 1개: 영구 로봇 도감

새 통화·일일 미션·별점 세트를 더하지 않고, 이미 있는 결과 도감(`2185~2205`)을 **영구 수집 루프 하나**로 승격한다.

### 동작

- 수집 슬롯은 `3타입 × (Lv1~5 + 각성) = 18개`다.
- 새 단계가 처음 만들어지는 합체 순간 0.8초짜리 작은 “NEW 설계도!” 도장만 띄운다. 전투를 멈추는 모달은 사용하지 않는다.
- 결과 화면은 이번 런 신규 항목을 먼저 반짝이고 `도감 11/18`을 보여 준다.
- 다시하기 버튼의 보조 문구 한 줄만 `다음 발견: 원뿔봇 Lv4`처럼 바꾼다. CTA는 여전히 한 번 탭이다.
- 타이틀에는 작은 `도감 11/18` 배지만 둔다. 보상 수령, 중복 조각, 확률은 없다.
- 저장 키는 버전된 `rollbot.dex.v2`. 현재 런 도감과 영구 도감을 분리하여 `runDex`, `savedDex`로 관리한다.

### 왜 이 하나인가

교사가 이미 킥으로 확인한 “합치기”가 곧 수집 진척이 된다. 별도의 미니게임이나 재화 설명 없이 다음 한 판의 명확한 목표를 만들며, Lv4~5와 각성체에 들어간 제작 비용도 반복 플레이 가치로 회수한다.

## 6. 구현 순서

### P0 — 상태·전투 계약 확장

1. `MAX_NORMAL_LEVEL=5`, `isMergeableStage`, 각성 상태, 새 `dexKey`를 추가한다.
2. 합체 관련 네 하드코딩(`1681`, `1687`, `1696`, `1708`)을 공통 함수로 교체한다.
3. 5단계 `ROBOT_SPEC`, 타입별 고레벨 탄 행동, 각성 5번째 공격을 구현한다.
4. Lv5×Lv5 각성, 각성체 출고, 각성체가 자비 후보에서 제외되는 단위 테스트를 먼저 통과시킨다.

### P1 — 교착 방지와 도달 보정

1. 기존 주문 보정·보상 보정·출고/전체 공격 3겹을 새 상한에 맞춘다.
2. `mergeDebt`와 예약 `twinCore`를 추가한다.
3. 만석, 각성체 포함 만석, Lv4 미짝 포함 만석, 정답 보상 도착의 상태 전이를 전부 테스트한다.

### P2 — 시각 진화와 합체 킥

1. 크기 배열과 레벨별 공통 장식 레이어를 만든다.
2. 타입별 Lv3~5 공격 시그니처를 추가한다.
3. 일반/Lv5/각성 합체 타임라인, 사운드, reduced-motion 경로를 구현한다.
4. 390×844에서 5칸 로봇의 장식·글로우가 인접 슬롯과 겹쳐 합체 대상을 가리지 않는지 스냅샷으로 확인한다.

### P3 — 페이싱 상태기계

1. `combatClock`과 `eventClock`, staging 최대 2기, release 큐를 분리한다.
2. 웨이브 5구간 곡선과 전환 초기 스폰을 적용한다.
3. 이벤트 타임스탬프 로그와 전체 런 시뮬레이터를 QA 훅에 추가한다.

### P4 — 문제 풀과 딜러

1. `variant`, `paramKey`, `promptTemplateId`, `misconceptionIds` 스키마를 기존 문제부터 붙인다.
2. 티어 3을 먼저 96개/5 variant 이상으로 확장한다. 그다음 티어 1·2·4 목표량을 채운다.
3. 계층형 딜러와 target 쿼터/자비 폴백을 구현한다.
4. 쉬움·어려움, 고정 웨이브별 20/200문항 감사 훅을 만든다.

### P5 — 영구 도감과 결과 CTA

1. `runDex`/`savedDex` 분리와 v2 저장 마이그레이션을 구현한다.
2. NEW 도장, 18칸 결과 도감, 다음 발견 보조 문구를 연결한다.
3. 저장 불가 환경에서도 런이 정상 동작하고 결과 화면이 깨지지 않게 한다.

## 7. 검증 기준과 봇 측정 항목

### 7.1 기능·교착

| 측정 | 합격 기준 |
|---|---|
| 동일 타입·동일 레벨 합체 | Lv1~4는 다음 레벨, Lv5는 각성체가 된다. 다른 타입/레벨은 100% 거부한다. |
| 각성 종결 | 각성체끼리도 합체되지 않고 출고는 가능하다. |
| 스펙 유효성 | 모든 타입×Lv1~5에서 `dmg`, `cd`, 탄 속성은 유한수이며 `NaN/undefined` 0건이다. |
| 자비 near-full | 빈 칸 1개, 미짝 정상체가 있는 1,000표본에서 다음 보상이 합체 가능할 비율 100%다. |
| 만석 탈출 | 임의 선반 상태 10,000개에서 `합체 가능 || 출고 가능 || 정답 overdrive 가능` 중 하나가 항상 참이다. |
| 예약 보상 안전 | 만석에서 `twinCore`가 유실되지 않고 전체 공격 후 출고/빈칸 생성 다음 정답까지 유지된다. |

### 7.2 진화 도달성과 전투 밸런스

봇 프로필은 `정답률 80%`, 정답 반응시간 평균 2.5초(1.2~5.0초 분포), 합체 가능 시 0.8초 안에 합체, 교착 시 1.2초 안에 추천 출고로 고정한다. 쉬움 500런을 실행한다.

- Lv3 도달 ≥95%, Lv4 ≥80%, Lv5 ≥35%, 각성 5~15%.
- 어떤 타입도 최고 레벨 도달률이 다른 타입의 0.6배 미만이면 실패한다. 문제 target 분포를 조정한다.
- 각성체 보유 전후 10초의 적 처치율 상승은 15~35%다. 50%를 넘으면 공백 유발 과성능으로 판정한다.
- 프레임: 390×844, 적 8 + 대기 2 + 각성체 2기에서 p10 FPS ≥30, 긴 프레임(>50ms) 비율 <1%.

### 7.3 페이싱 봇 로그

각 이벤트에 `{runMs, combatMs, wave, phase, type}`을 기록한다.

필수 type: `enemyTelegraph`, `enemySpawn`, `stagingSpawn`, `stagingPulse`, `stagingRelease`, `shot`, `hit`, `kill`, `merge`, `awaken`, `waveCue`, `problemShown`, `problemResolve`.

전체 8웨이브 200런에서:

- 비계산 active 구간 의미 이벤트 최대 공백 p99 ≤2.2초, 단일 최댓값 ≤2.6초.
- 계산 staging 구간 시각 이벤트 최대 공백 p99 ≤2.0초.
- 피해 가능한 적이 안전선 아래로 내려온 계산 구간 사건 0건.
- 계산 종료 후 대기열 2기가 같은 프레임에 풀리는 사건 0건; release 간격 0.40~0.55초.
- 웨이브 전환 뒤 첫 텔레그래프 0.5~0.9초, 첫 실제 진입 1.0~1.4초.
- 적 없는 상태가 3초를 넘으면 이유 코드가 `think-staging` 또는 `wave-finale`여야 하고, 그동안 위 시각 이벤트가 존재해야 한다.

### 7.4 문제 생성기 봇

각 모드, 각 웨이브 고정, 전체 웨이브 순환 조합에서 각각 200세트 × 20문항을 뽑는다.

- `variant+paramKey` 고유율 ≥90%.
- 같은 variant 3연속 0건, 한 세트 5회 이상 0건.
- 같은 promptTemplateId 3회 이상 0건.
- 같은 `variant+paramKey` 2회 이상 0건.
- 정답이 choices에 정확히 1개, 선택지 문자열 중복 0건, 수학 검산 오류 0건.
- 모든 오답에 `misconceptionId`, 각 문항에 서로 다른 오개념 오답 최소 2개.
- 쉬움 계산형 비중: W1~3 0%, W4~8 45~60%. 현재 기대 75%에서 낮추되 4티어 구조는 유지한다.
- target 9문항 창에서 각 타입 최소 2회. 자비 개입 후에도 variant 제한 위반 0건.

### 7.5 시각·사용성 수동 검증

- 같은 타입 Lv1~5를 배지 글자를 가리고 나란히 둔 스크린샷에서 교사 3명 중 3명이 순서를 맞힌다.
- 390×844 실제 크기에서 눈·레벨 장식·합체 가능 글로우가 구분된다.
- 합체/Lv5/각성 스크린샷과 피격 스크린샷을 나란히 놓았을 때 긍정/부정 사건을 즉시 구분한다. 합체 경로 화면 흔들림은 0이다.
- 합체 중 드래그 연타, 웨이브 전환, 게임오버가 겹쳐도 중복 로봇·음수 슬롯·미처리 예외 0건이다.
- 영구 도감 저장/로드/구버전 키/저장 거부 네 경로에서 콘솔 오류 0건이다.

## 8. 구현 완료 정의

완료는 “Lv5가 코드에 존재”하는 상태가 아니다. 아래를 모두 만족해야 한다.

1. Lv1~5와 각성체가 실제 한 런 또는 도달성 봇에서 관찰되고, 단계별 실루엣과 공격이 다르다.
2. 기존 교착 방지 3겹이 모든 확장 레벨과 각성체에서 유지된다.
3. 계산 중 안전은 유지하면서 전체 런 이벤트 공백 측정이 기준을 통과한다.
4. 20문항 반복 기준을 `kind`가 아니라 `variant+paramKey`와 promptTemplate까지 측정해 통과한다.
5. 도감이 다음 한 판의 단일 목표를 제시하되 새 통화·가챠·강제 모달을 만들지 않는다.
