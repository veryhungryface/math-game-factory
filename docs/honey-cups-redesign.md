# 꿀몇잔(honey-cups) 심층 게임 디자인 검토와 재설계안

## 검토 범위와 결론

검토 대상은 `public/g/honey-cups/index.html` 전체, `public/g/honey-cups/meta.json`, `factory/work/chosen.json`, `factory/prompts/30-build.md`, `docs/design-bible.html`이다. 저장소의 실제 성취기준은 `[6수01-15]`(소수의 나눗셈)이며, `[6수03-03]`은 직육면체와 정육면체이므로 이 문서에서는 요청문의 “6수03-03 계열”을 **6학년 소수의 나눗셈 단원 계열**이라는 뜻으로 해석한다.

현재 게임은 수학적 결과를 시각화하는 장난감으로는 명료하지만, 플레이어가 그 결과를 만들어 내는 게임은 아니다. 꿀의 총량과 잔 용량이 정해진 순간 밀봉 잔 수와 나머지가 이미 결정되고, 입력은 그 계산을 바꾸거나 실패시킬 수 없으므로 “끝까지 홀드한 뒤 완료 버튼”이 지배 전략이다.

## 1. 원인 진단: 붓기 → 채움 → 판정 해부

### 1.1 실제 상태 흐름

1. `startRound()`가 통의 꿀을 `R.N`, 열린 잔을 0으로 초기화한다(`index.html:1391`). 포함제 라운드에서 `R.N = ka × gm`, 잔 용량은 `R.C = kb × gm`이므로 시작부터 `R.N = qR.C + r×gm` 관계가 고정된다.
2. 포인터를 누르면 `tiltFrom(0)`이 목표 기울기를 약 0.46으로 만들고, 좌우 드래그는 기울기와 배출 **속도만** 바꾼다(`index.html:1631–1646`). 배출 방향, 잔 선택, 목표량에는 영향을 주지 않는다.
3. `update()`는 기울기가 0.30을 넘는 동안 통에서 알갱이를 하나씩 빼 `emitGrain()`으로 보낸다(`index.html:1218`, `1304`). 홀드를 유지하면 유일한 종료 조건은 `S.tank === 0`이다.
4. 알갱이가 착지하면 `S.open++`가 되고, `S.open >= R.C`인 즉시 `sealCup()`이 호출된다(`index.html:1322`). `sealCup()`은 정확히 `R.C`만 빼고 초과분을 열린 다음 잔에 그대로 이월한다(`index.html:1335`). 즉 잔은 플레이어가 멈춰서 밀봉하는 것이 아니라 자동으로 밀봉된다.
5. `다 담았어`는 `restGrains() = 통 + 열린 잔 + 공중 알갱이`가 한 잔 용량보다 작은지만 검사한다(`index.html:673`, `1424`). `rest >= R.C`이면 조기 완료로 오답, `rest < R.C`이면 성공이다.
6. 등분제 라운드는 통이 빌 때까지 라운드로빈으로 자동 분배한 뒤 자동 마감된다(`index.html:1297`, `1445`). 플레이어는 분배 비율에도 완료 시점에도 개입하지 않는다.

### 1.2 왜 “무뇌 홀드”가 최적 전략인가

- **자동 멈춤은 없지만 자동 밀봉이 있다.** 통은 0에서만 멈추고, 잔은 용량에 도달할 때마다 자동으로 닫혀 다음 잔으로 넘어간다. 따라서 플레이어가 잔의 정확한 높이에서 손을 뗄 필요가 없다.
- **오버플로와 손실이 없다.** 잔을 넘긴 알갱이는 쏟아지거나 실패하지 않고 `S.open -= R.C`로 다음 잔에 보존된다. 기획서에는 “남은 꿀이 한 잔보다 적은데 더 기울이면 넘친다”고 되어 있지만 실제 코드에는 넘침 상태, 테이블 웅덩이, 손실 판정이 모두 없다.
- **끝까지 붓는 것이 보상상 더 좋다.** 성공 조건은 남은 총량이 `R.C` 미만인 것이며, `cleanStamp`는 통이 0일 때 주어진다. 따라서 나머지까지 열린 잔에 전부 부어 통을 비우는 전략이 “한 방울도 안 남김” 보너스까지 얻는다.
- **성공 시 `exactStamp`는 사실상 항진명제다.** 총량 보존식 `N = sealedCount×C + rest`에서 `rest < C`가 성립하면 `sealedCount = floor(N/C) = R.cupCount`가 자동으로 성립한다. 성공 판정을 통과한 뒤 다시 `sealedCount === R.cupCount`를 검사하는 것은 별도의 정밀 플레이를 측정하지 않는다.
- **판정이 관대한 것이 아니라 판단을 요구하지 않는다.** 남은 꿀 배지와 “한 잔” 선을 실시간으로 모두 보여 주고(`index.html:1192`), 일찍 누르면 다시 계속할 수 있다. 반대로 늦게 부어도 실패가 없으므로 유일한 합리적 선택은 통이 빌 때까지 누르는 것이다.
- **완료 버튼은 상태 전환 버튼에 가깝다.** 포함제에서는 통이 빈 뒤 퀴즈로 넘어가기 위해 한 번 더 눌러야 하고, 등분제에서는 같은 조건에서 자동 종료된다. 교사 의견처럼 수학적 결정을 확정하는 기능이 아니라 불필요한 확인 탭으로 남는다.

결정적으로 현재 결과는 입력 궤적과 무관하게 항상 `sealedCount = floor(A/B)`, `open = A mod B`로 수렴한다. 드래그 강도는 기다리는 시간만 바꾸며, 실력·계산·추정은 결과에 영향을 주지 않는다.

### 1.3 기획서와 구현의 핵심 차이

| 기획서 약속 | 실제 구현 | 게임성 영향 |
|---|---|---|
| 마지막 가능한 잔을 넘기면 꿀이 넘침 | 넘침·손실·과충전 판정 없음 | 늦게 멈추는 위험이 사라짐 |
| 등분 잔 높이에 소수점 핀 드래그 | 통이 빌 때까지 자동 균등 분배 후 3지선다 | 몫의 소수점 위치가 조작이 아님 |
| 원래 눈금과 ×10 눈금의 연결 이동 | 구현 없음 | 두 수의 소수점을 함께 옮기는 원리가 보이지 않음 |
| 가끔 “왜” 보기, 플레이 중 문제창 없음 | 모든 7라운드 뒤 3지선다 | 핵심 수학이 플레이 뒤 퀴즈로 분리됨 |
| 정확 배송·넘침 없는 수동 판단 | 성공 조건이 곧 정확 배송 도장 | 도장이 숙련도를 측정하지 못함 |

## 2. 문제 다양성 감사

### 2.1 생성기 유형과 실제 노출

생성기는 무작위 재시도가 아니라 제약 만족 풀을 전수 생성해 샘플링하고, 스케일 정수로 계산한다. 이 점은 정확성과 재현성 면에서 좋다. 실제 풀을 코드 그대로 실행해 집계한 결과는 다음과 같다.

| 밴드 | 풀 크기 | 수 범위(실제 값) | 다루는 내용 | 실제 한 런 배치 |
|---|---:|---|---|---:|
| `hook` | 14 | A=1~8, B=0.2~0.8, q=4~12 | 1보다 작은 수로 나누면 몫이 커질 수 있음 | 1회, 단 첫 문항은 3÷0.5 고정 |
| `fill0` | 103 | A=1.2~13.8, B=0.3~2.5, q=4~9 | 자연수/소수 ÷ 소수, 나머지 0, 동시 소수점 이동 | 2회 |
| `split` | 99 | A=2.2~13.8, n=2~6, 몫=1.1~4.8 | 소수 ÷ 자연수, 몫의 소수점 | 2회 |
| `fillR` | 624 | A=4.0~15.0, B=1.2~4.0, q=3~6, r=0.2~2.7 | 나머지가 있는 포함제, 나머지 소수점 | 1회 |
| `round` | 392 | A=7~60, B=3~9, 정수부 q=2~12 | 정수가 아닌 몫을 소수 1·2째 자리까지 반올림 | 1회 |

총 풀은 1,232문항이고 프롬프트도 모두 고유하므로 **문항 수 자체는 부족하지 않다.** 그러나 한 런의 스케줄은 `hook → fill0 → split → fillR → fill0 → split → round`로 고정된 7문항이며, 첫 문제까지 고정이다. 수치 표면은 다양하지만 플레이 동사는 포함제의 “홀드 후 완료”와 등분제의 “홀드 후 자동 완료” 두 가지뿐이라 체감 다양성은 낮다.

추가 편향은 다음과 같다.

- 모든 소수 입력은 소수 첫째 자리뿐이다. 소수 둘째 자리 입력이나 0을 포함한 자릿값 사례는 없다.
- `fillR`의 제수는 1.2~4.0으로 제한되어, 1보다 작은 소수로 나눈 나머지 상황은 다루지 않는다.
- `round` 392개 중 153개는 유한소수, 239개는 순환소수다. “정수로 나누어떨어지지 않음”은 보장하지만 “끝없이 이어지는 몫을 어림”만을 보장하지는 않는다.
- 반올림 결과가 절단값에서 실제로 올라가는 문제와 그대로인 문제는 각각 196개로 균형이 좋다. 다만 이것은 생성 풀의 균형이고 한 런에는 1개만 나온다.

### 2.2 오개념 역산 오답 품질

| ID | 역산 방식 | 평가 |
|---|---|---|
| M1 | 정답 q의 10배/0.1배로 “피제수만 이동/제수만 이동” 재현 | 강함. 실제 한쪽 소수점 이동 오류를 직접 수치화한다. 다만 화면의 이중 눈금 조작이 없어 사후 선택지로만 남는다. |
| M2 | 몫 m에서 소수점 제거 또는 한 자리 더 이동 | 강함. 몫의 소수점 위치 오류와 직접 대응한다. 그러나 등분 잔은 완료 뒤 모두 “가득 찬 밀봉 잔” 그림으로 바뀌어, 힌트의 “잔 높이”를 다시 볼 수 없다. |
| M3 | 원래 나머지 r을 정수처럼 표기하거나 한 자리 더 축소 | 매우 강함. `1.4 ↔ 14 ↔ 0.14`처럼 대표 오개념이 선명하고 원래 단위 잔량 배지와도 연결된다. |
| M4 | 나눗셈 대신 곱셈 또는 뺄셈 수행 | 보통. 연산 대체 오류는 설명 가능하지만 “나누면 항상 작아진다” 자체를 정밀하게 역산한 선택지는 아니며, `1.5잔` 같은 물리적으로 어색한 완성 잔 수가 생길 수 있다. |
| M5 | 목표 자리에서 자름/무조건 올림, 또는 한 자리 앞에서 반올림 | 강함. 다음 자리 확인 누락과 반올림 자리 혼동을 분리한다. |

오답은 랜덤 근삿값이 아니라 M1~M5 공식과 개별 힌트로 연결되어 있어 규범의 취지는 잘 지킨다. 다만 `makeChoices()`는 중복이 하나라도 생기면 문항을 폐기할 뿐, 규범에 적힌 “범위 검사 → 부족분 보충”은 구현하지 않는다. 더 큰 문제는 좋은 오개념 설계가 핵심 액션에 들어가지 못하고 매 라운드 뒤의 문자열 3지선다에 집중되어 있다는 점이다.

### 2.3 단원 핵심 커버리지

| 단원 핵심 | 코드 커버리지 | 판단 |
|---|---|---|
| `(소수)÷(자연수)`, `(자연수)÷(소수)`, `(소수)÷(소수)` | `split`, `hook/fill0`에 모두 존재 | **수치 범위는 충족.** 다만 계산은 자동 물리 시뮬레이션이 대신한다. |
| 몫의 소수점 위치 | `split`의 M2 3지선다 | **부분 충족.** 플레이어가 소수점을 놓거나 몫을 구성하지 않으며, 기획서의 핀 드래그도 없다. |
| 두 수의 소수점을 같은 자리만큼 옮기기 | M1 오답과 설명 문장 | **설명 수준.** 연결 눈금 연출과 조작이 없어 원리 탐구가 아니다. |
| 나머지가 있는 나눗셈 | `fillR` 624문항, 원래 단위 잔량 표시 | **비교적 강함.** 다만 나머지를 플레이어가 계산·보존하지 않고 끝까지 부어 열린 잔에 옮겨 버린다. |
| 나누어떨어지지 않는 몫 | `round`와 `fillR` | **부분 충족.** `round`는 소수 몫을 묻지만 붓기 장면은 정수 개의 밀봉 잔과 부분 잔만 만들고, 실제 소수 몫 구성은 사후 퀴즈다. |
| 반올림 | `round` 392문항, 올림/버림 균형 | **문항 생성은 강함, 메커닉은 약함.** 계산 후 반올림을 3지선다로 묻는다. |
| 어림·몫의 범위 판단 | 별도 유형 없음 | **미충족.** 정확 계산 후 반올림과, 붓기 전에 “몫은 대략 몇인지/어느 두 수 사이인지” 판단하는 어림은 다르다. |

실시간 계산 부하 규칙과의 관계도 재검토가 필요하다. 현재 붓기 액션 중에는 계산 압박이 없어 부하 위반은 아니지만, 그 대가로 계산이 액션과 완전히 분리되었다. 재설계에서는 **계산 단계에서 시간 압박을 멈추고**, 답을 정한 뒤 붓기 실행에서 정확도·타이밍을 시험해야 한다.

## 3. 재설계안 3개

### 안 1 — 주문 컵 정밀 배송: 수동 차단 + 실제 오버플로 **(추천)**

**Core loop 1/2.** 먼저 `A ÷ B`의 몫 q와 나머지 r을 계산해 배송표의 “가득 채울 잔 q개 / 통에 남길 양 r”에 직접 놓고, 계산 중에는 타이머와 붓기를 정지한다.  
**Core loop 2/2.** 붓기를 시작하면 잔은 용량에 닿아도 자동 전환되지 않으며 플레이어가 손을 떼고 `밀봉`해야 한다; q번째 잔 뒤에도 계속 붓거나 눈금을 넘기면 꿀이 테이블로 실제 유출되고, r만 통에 남긴 채 `배송 완료`하면 성공한다.

- **실패 조건:** 잔 하나라도 `C` 미만에서 밀봉, `C` 초과로 1알 이상 유출, q개보다 많거나 적은 잔 배송, 최종 통 잔량이 r과 불일치. 탐험 모드는 해당 잔을 되돌리고 오개념별 힌트를 주며, 잔치 모드만 목숨을 차감한다.
- **수학이 동사가 되는 지점:** q를 계산해야 몇 번째 잔에서 멈출지 알 수 있고, r을 계산해야 마지막에 꿀을 얼마나 남길지 알 수 있다. 몫과 나머지가 단순 사후 라벨이 아니라 밸브를 닫는 목표 상태가 된다.
- **디자인 세부:** 실시간 “정답 잔량 숫자”와 초록 한 잔 선은 제거하고, 0.1 L 단위 눈금만 남긴다. 큰 흐름/미세 흐름 두 단계 입력을 두어 계산이 맞아도 터치 정밀도 때문에 억울하게 실패하지 않게 하고, 목표 근처에서는 액션을 감속한다.
- **추천 이유:** 기존 입자, 통, 잔, 밀봉, q/r 생성 풀을 가장 많이 재사용하면서 교사 의견의 세 지점—자동 완성, 무의미한 완료 버튼, 정확히 멈추는 재미 부재—를 한 번에 고친다. 기획서가 원래 약속했던 오버플로도 복원한다.

### 안 2 — 눈금 없는 암흑 배송: 먼저 어림하고 나중에 실측

**Core loop 1/2.** 불투명한 통에 A L가 있고 B L 잔으로 대략 몇 잔이 나올지 `하한–예상–상한` 세 토큰으로 먼저 정한 뒤, 예상한 개수만큼 빈 잔을 작업대에 꺼낸다.  
**Core loop 2/2.** 붓는 동안 통 잔량과 잔 눈금을 숨기고 플레이어가 유량과 시간을 스스로 조절해 각 잔을 채우며, 완료 후 저울이 실제 부피를 공개해 예상 범위·가득 찬 잔 수·나머지를 함께 비교한다.

- **실패 조건:** 준비한 잔 수가 실제 q에서 2개 이상 벗어나 배송 공간 부족/과잉 발생, 또는 각 잔의 실측이 B 허용오차를 벗어남. 1개 차이는 실패 대신 “어림 보정” 피드백으로 처리한다.
- **수학이 동사가 되는 지점:** `B×몇 ≈ A`를 이용해 몫의 범위를 정하고, 그 어림값만큼 잔이라는 물리 자원을 배치한다. 정답 공개 뒤 `qB ≤ A < (q+1)B`와 `r=A-qB`를 실측 결과로 확인한다.
- **디자인 세부:** 초반은 12÷2.9처럼 기준 배수로 범위를 잡기 쉬운 수, 후반만 소수 둘째 자리와 반올림을 쓴다. 계산 화면에는 배수 타일을 상시 제공하고 시간 압박은 두지 않는다.

### 안 3 — 잔 창고 역산: 남김없이 담길 제수 선택

**Core loop 1/2.** “꿀 A L를 q잔에 남김없이 배송” 주문을 받고, 서로 다른 용량 B 후보 3~4개 중 맞는 잔 세트를 작업대에 놓는다.  
**Core loop 2/2.** 선택한 잔으로 실제 자동 분배를 실행하면 맞는 제수는 q잔이 동시에 정확히 차고, 잘못 고른 제수는 부족·남음·오버플로가 눈앞에 남아 잔을 교체해 다시 역산한다.

- **실패 조건:** 선택한 B에 대해 `qB ≠ A`; 부족이면 빈 공간, 초과면 통 잔량 또는 유출로 즉시 시각화한다. 1차 실패는 상태를 유지해 차이를 관찰하게 하고 2차부터 잔치 모드 페널티를 준다.
- **수학이 동사가 되는 지점:** `A ÷ B = q`를 맞히기 위해 `B = A ÷ q` 또는 `q×B=A`를 역으로 사용해 **제수 자체를 선택**한다. M1의 한쪽 소수점 이동, M2의 몫 소수점 오류를 실제 크기가 다른 유령 잔 후보로 바꿀 수 있다.
- **디자인 세부:** 정확 나눗셈뿐 아니라 “가장 적게 남는 잔”, “몫이 5와 6 사이가 되는 잔” 주문을 섞으면 비교·어림 유형으로 확장된다. 다만 같은 런에서 정밀 붓기와 혼합하지 말고 별도 스테이지로 분리한다.

## 4. 추천 구조와 난이도 진행

추천은 **안 1을 기본 루프**로 삼고, 안 3을 짧은 변주 스테이지로 넣는 구성이다. 안 2는 어림 학습에는 가장 깊지만 촉각 오차와 수학 오차를 분리하기 어려워 후속 확장으로 두는 편이 안전하다.

권장 한 런은 다음처럼 재배치한다.

1. **관계 예측:** “몫이 A보다 큰가/작은가”를 시간 제한 없이 고른다.
2. **정밀 배송:** q와 r을 배송표에 놓고 안 1로 직접 실행한다.
3. **원리 피드백:** 오답일 때만 M1~M5 유령 눈금과 차이를 보여 준다. 매번 사후 3지선다를 강제하지 않는다.
4. **변주:** 3라운드마다 안 3의 역산 주문 또는 몫 범위 어림을 넣는다.
5. **반올림 라운드:** 붓기 전에 몫의 다음 자리까지 계산 타일을 완성하고, 그 결과가 배송 가능한 잔 수/잔량 허용구간을 정하게 한다.

“다 담았어”는 삭제하거나 다음처럼 의미를 바꿔야 한다. 붓기 종료 자체는 손을 떼는 입력으로 처리하고, 버튼은 **계산한 q개의 잔과 r의 상태를 되돌릴 수 없게 제출하는 `배송 완료`**여야 한다. 제출 전에는 실측값을 숨기고, 제출 후에만 판정해야 버튼에 긴장과 책임이 생긴다.

## 5. 구현 난이도

| 안 | 상대 난이도 | 주요 변경 | 위험과 완화 |
|---|---|---|---|
| 안 1 수동 차단+오버플로 | **중 (M)** | 자동 `sealCup()` 분리, 잔별 under/over 상태, 유출 파티클과 판정, q/r 입력, 미세 유량, 테스트 훅 보강 | 프레임·터치 차이로 억울할 수 있음 → 알갱이 정수 판정, 목표 근처 감속, 탐험 모드 되돌리기 |
| 안 2 숨김+실측 어림 | **상 (L)** | 불투명 상태, 잔 사전 배치, 어림 범위 데이터, 실측 공개/리플레이, 오차 분석 UI | 운동 능력과 수학 오류가 섞임 → 넓은 허용오차, 유량 프리셋, 어림 점수와 정밀 점수 분리 |
| 안 3 제수 선택 역산 | **중하 (S~M)** | 잔 후보 UI, 역산 문제 풀과 M1/M2 기반 크기 후보, 잘못된 선택의 부족/남음 시뮬레이션 | 선택 퀴즈로만 퇴행할 수 있음 → 후보를 실제 잔 크기로 보여 주고 선택 뒤 반드시 물리 검증 |

공통 구현 원칙은 세 가지다. 첫째, 계산 단계에는 실시간 압박을 걸지 않는다. 둘째, 정답은 상승·빛·확산, 오답과 유출은 흔들림·낙하·웅덩이로 연출 어휘를 분리한다. 셋째, 정밀 판정은 화면 픽셀이 아니라 현재처럼 스케일 정수 알갱이로 유지한다.

## 최종 판단

현재 꿀몇잔의 실패 원인은 콘텐츠 수가 아니라 **행동의 결과가 입력 전에 이미 결정되고, 늦게 멈추는 비용조차 없다는 것**이다. 가장 작은 방향 전환은 기획서에 있었으나 빠진 “실제 오버플로”를 복원하는 것이고, 가장 중요한 구조 변경은 q와 r을 먼저 계산한 뒤 그 값으로 수동 차단·밀봉·최종 잔량을 만들어 내게 하는 것이다.
