헌장 — 세 가지 서약

모든 기획·구현·검수 판단의 최상위 기준. 서로 충돌하면 위에 있는 것이 이긴다.

① 수학이 동사다

게임 위에 문제창을 얹지 않는다. 게임을 잘하려면 자연스럽게 수학을 쓰게 되는 구조 — 어림 버튼이 정답 입력이 아니라 나를 다른 수로 던지는 텔레포트인 것처럼, 수학 판단이 곧 조작이어야 한다.

② 틀린 답을 가르치느니 안 만든다

품질이 형편없으면 안 만드느니만 못하다. 수학 오류 1건 = 점수 무관 즉시 폐기. 검수 80점 미만 = 게시하지 않는다. 실제로 6회차 「찰랑 스핀」은 77점으로 폐기됐다.

③ 억울하게 지면 안 된다

실수 하나가 몇 수 뒤에 몰아서 게임오버로 터지는 구조는 금지. 목숨 3개 이상, 실수는 즉시 눈에 보이는 작은 손해로 끝난다. 이 조항은 총점 80점을 넘어도 단독으로 게시를 막는 게이트다.

1단원

교육 — 틀린 것을 가르치지 않는다

근거: 교육부 고시 제2022-33호 원문 PDF · 검정 교과서 9종 실물 차례 · 실제 폐기 사고 1건

1.1교육과정 정합 — 단원 번호가 아니라 성취기준 코드에 묶는다

  • 2022 개정 5~6학년군 성취기준 45개 전체를 고시 원문에서 확보. 코드를 지어내면 QA가 자동 탈락시킨다.
  • 초등 3~6 수학은 검정 교과서(9종)라 단원 순서가 출판사마다 다르다 — 6-2의 2·3단원(공간과 입체↔소수의 나눗셈)은 출판사별로 반대. 그래서 게임은 성취기준 코드에 매핑한다.
  • 고시의 "적용 시 고려 사항"에서 뽑은 문항 생성 제약 18조가 모든 기획·빌드·검산 프롬프트에 자동 주입된다 — 원주율은 3.14만, 각뿔·원뿔 전개도는 안 다룸, 가능성은 0·½·1 수준의 수 표현 등.

1.2문제 생성 5원칙

  • ① 자릿값부터 역생성. "받아올림이 반드시 있는 덧셈"은 일의 자리 ao=2..9, bo=(10−ao)..9를 먼저 뽑아 조건을 구조적으로 보장한다. 만들고 나서 검사·재시도하는 방식은 편향과 무한루프를 낳는다. (킹수학 실코드에서 검증)
  • ② 제약 만족 풀에서 샘플링. 단원 제약을 만족하는 후보를 전수 생성해 풀을 만들고 셔플한다.
  • ③ 오답은 오개념의 역함수. 오답 4개 중 최소 2개는 실제 학생 실수(자릿값 오배치·받아올림 누락·분모끼리 더함·역수 혼동)를 역산한 값 + 코드에 misconceptionId 기록. 잘 만든 상용 게임 전부가 이렇게 한다 — 랜덤 오답은 하수다.
  • ④ 후처리 파이프라인 고정: 정답 제거 → 범위 검사 → 중복 제거 → 부족분 보충 → 셔플.
  • ⑤ 부동소수점 금지. 분수는 {n,d} 정수쌍 + 기약 정규화, 소수는 n/10^s 정수 스케일링. 0.1+0.2 ≠ 0.3.

1.3한국 교과서 표현 함정 사전

표현뜻예 (225, 반올림)
반올림하여 십의 자리까지결과가 십의 자리까지 정확230
십의 자리에서 반올림십의 자리 숫자를 보고 판단 → 결과는 백의 자리까지200

이 한 글자 차이로 1회차 게임이 수학 0점을 받고 폐기 직전까지 갔다. 구조적 해법: 어림 문제는 roundingMode / decisionPlace / retainedPlace / promptConvention 4필드 모델로 만들어 문장과 정답이 같은 데이터에서 나오게 한다. 그 외 — 이상/이하는 경계 포함·초과/미만은 제외(선택지에 경계값을 넣어 시험), 「대략 몇백?」은 문맥(자르기·담기)에 따라 버림/올림이 강제되니 상황을 문장에 명시.

1.4교차 검증 — 같은 모델은 같은 맹점을 공유한다

게임을 만든 모델(Claude)과 다른 회사 모델(GPT-5.6-sol)이 문제 표본을 전수 손검산한다. 오류 1건이면 무조건 fail. 검산관은 재미·비주얼을 보지 않는다 — 단일 임무가 정확도를 만든다.

2단원

재미 — 수학이 동사가 되게 한다

근거: 실사용자 플레이 피드백 6건 · vibe 22종 · 킹수학 400종 실분석

2.1실사용자가 직접 가르쳐준 4계명 (젤리 게이트 사건)

  • 선택지 2개짜리 러너 금지. 최소 3~4개를 화면에 고르게 분산. 왕복 두 칸은 게임이 아니다.
  • 캐릭터는 게임 화면 크기에서 귀여워야 한다. 원본 에셋이 예뻐도 32px로 뭉개지면 무의미 — 화면 폭 12~15% 이상으로 렌더링.
  • 숫자·분수는 화면 폭 5% 이상 + 고대비 카드. 분수는 KaTeX 실조판으로. 어두운 배경에 흘려 쓴 작은 숫자는 실격.
  • 실수 관용 — 헌장 ③. 지연된 누적 실패 구조는 그 자체로 게시 불가.

2.2검증된 메커닉 패턴 — 465종에서 살아남은 것들

패턴내용어느 단원에
절차의 스텝화필산·장제법은 최종답 대신 자리별 스텝 인터랙션 — 세로셈판이 실시간으로 채워진다곱셈·나눗셈 계열
실측 판정각도기·삼각자를 드래그로 직접 대보고 벡터+허용오차(±4°)로 판정. 4지선다보다 조작적도형·각도
구성형 도구성취기준 동사가 "그린다/만든다"면 채점형 퀴즈가 아니라 직접 그리기. 판정은 불변량→연결성→접기 시뮬레이션→충돌 4단계전개도·그래프
채점자 역전"풀어라" 대신 "이 답을 채점해라" — 같은 연산이 다른 인지 활동이 된다. 오개념 라이브러리가 품질을 좌우 = 우리 강점과 정합연산 전반
공간 인터랙션"정답으로 이동해서 닿는" 조작이 버튼 선택보다 몰입 — 팩맨식 이동, 블록 캐기전 단원
이중 상태 확률이론적 가능성 vs 실험 빈도 누적을 둘 다 — [예측→시행→비교] 루프. 킹수학조차 없는 구조라 앞설 수 있는 지점가능성 (재도전 필수)
이유 설명 트랙정답과 별개로 "왜 맞는가" 선택 문항에 추가 별 — 발견/정답/설명 3종 보상도형·개념

2.3온보딩과 리텐션

  • 30초 안에 첫 재미. 온보딩은 핵심 규칙 2~4개 체크리스트 + 마스코트 1인칭 호소 한 줄("얘들아, 도와줘!"). 첫 성공까지 지속되는 힌트 배너.
  • 정답 후 보상에 마이너스 금지 — 정답 맞히고 벌 받는 경험은 동기를 파괴한다(보상 풀에서 코드로 원천 차단).
  • 난이도 선택 = 관용도 선택을 옵션으로. 형성평가형(오답=힌트→정답 공개) ↔ 아케이드형(목숨 3+즉시 피드백) 중 단원 성격에 맞게 고르고 이유를 기획서에 남긴다.
  • 로컬 리텐션: 킹수학의 최강 무기는 학급 주간 랭킹(시즌 스포츠)이지만 우리는 서버가 없다 — localStorage로 최고기록 갱신 연출·일일 미션·스탬프 컬렉션.
3단원

아름다움 — 닌텐도를 기준선으로

근거: 실사용자 요청("첫화면이 멋져야, 닌텐도처럼") · 5종 전체 리디자인 실전

3.1첫인상 — 타이틀 화면은 필수다

게임을 열면 닌텐도 게임을 켠 것 같아야 한다: 세로형 키 아트(1024×1536, GPT 이미지 생성 — 주인공 역동 포즈 + 상단 ⅓ 로고 여백) 풀블리드 + 로고 연출(그냥 텍스트 금지 — 다중 그림자·기울임·게임 주제와 맞는 형태: 대칭 게임은 좌우 대칭 로고, 슬라이스 게임은 베인 자국 로고) + 펄스 시작 버튼 + 느린 줌 모션 + 학년·단원 뱃지. 이미지 로드 실패 시 코드 그라디언트 폴백까지.

3.2게임 필(Juice) — "화려하게"는 체크가 안 되니 기법으로 센다

9기법 중 최소 6개를 실제 코드로 구현해야 검수를 통과한다: hit-stop · squash&stretch · overshoot 이징 · 단계별 화면 흔들림 · 콤보 비례 파티클 · 컬러 플래시 · 잔상 트레일 · 상시 배경 모션 · 사운드-화면 동기. 점수는 카운트업, 버튼은 face/edge 2톤 입체+눌림, 게임오버 화면도 타이틀급으로.

3.3팔레트 다양성 — 전부 네온이면 전부 똑같아 보인다

실제 사고: 초기 4개 게임의 배경색이 전부 #07로 시작(어두운 남색+네온 시안/마젠타). 원인은 프롬프트 예시 자체가 네온이었던 것. 지금은 최근 6개 게임의 무드가 자동 회피 목록으로 기획에 주입되고, 대낮 놀이공원·노을 캔디·자연 숲·파스텔 동화·모노크롬+포인트·레트로 아케이드·수채화 종이 7계열에서 단원 내용과 맞는 것을 고른다. 무드 선택의 이유를 한 줄로 남겨야 한다.

3.4아트 디렉션 축 — 게임마다 화풍을 달리한다

실제 사고: 2026-08-29 전수 감사에서 게시작 24작 전부가 같은 화면이었다 — 상단 어두운 알약 칩 HUD → 크림색 문제 카드 → AI 회화 배경 → 하단 금색 광택 CTA. 최근 9작은 색을 뺀 CSS 선언의 47~78%가 문자 그대로 동일했다. 원인은 취향이 아니라 파이프라인이었다: 20-art.md의 고정 스타일 문구가 모든 에셋에 붙었고, 30-build.md의 "게임 화면 폴리시"가 알약 칩 문법을 문자로 지시했으며, "배경이 단색이 아니다" 체크가 미니멀 배경을 금지했다. 셋 다 폐기됐다.

이제 게임마다 아트 디렉션 축을 달리한다. 기획이 art_direction.visual_axis로 축을 확정하고(직전 5작과 같은 축 금지, 축당 정원 3작), 아트는 그 축의 스타일 스탠자만 이미지 프롬프트에 붙이고, 빌드는 축의 부품 문법·배경 정책·정답 연출 개성을 따르고, 검수는 비주얼 20점 중 8점을 "분화"에 배정해 최근 3작과 대조한다. 축 정의(10축: 종이공작·플랫벡터·네온·클레이·픽셀·인쇄리소·칠판문구·블루프린트·직물·유리)는 references/game-references.json의 art_directions, 전수 감사·축 배정표·재스킨 계획은 docs/design-diversity-plan.md.

기본값 금지 3종: ① border-radius:13px + border:2px + inset 흰 하이라이트 + box-shadow:0 3px 0 스티커 칩(축 A·I 외 금지) ② 모든 게임에 AI 회화 배경(축 B·C·E·G·H는 배경 일러스트 자체가 금지) ③ 파티클 버스트 + 점수 팝업 + 화면 흔들림 3종 세트(축의 사건으로 대체 — 잉크가 번지고, 실이 꿰매지고, 치수선이 뻗는다).

3.5가독성과 반응형

  • 정오 피드백은 색 단독 금지(색약 배려) — 색+텍스트/도형+사운드 병행. 힌트는 정답 대신 "지금 이 행동이 성공하는가"를 즉시 표시.
  • 분수·수식은 KaTeX 실조판(로컬 벤더, CDN 금지). 렌더는 텍스트 변경 시에만, 매 프레임은 transform만.
  • 모바일 390px부터 초와이드 2000px까지 검증 — 플레이 영역이 화면을 활용해야 한다. 데스크톱 1280px+에서 레이아웃이 재배치(--stageW: min(100vw, 1280px) + html.land, 와이드 원형 3종)돼야 하며, 중앙 좁은 컬럼+빈 거터는 실격. 상세 규격·레시피·원형은 docs/playfield-spec.md. (구 "중앙 640px 컬럼+레터박스" 표준은 2026-08-28 폐기됨)
4단원

품질 게이트 — 통과가 아니라 거른다

3사 모델 분산: 판단이 어려운 곳은 상위 티어, 검산은 타사 모델, 관점 다양화는 3사 기획 경쟁

4.1기계가 확실히 판정할 수 있는 것 40가지

puppeteer가 실제로 플레이한다: __GAME_TEST__ 훅으로 시작·정답·오답을 강제 실행해 점수/목숨 변화를 검증, 문제 40개 표본 추출(정답∈선택지·중복·다양성 70%+), FPS 30+, 콘솔 에러·404 0건, 모바일~초와이드 4개 뷰포트, 표지 이미지 규격(1200×630/1080×1080)과 타 게임과의 sha256 중복(이미지 도용 사고 재발 방지)까지.

4.2사람 없이 사람처럼 — 검수관의 채점표

교육과정 정합 25 · 수학 정확성 25 · 재미 20 · 비주얼 20 · 모바일 10. 검수관은 스크린샷을 실제로 열어 보고, 문제를 손으로 검산하고, juice 기법 개수를 코드에서 센다. 후하게 주지 마라 — 평범하면 70점대가 명문화돼 있다. 80점은 "친구에게 링크를 보낼 만한" 수준. 여기에 실수 관용도 게이트(점수 무관)가 별도로 얹힌다.

4.3피드백 루프

사용자 의견은 factory/state/feedback.md에 적으면 다음 사이클의 기획·검수 프롬프트에 자동 주입 후 아카이브. 레퍼런스는 10게임마다 새 카테고리를 자동 스카우트하되 사람 승인 후에만 병합. 이 문서(바이블) 자체도 사고가 날 때마다 갱신된다 — 실패가 규범이 된다.

5.2포지셔닝 — 정면 경쟁이 아니라 상호보완

킹수학의 본질은 교실 다인 배틀 인프라(전자칠판 팀전·QR 리더보드·학급 시즌 랭킹)이고 오답 교정·오개념 설계는 거의 없다. 우리는 정반대 — 1인 몰입 + 오개념 역산 + 실수 관용 + 닌텐도급 프로덕션. 훔칠 것은 배틀 UI가 아니라 조각들이다: 소수점 시프트 조작, 전개도 접기 3D 피드백, 비례 문항 스펙, 프리핸드 채점 드로잉.

6단원

실패 박물관 — 일곱 번의 사고

전부 실제로 일어났고, 전부 규범이 됐다. 같은 사고는 두 번 나지 않는다.

사고 1 · 「자리에서」를 「자리까지」로 읽음

1회차 어림 게임이 "225를 십의 자리에서 반올림"의 답을 230으로 판정(정답 200). 검수관이 수학 0점 + 즉시폐기 → 수정 라운드에서 살아남.

→ 함정 사전 명문화 + 어림 4필드 데이터 모델 + 타사 모델 전수 검산 신설

사고 2 · 목숨이 평생 한 번만 깎이는 게임

"스와이프당 1회" 관용 로직이 pointerdown 기준이라, 손가락을 떼지 않고 플레이하면 목숨이 다시는 안 깎였다. 사용자 리포트 "죽지를 않아"로 발각.

→ 시간(220ms) 디바운스로 교체 + 연속 다중 히트 회귀 시나리오를 검증 표준에 추가

사고 3 · 남의 게임 이미지를 가져다 씀

병렬 이미지 생성 중 한 에이전트가 "최근 파일" 휴리스틱으로 다른 게임의 커버를 자기 것으로 저장 — 두 게임이 byte-identical 표지.

→ "툴이 반환한 경로만 써라" 규칙 + QA에 타 게임 대비 sha256 중복 검사(fatal)

사고 4 · 와이드 화면에서 레이아웃 전면 붕괴

QA가 세로 모바일 위주라 2000px 창에서 카드가 납작하게 늘어나고 겨냥도가 시커먼 덩어리가 된 걸 놓쳤다. 사용자 스크린샷으로 발각.

→ 당시 결론: 세로형 게임 중앙 640px 컬럼 표준 + QA 초와이드 뷰포트 + 검수관 wide.png 육안 의무화. 단, 640px 컬럼 표준은 2026-08-28 판형 규범 교체로 대체됨 — 전 게임이 중앙 좁은 컬럼으로 수렴해 "다 똑같고 화면을 안 쓴다"는 피드백을 낳았다. 현행 규범은 docs/playfield-spec.md(--stageW 1280 + 와이드 원형 3종). QA 초와이드 검증과 육안 의무화는 유지.

사고 5 · "유효하면 아무거나 합쳐지는" 병합

전개도 게임이 서로 다른 유효 전개도끼리 병합을 거부 — 십자형과 지그재그형 둘 다 정육면체가 되는데도. 사용자의 수학 직관이 코드보다 옳았고, 이 때문에 진행이 막혀 "치수가 안 보인다"는 2차 증상까지 유발.

→ 룰 심화 리워크("같은 상자의 다른 표현끼리") + 판정 로직 변경 시 기하학적 전수 검증 의무

사고 6 · 전부 같은 모델 = 전부 같은 취향

기획을 한 모델이 독점하자 4개 게임의 배경색이 전부 #07 남색 네온으로 수렴. "디자인이 다 똑같다"는 지적.

→ 기획 3안을 Claude/GPT/Grok 3사 경쟁으로 + 팔레트 무드 자동 회피 목록

사고 7 · 크론이 10분 만에 보고를 삼킴

파이프라인(30~50분)을 크론 타임아웃(10분)이 잘라 게임은 만들어지는데 보고만 증발. 태그만 겹치고 내용은 다른 "유령 매핑"이 시장에도 흔했다(5땡킹: 가능성 태그, 실제론 배수 게임).

→ 실행/보고 분리 구조 + 사전점검(preflight) 스크립트 + 단원 태그는 코드가 아니라 내용으로 검증
