## 0. 한 줄 요약

이 공장의 캐치프레이즈는 "2시간마다 게임 1개 자동 생산"이지만,
**실제 산출물을 만드는 것은 단선 파이프라인이 아니라 서로 다른 시간 상수를 가진 5겹의 피드백 루프**다.
파이프라인은 그중 가장 안쪽 한 겹(L0)일 뿐이고, 나머지 네 겹이 없으면
게시작 24편 중 9편은 존재하지 않고, 나머지 15편도 지금 점수를 받지 못한다.

| 층 | 이름 | 주기 | 무엇을 고치나 | 대표 실적 |
|---|---|---|---|---|
| **L0** | 생산 루프 | 2시간 (1사이클) | 게임 1편 | 게시 24 / 폐기 24 |
| **L1** | 사이클 내 자기수정 | 분~십분 | 이번 게임의 결함 | 수리(최대 3회) 후 재통과 다수 (칸자물쇠 88, 등불을 켜 92) |
| **L2** | 사이클 간 학습 | 하루 | **다음 게임들의 실패 유형** | fun 평균 6.8 → 12.4 (8/28→8/29) |
| **L3** | 캠페인 | 며칠~주 | **이미 게시된 전체 카탈로그 + 재발 방지 게이트** | 캠페인 6건 — 판형 11작 · 시각 18작 · 디자인 24작 · 타이틀 24작 · 구작 소급 5작 |
| **L4** | 부활 | 비정기 | **폐기된 것** | 게시작 24편 중 **9편(37.5%)** 이 부활 산물 |

## 1. 먼저 수치 — 단선 파이프라인이라면 나올 수 없는 숫자들

`factory/state/queue.json` 기준 (2026-08-29):

```
게시 24작 · 폐기 24작 · 게시율 50.0%
카탈로그 평균 점수 88.0 / 100  (게이트 80)
게시작 24편 중 9편(37.5%)이 run 이름에 `-salvage` 를 달고 있다 — 한 번 폐기됐다가 부활한 것
폐기본 보존 30폴더 · 사용자 피드백 아카이브 46건 · 사이클 로그 55회차
```

읽는 법:

- **게시율 50%는 실패가 아니라 게이트가 일하고 있다는 증거다.** 80점 미만은 어떤 경로로도
  게시되지 않는다(§7.3). 평균 88점은 통과분만 남은 결과다.
- **9/24 = 부활.** 폐기가 종점이었다면 카탈로그는 15작이고 평균은 지금보다 낮다.
  쩍쩍 75→87, 첨벙 79→86, 겹쳐딱 58→92, 경계폭주 65→91, 폴짝이 65→90, 꽝도장 51→87.
  **첫 검수 점수는 게임의 상한이 아니라 진단값이다.**
- **폐기 24건이 전부 보존돼 있다**(`factory/state/rejected/` 30폴더). 이것이 L2·L4의 원료다.

## 2. L0 — 생산 루프 (사이클 단위, `factory/run.sh`)

크론(Hermes `7c43f44b8c54`)이 2시간마다 `factory/cron-entry.sh` → `factory/run.sh` 를 부른다.

```
슬롯 선택(pick-slot.mjs)
  → 기획 3안 병렬 (grok-4.6 / gpt-5.6-sol / gpt-5.6-terra — 서로 다른 회사·티어)
  → 심사 (codex sol, fun 예측 게이트)
  → 아트 (codex 이미지 생성 병렬: bg/hero/thumb/square/title)
  → 빌드 (grok, 한 파일 HTML)
  → 자동 QA (qa.mjs, puppeteer 43항목)
  → 독립 수학 전수 검산 (codex sol — 만든 모델과 다른 회사)
  → 검수 채점 (codex sol, 100점 만점 / 80점 게이트)
  → [미달 시] 수정 루프(최대 3회) → 재QA → 재검산 → 재검수
  → publish-game.mjs (게이트 강제) → verify-catalog.mjs (장부 감사)
  → 커밋·푸시·Vercel → 디스코드 보고
  → (10작마다) 레퍼런스 스카우트
```

### L0가 단순한 단계 나열이 아닌 이유 — 세 개의 분기점이 루프다

1. **기획이 3안 병렬 + 심사다.** 한 모델이 한 안을 내는 구조가 아니라,
   서로 다른 회사 모델 3개가 서로 다른 각도(정통 아케이드 / 요즘 모바일 게임 문법 / 비주얼 승부)로
   동시에 내고 상위 티어가 고른다. `run.sh` 주석에 이유가 적혀 있다 —
   "전부 같은 모델로만 기획하니 게임들이 서로 비슷해 보인다는 지적을 받았다."
2. **판정자와 생산자가 분리돼 있다.** 빌드는 grok, 검수·수학검산은 codex.
   `factory/config.sh`: *"같은 모델이 만들고 같은 모델이 검산하면 같은 맹점을 공유한다."*
3. **수학 검산이 종합 검수에서 분리돼 있다.** `run.sh` 6.5단계 주석:
   *"수학 오류는 이 프로젝트에서 가장 치명적인 결함이라 종합 검수와 분리해 독립 에이전트에게
   전수 검산만 시킨다. 두 눈이 따로 보게 하는 것이 요점."*
   실제로 8/29 세 회차(pair-heist·decimal-dot-raiders·decimal-alchemy)가 `math: 0` 으로
   즉시 폐기됐다 — 나머지 항목은 다 통과였다.

### 자동 QA는 43개 이진 검사다 (`factory/lib/qa.mjs`)

캔버스가 있는 게임 기준 `total: 43` (캔버스가 없으면 `visual.notblank` 가 빠져 42):

```
file.index file.meta file.thumb file.square thumb.dims square.dims image.notduplicate
meta.schema meta.slug meta.title meta.standards meta.unit
static.nocdn static.relpath static.testhook static.viewport static.lang static.title
static.size static.assets
run.ready run.api run.score run.penalty run.console run.pageerror run.network
math.count math.prompt math.answer math.choices math.dupchoices math.variety math.numeric
input.real perf.fps perf.fps1280
mobile.overflow mobile.touch tablet.overflow visual.notblank
layout.wide1280 wide.overflow
```

이 중 **20개가 `fatal`** 이다 — 하나라도 실패하면 `auto_pass:false` + `process.exit(1)`.
정적 검사 구간이 끝나는 시점에 fatal 이 있으면 **브라우저 검사 자체를 건너뛰고** 즉시 종료한다(비용 절약).
반대로 `thumb.dims`·`math.variety`·`layout.wide1280` 은 **비-fatal** 이다 — 기계는 통과시키고 검수 에이전트가 감점한다.
**"기계가 확실히 판정할 수 있는가"와 "중요한가"는 다른 축이고, 이 공장은 둘을 섞지 않는다.**

#### 2026-09-01 보강 4건 — 게이트가 뚫린 실사례에서 나왔다

1. **`input.real` 신설 (fatal).** `__GAME_TEST__.answerCorrect()` 는 게임 내부 판정을
   직접 부르므로 **입력 경로를 통째로 건너뛴다.** 터치가 완전히 죽은 송판올려(plank-up)가
   41개 중 40개를 통과했다. 이제 브라우저가 만든 **진짜 pointer 이벤트**로
   탭·드래그를 (엘리먼트 중심 + 격자로) 쏘고, 무입력 기준선보다 큰 변화가
   `getState()`·DOM 서명·캔버스 픽셀 중 하나에 생기는지 본다. 음소거·도움말 같은
   게임 크롬 버튼은 근거에서 제외한다 — 그걸 허용하면 죽은 게임이 음소거 토글로 통과한다.
   범용 제스처로 도저히 닿지 않는 게임은 훅에 선택적 `simulateInput()` 을 노출해 탈출할 수 있다.
2. **`perf.fps` fatal 승격 + 중앙값화 + 데스크톱 추가.** 단일 3초 표본은 머신 부하에 따라
   11~60fps 로 요동쳐 오탐·미탐이 둘 다 났다. 이제 1.5초 표본 3회의 중앙값을 쓰고,
   미달이면 한 번 더 재고, **그래도 미달이면 같은 브라우저에서 고정 비용 캔버스 벤치를 돌려
   그 시점의 머신 여유를 재서 보정**한다. 보정값도 30 미만이면 fatal, 보정값이 30 이상이면
   "머신 부하 가능성"으로 비-fatal 판정 보류. 1280 뷰포트도 같은 방식으로 따로 잰다.
3. **표본 변주.** `sampleProblems(40)` 한 번만 부르면 결정적 시드 게임은 늘 같은 40문항만
   보여 준다. 이제 `n = 40 / 17 / 63` 세 번 불러 합집합(중복 제거)을 검산 표본으로 넘긴다.
4. **`math.variety` 강화.** 프롬프트 **문자열 전체**를 비교하니 `"(상자 3, 시점 A)"` 같은
   접미사만 갈아 끼우면 무력화됐다(cube-unfasten 은 사실상 10문제로 100% 를 받았다).
   이제 괄호·대괄호 주석 덩어리와 꼬리 일련번호를 걷어낸 **핵심 문장**으로 센다.
   숫자 자체는 지우지 않는다 — `3/4 × 2/3` 과 `1/2 × 5/6` 은 다른 문제다.
   같은 잣대로 다시 재니 cube-unfasten 은 원문 100% → 핵심 16%(10/63) 로 드러났다.

이 목록 자체가 루프의 퇴적물이다:

- `layout.wide1280` — 8/28 판형 캠페인(§5.1)이 남긴 것
- `image.notduplicate` — sha256 으로 **다른 게임의 thumb/square 와 바이트 동일한 이미지**를 잡는다.
  유래는 아트 에이전트가 `find ~/.codex/generated_images -mmin -N` 으로 "최근 파일"을 집어
  **동시 실행 중인 다른 에이전트의 이미지를 훔쳐 온** 사고다(대칭 브레이커의 square.png 가 어림 대시와 byte-identical).
  → 기계 검사 + `20-art.md` 의 "최근 파일 찾기 절대 금지" 조항 두 겹으로 막았다.
- `math.dupchoices` — 오답 수치가 우연히 정답과 일치하는 경우(유리를 불어 r=2 사례) → `공장 규범: 오답 수치 우연 전수 검사`

**QA 항목 리스트를 시간순으로 읽으면 이 공장이 밟은 지뢰 목록이 된다.**

### 검수 채점표 (`40-review.md`) — 배점 자체가 우선순위 선언이다

| 항목 | 배점 | 특기 |
|---|---|---|
| 교육과정 정합성 | 25 | standards·unit 실재 + 내용 일치 10 / 핵심 개념 정면 10 / 학년 수준 5 |
| 수학 정확성 | 25 | **표본 손 검산에서 하나라도 틀리면 이 항목 0점 + 총점 무관 즉시 폐기** |
| 재미 | 20 | 수학이 동사인가 6(문제창이면 5점 이하) / 30초 재미 5 / 피드백·곡선 5 / **선택지·레인이 2개면 −4** |
| 비주얼 | 20 | 이 중 **8점이 「디자인 분화」**(선례 비유사 4 + 축 준수 4) — §5.3 |
| 모바일·성능 | 10 | 390×844 잘림 3 / FPS·터치·오디오 2 / 로딩 2 / **숫자·분수 가독성 3** |

배점 외 **별도 게이트 4종**(점수와 무관하게 `must_fix: high` 또는 `passed:false`):
퇴화 전략(무뇌 봇) · 실수 관용도(한 번의 실수로 회복 불가면 실격) · 물리 은유 정합성 ·
데스크톱 플레이 영역 활용(좌우 거터 합이 화면 폭 30% 초과 시).
그리고 프롬프트에 이 한 줄이 있다 — *"후하게 주지 마라. 평범하면 70점대."*

### 게이트 통과 조건은 AND 4개

```
검수 passed === true
  AND  reject_immediately !== true      # 수학 오류 1건 / 실수 관용도 결함이면 점수 무관
  AND  QA 종료코드 0                     # fatal 0건
  AND  수학 검산 verdict ≠ fail          # errors 1개만 있어도 fail (예외 없음)
```

유일한 완화 지점은 검산 결과 파일이 아예 없을 때(`unknown`)뿐이고, 그때는 종합 검수에 맡긴다.

## 3. L1 — 사이클 내 자기수정 루프 (분~십분)

같은 사이클 안에서, 사람 개입 없이 되돌아가는 루프들.

### 3.1 검수 미달 → 수정 루프 최대 3회 → 재검수 (`45-fix.md`)

`run.sh` 8~9단계. 검수 `passed != true` 이거나 QA 종료코드 ≠ 0 이거나 수학 검산이 `fail` 이면
수리 에이전트(grok)가 `review.json` 의 `must_fix` 를 전부 처리하고, **QA·수학검산·검수를 다시 탄다.**
재검수 프롬프트에는 이 한 줄이 붙는다:

> 이것은 **N차 재검수**다. `factory/work/fix.json` 에 수정 내역이 있다. 수정이 실제로 반영됐는지 확인해라.
> 봐주지 마라 — 이전 점수와 무관하게 기준대로 채점해라. 여전히 미달이면 그렇게 판정해라.

**기회 상한은 2026-08-31까지 1회였고, 이제 3회다 (`MAX_FIX_ROUNDS`).** 무한 재시도를 허용하면
점수가 수렴할 때까지 갈리며 게이트가 무의미해진다 — 그래서 **상한은 있되 폐기 전에 부족한 부분을
살릴 기회를 넓혔다.** 부활 트랙(L4) 실적(9/24편)이 "1회 수리로 부족했던 작품이 2·3차 수리면 살았을
가능성"을 시사했고, 이것이 상한 3회의 근거다. 반대편 근거도 정직하게: 라운드가 늘면 사이클이
크론 주기(120m)를 넘는다 — run.lock 이 다음 틱을 스킵하므로 시스템은 안전하지만, 연속 미달 게임에서
생산 간격이 늘어난다. 관측 포인트: queue.json 의 수정 라운드 분포(3회 소진 후 폐기 비율) — 높으면
수정이 아니라 기획·빌드 단계(L0 쪽)의 문제다. 8/25 신작 3연작(유리를 불어 81 · 등불을 켜 92 ·
칸자물쇠 88)은 셋 다 "첫 검수 미달 → 수리 → 게이트 재통과" 패턴이었다.
각 라운드의 검수 이력(review-N.json)은 다음 수정 프롬프트에 누적 주입된다 — 같은 지적의 반복 방지.

### 3.2 빌드 러너 결과 기반 폴백 (2026-08-28 도입)

**사고**: 8/27 20:14 이후 4회차(mirror-vault · mirror-falls · glass-star-theater · lightfold-forge)가
전부 빌드 단계에서 `402 Payment Required: Grok Build usage balance exhausted` 로 통째로 죽었다.
`resolve_runner()` 는 **바이너리 존재만** 확인했고 grok CLI 자체는 살아 있었으므로 폴백이 발동하지 않았다.

**수정** (`run.sh` 5단계): 러너의 *존재*가 아니라 *실행 결과*를 본다.

```bash
BUILD_ERR="$(grep -m1 -Eo 'status 402|402 Payment Required|Payment Required|usage balance exhausted' "$LOG_DIR/build.log")"
if { [ "$BUILD_RC" -ne 0 ] || [ -n "$BUILD_ERR" ] || [ ! -f ".../index.html" ]; } ...
  codex_run "$T_BUILD" ... "$CODEX_MODEL_SMART"   # sol 로 1회 재시도
```

동시에 **장부 버그**도 고쳤다 — 빌드에서 죽은 회차는 `queue.json` 의 `failed` 에 안 남고 있었다.
폐기 단계에만 인라인으로 있던 기입 로직을 `record_failed()` 헬퍼로 분리하고 빌드 실패 경로도 통과시켰다.
사라졌던 4회차는 `reason: "grok 402 빌드 실패 … 폴백 부재로 미기록됐던 회차, 2026-08-28 소급 기입"` 으로
지금 queue.json 에 남아 있다.

**교훈**: 폴백은 "도구가 있는가"가 아니라 **"결과가 나왔는가"** 를 조건으로 걸어라.

### 3.3 무뇌 봇 자가 테스트 — 빌드가 자기 게임을 봇으로 검증한다

`30-build.md` B3. 구현이 끝나면 빌드 에이전트가 **자기 게임에 봇 4종을 붙여 각 200판** 돌린다:

| 봇 | 전략 |
|---|---|
| 연타 봇 | 항상 같은 입력만 반복 |
| 순환 봇 | 1→2→3→4 순서로 돌려가며 입력 |
| 무작위 봇 | 매번 무작위 위치·무작위 방향 |
| 무입력 봇 | 아무것도 하지 않고 세션 길이만큼 방치 |

**합격선: 어떤 봇도 완주율 25% 이하, 무입력 봇은 0%.**
넘으면 정답 후보 비율을 낮추거나(쓱말이는 레벨별 0.55→0.28), 시작 상태를 정답이 아닌 값으로 두거나
(파도 검문소 — 무조건 출항 봇 0%), 실패 조건을 강화한다.
측정값은 최종 응답에 한 줄로 보고하고 **검수관이 대조한다.**

이것이 L1인 이유: 생산자가 스스로 반증을 시도하고, 실패하면 자기 코드를 고친 뒤 다음 단계로 넘어간다.

## 4. L2 — 사이클 간 학습 루프 (하루 단위)

**폐기 패턴을 분석해 프롬프트 게이트로 승격시키는 루프.** 이 공장에서 가장 값어치가 큰 층이다.
개별 게임을 고치는 게 아니라 **앞으로 만들어질 모든 게임의 실패 확률**을 낮춘다.

### 4.1 실사례 — 8/28 fun 6연속 폐기 → 3단계 게이트 신설 → 다음 날 fun 2배

**관찰**: 8/28 하루 6회차가 연속 폐기됐다.

| 회차 | 슬러그 | 총점 | curriculum | math | **fun** | visual | mobile |
|---|---|---|---|---|---|---|---|
| 081607 | light-shards | 58 | 17 | 15 | **4** | 14 | 8 |
| 111633 | butterfly-pinbox | 71 | 19 | 24 | **5** | 14 | 9 |
| 141658 | twin-stars | 69 | 21 | 24 | **5** | 12 | 7 |
| 171723 | mirror-garden | 75 | 18 | 23 | **11** | 14 | 9 |
| 201747 | mirror-beat | 62 | 18 | 18 | **4** | 17 | 5 |
| 231812 | overlap-tower | 47 | 15 | 0 | **12** | 13 | 7 |

curriculum 18.0 · visual 14.0 은 다 통과 수준인데 **fun 평균 6.8/20 하나가 게이트를 무너뜨렸다.**

**분석** (`docs/fun-bottleneck-2026-08-29.md`, review json 12개 전수 독해):
실패 패턴 8종이 나왔다 — F1 무뇌 전략 100% 성공(6/6) · F2 코드가 대칭짝·대응점을 대신 생성(6/6) ·
F3 기획의 드래그·회전·포개기가 하단 4지선다로 붕괴(6/6) · F4 이빨 없는 실패(4/6) ·
F5 난이도 곡선 미구현(4/6) · F6 이름만 레퍼런스(4/6) · F7 정답 누설(2/6) ·
**F8 주스 9종 다 넣고도 fun 4점(3/6)**.

F8이 핵심 반증이다 — **연출을 아무리 붙여도 F1~F3이 있으면 fun은 회복되지 않는다.**
그리고 성공작 대조(쓱말이 91/fun17 · 소수 스매시 91/fun17 · 파도 검문소 90/fun16 · 꿀몇잔 90/fun14)에서
4개 축을 추출했다: ①답 공간 = 조작 공간(선택지 버튼 없음) ②무작위 성공률이 낮음(봇 실측 18%·0% vs 실패작 100%)
③실패에 이빨이 있음 ④기획서의 핵심 루프가 코드에 실재.

**승격** — 분석을 문서로 끝내지 않고 **세 단계 프롬프트에 게이트로 심었다**:

| 단계 | 파일 | 신설된 게이트 |
|---|---|---|
| 기획 | `10-design.md` | 「fun 필수 요건」 F1~F8 금지 + 컨셉 JSON에 `fun_contract` 5필드 (`answer_action` / `random_success_rate` / `player_does_the_math` / `fail_teeth` / `tension_curve`) |
| 심사 | `15-judge.md` | 「fun 예측 게이트」 — 실격 사유 **D1 무뇌 전략 / D2 코드 대행 / D3 4지선다 붕괴 / D4 이빨 없는 실패 / D5 곡선 없음 / D6 90분 초과 과욕**. 하나라도 걸리면 총점과 무관하게 탈락. 3안 전부 실격이면 최고안 + `fun_mandate` 로 **승자 컨셉의 필드를 실제로 수정**. `predicted_fun` 15 미만이면 게시 불가로 간주 |
| 빌드 | `30-build.md` | 「재미 구현 체크리스트」 B1~B6 — 조작=판단 직결, 코드 대행 금지, **무뇌 봇 4종×200판 자가 테스트 의무화**(§3.3) |

**비용 논리가 이 승격의 근거다.** `15-judge.md` 에 그대로 적혀 있다 —
*"재미없는 기획은 빌드 전에 여기서 죽어야 한다(폐기 1회 비용 ≈ 40분)."*
게이트를 **가장 싼 단계로 앞당기는 것**이 이 루프의 설계 원리다.

**효과 실측** — 개입 다음 날(8/29) 11회차:

| | 8/28 (6회, 개입 전) | 8/29 (11회, 개입 후) |
|---|---|---|
| 총점 평균 | 63.7 | **72.2** (+8.5) |
| **fun 평균** | **6.8 / 20** | **12.4 / 20** (+5.6, 1.8배) |
| visual 평균 | 14.0 | 13.3 |
| math 0점(즉시폐기) | 1회 | 3회 |

fun은 목표대로 올라갔다. 그런데 **게시는 여전히 0건이다** — 최고점이 79(dot-stamp-day)였다.
이것이 이 루프의 정직한 현재 상태이자 다음 사이클의 입력이다:

> **게이트를 하나 올리면 병목은 사라지는 게 아니라 이동한다.**
> 8/29의 새 병목은 (a) 수학 즉시폐기 3회 (b) visual 평균 13.3 — 같은 날 도입된
> 디자인 축 준수 게이트(§5.3)가 감점을 시작했다. 실제로 22:18 회차 `review-2.json` 의
> `visual_diff.axis_compliance` 는 *"index.html:24의 로고 text-shadow가 shadow 금지를 위반 … 축 준수 0/4"* 로
> 새 게이트가 그 자리에서 물었다.
> 다음 L2 사이클은 이 두 지점을 봐야 한다. `fun_gate`/`predicted_fun` 은 이미 judge 로그에 남고 있으므로
> 개입-효과 측정은 계속 가능하다.

### 4.2 검수 지적 → 규범 신설 (OPERATIONS §9)

개별 검수 지적 중 **일반화 가능한 것**은 그 게임만 고치고 끝내지 않고 프롬프트 규범으로 승격한다.
git 이력에 `공장 규범:` 접두어로 9건이 남아 있다:

```
2026-08-18  「○의 자리에서」 vs 「○의 자리까지」 함정을 공장 규범에 명시
2026-08-19  vibe 시리즈 22종 실분석 인사이트를 공장 규범에 반영
2026-08-20  물리 은유 정합성 규칙 추가 (빌드+검수)
2026-08-20  정답/오답 연출 감정 어휘 분리
2026-08-20  실시간 액션 중 계산 부하 규칙
2026-08-20  퇴화 전략 게이트 추가 (검수)
2026-08-21  킥 메커닉 상한·페이싱·반복 체감 규칙
2026-08-21  판형은 콘텐츠가 결정·작명 다양성 (사용자 근본 지적)
2026-08-25  오답 수치 우연 전수 검사
```

「○의 자리에서 반올림」과 「반올림하여 ○의 자리까지」가 완전히 다른 조작이라는 한국 교과서 함정은
**게임 하나를 폐기시킨 뒤** `CLAUDE.md` 최상단 경고 절이 됐고, 데이터 모델까지 지정됐다
(`roundingMode`/`decisionPlace`/`retainedPlace`/`promptConvention` 4필드 분리).
개별 사고가 **구조적 처방**으로 번역된 사례다.

### 4.3 이력 기반 중복 회피 — 점수식으로 구현된 다양성

`queue.json` 은 `produced`/`failed` 외에 `mechanic_history`(25건), `palette_history` 를 들고 있고
`publish-game.mjs` 가 게시 때 멱등으로 갱신한다. `pick-slot.mjs` 가 이것을 **점수식**으로 소비한다:

```
메커닉 점수 = 100
            − 60  (mechanic_history 마지막 6개에 있으면)
            − 80  (같은 단원의 기존 게임이 이미 쓴 메커닉이면)
            + 25  (단원 영역과 math_fit 일치)
            −  3 × web_difficulty
→ 상위 5개를 mechanic_pool, 회피 대상 합집합을 avoid_mechanics 로 기획에 전달
```

`palette_history` 마지막 6개는 `avoid_palette_moods` 로 넘어간다.

> **2026-08-26 사고**: `mechanic_history` 가 18작 중 13개만 기록돼 **중복 회피가 조용히 무력화돼 있었다.**
> 이력 기반 회피는 이력 기록이 멱등할 때만 작동한다 — 그래서 게시 진입점이 `publish-game.mjs` 하나로
> 통합됐고, `verify-catalog.mjs` 는 `mechanic_history.length < produced.length` 를 **정합성 위반으로 잡는다**.

**단, 다양성 회피가 전부 코드인 것은 아니다.** 8/29 디자인 캠페인이 추가한 축(`visual_axis`) 회피는
`pick-slot.mjs` 에 **필드가 없다** — 기획 에이전트가 `queue.produced` 마지막 5개의 slug 를 뽑아
각 `meta.json` 의 `art_direction.visual_axis` 를 직접 grep 해서 확인하는 **수동 절차**다(§7.7 참조).
코드 게이트와 프롬프트 게이트의 신뢰도 차이는 §7.7 에서 다룬다.

## 5. L3 — 캠페인 루프 (사람 피드백 구동, 며칠~주 단위)

사용자(교사)의 지적 하나가 **전수 감사 → 근본 원인 → 일괄 수리 → 재발 방지 게이트 신설** 로 전개되는 층.
L2가 "다음 게임"을 고친다면, L3는 **이미 게시된 전 카탈로그**를 고치고 동시에 파이프라인에 항체를 남긴다.

**캠페인의 5박자는 항상 같다:**

```
① 사용자 지적 (보통 스크린샷 한 장)
② 전수 감사 — 자동 캡처 + AI 판정 + 오케스트레이터 교차 확인
③ 근본 원인 — 거의 항상 "프롬프트/스펙에 박힌 몇 줄"
④ 일괄 수리 — 병렬 서브에이전트, 게임당 1명
⑤ **재발 방지 게이트 신설** ← 이게 없으면 캠페인이 아니라 잡일이다
```

`docs/legacy-audit-2026-08-20.md`. **이건 방향이 반대인 캠페인이다** — 사용자 지적이 아니라

- 꽝도장 — 게시 후에도 *"애들이 풀 수 없는 속도"* 지적을 받아 낙하를 approach(계산 6초)/zone(판정 창 2.4초)로 분리 재설계.
  **어린이 모사 봇(반응 1.5~4.5s) 48판 100%, 무뇌봇 44판 0%** 로 재검증

### 함정 — 부활은 게시 경로를 우회하기 쉽다

**2026-08-26 사고**: 사람이 `cp -r` 로 부활시키면 `run.sh` 10단계를 건너뛰므로
`meta.json` 의 `qa.passed` 가 `false` 로 남고, `build-index.mjs` 필터에 걸려
**게시 커밋이 있는데도 허브·카탈로그에서 사라진다.** 쩍쩍·첨벙·유리를 불어·등불을 켜·칸자물쇠 5작이
이 상태였고 쩍쩍·첨벙은 **6일간** 보이지 않았다. 카탈로그가 13→18작으로 복구됐다.
→ 처방은 §7.3(단일 진입점 + 장부 감사).

## 7. 횡단 원칙 — 모든 층에 공통으로 적용되는 것

### 7.1 신뢰하지 말고 실측하라

에이전트의 "고쳤습니다"는 데이터가 아니다. `docs/OPERATIONS.md` §6:

- 에이전트가 고쳤다고 해도 **스크린샷을 Read 로 직접 봐라.** *거짓 verified 사례가 실제로 있었다(첨벙 태블릿).*
- 수학 수정은 예시 1개 이상 **손검산**으로 재확인
- 퇴화 전략 의심 시 **무뇌 봇 실측(성공률 수치)** 을 요구해라
- 라이브 반영은 `curl` 로 확인 (Vercel 전파 수십 초)

검수 프롬프트에도 같은 의무가 박혀 있다 — *"스크린샷: … **Read 툴로 실제로 봐라**"*.
캠페인의 감사 단계가 전부 "자동 캡처 → 이미지 판정 → 오케스트레이터 교차 확인" 3단인 것도 같은 원칙이다.

**측정 환경 자체도 실측 대상이다**: QA 브라우저는 swiftshader 소프트웨어 렌더링이라 fps 게이트가 부하에 민감하다.
크론이 유출한 고아 크롬(ppid=1, GPU 354%)이 fps 측정을 왜곡한 사고가 있었다 — 최종 측정은 한산할 때 한다.

### 7.2 판정자와 생산자를 분리하라 (타사 모델 교차)

`factory/config.sh` 원문:

> 역할 배정 원칙: 판단이 어려운 단계(심사·빌드·검수)는 상위 티어, 기획·수정은 중간 티어,
> **수학 검산은 다른 회사 모델**(교차 검증 — 같은 모델이 만들고 같은 모델이 검산하면 같은 맹점을 공유한다).

실행: 빌드 grok / 검수·수학검산 codex sol / 기획 3안은 grok-4.6·sol·terra 3사·3티어.
캠페인의 이미지 판정도 같은 원리로 codex 가 맡고 오케스트레이터가 교차 확인한다.

### 7.3 게이트는 불변식이다 — 점수 유도 금지

```js
// factory/lib/publish-game.mjs
if (gate < 80) fail(`게시 거부: 게이트를 80점 아래로 낮출 수 없습니다 — 요청값 ${gate}점`);
...
if (score < gate) fail(`게시 거부: ${score}점은 게이트 ${gate}점 미만입니다.`);
```

- **게시 진입점이 하나다.** 자동 사이클도, 사람이 손으로 하는 부활도 `publish-game.mjs` 를 거친다.
  이 스크립트가 `meta.qa` 갱신 · `queue.json`(produced·mechanic_history·palette_history) 갱신 · 허브 재빌드를 **멱등**으로 한다.
- **어떤 `--gate` 값으로도 80 아래로 못 내린다.** 게이트는 인자가 아니라 코드 상수의 하한이다.
- 재검수 프롬프트는 명시적으로 *"봐주지 마라"* 라고 지시한다 — 점수를 만들어 통과시키는 것은 실패 모드다.
- 폐기·실패는 숨기지 않고 그대로 보고한다(OPERATIONS §11: *"게이트가 일한 것"*).

### 7.4 모든 사고는 규범이 된다 (HANDOVER → OPERATIONS/CLAUDE.md 승격)

사고는 두 단계로 소화된다:
1. **HANDOVER 에 사건 기록** — 무슨 일이 있었고 무엇을 어떻게 고쳤는지 (살아있는 문서)
2. **일반화되면 OPERATIONS §13 함정 목록 / CLAUDE.md 규범 / 프롬프트 조항으로 승격** (불변 문서)

승격된 함정의 예:
- **스냅샷 좀비**: `run.sh` 는 자신을 `/tmp/mgf-run-$$.sh` 로 복사해 실행하므로(1시간짜리 사이클 도중
  누가 파일을 편집하면 셸이 엉뚱한 바이트 오프셋으로 점프한다) `pkill -f "factory/run.sh"` 만으로는 안 죽는다.
  **좀비가 옛 코드로 완주하며 큐를 오염시킨 실제 사고**(등불을 켜 1차)가 있었다 → `pkill -f "mgf-run-"` 병행.
- **러너 모델 인자 400** (8/25): 폴백 시 다른 회사 모델 이름을 그대로 넘겨 400 → `stage_run` 이
  **폴백 시 모델 인자를 버리도록** 구조적으로 수정.
- **크론 600초 절단** (8/18 5회차): Hermes 크론이 스크립트를 600초에 강제 종료하는데 사이클은 30~50분이라
  보고가 통째로 유실됐다(게임은 고아 프로세스로 계속 만들어졌다) → `cron-entry.sh` 는 `nohup` 백그라운드 발사 후
  즉시 종료하고, **보고는 run.sh 자신이 직접** `hermes send` 한다.
- **pgrep 한글/괄호 패턴** 정규식 오작동 → PID 기준 감시.
- **인용부호 없는 변수 확장**으로 슬러그 목록 전체가 폴더명이 된 빈 디렉터리 2개 → 경로 변수는 항상 인용.

### 7.5 장부 정합성 — 상태를 믿지 말고 감사하라

`factory/lib/verify-catalog.mjs` 가 **`queue.produced` ↔ `catalog.json` ↔ `public/g/` 실제 폴더**
3자를 대조한다. 5종 위반 중 하나라도 걸리면 `exitCode = 1`:

1. produced 에 있는데 catalog 에 없음 → **원인을 3단계로 자동 진단**(디렉터리 없음 / meta.json 없음 / `meta.qa.passed !== true` / 허브 재빌드 필요)
2. catalog 에 있는데 produced 에 없음 (생산 이력 누락)
3. 필수 4파일(`index.html`/`meta.json`/`thumb.png`/`square.png`) 결손
4. produced 에도 failed 에도 없는 **고아 디렉터리**
5. `mechanic_history.length < produced.length` → **중복 회피 무력화 경고**(§4.3)

`run.sh` 10단계가 게시 직후 이걸 호출한다 — *"게시했는데 허브에 안 보이는 사고를 그 자리에서 잡는다."*
단 **경고만 하고 파이프라인을 죽이지는 않는다**(`|| log "⚠️"`) — 감사 실패가 게임 게시를 막을 이유는 없고,
로그에 남으면 사람이 다음 사이클에 처리한다. **감사와 차단을 구분한 설계다.**

```
$ node factory/lib/verify-catalog.mjs
✅ 정합성 이상 없음 — 게시 24작 / 카탈로그 24작
```

이 감사가 없던 시절에 5작이 6일간 사라져 있었다(§6 함정 절). **자동화의 상태는 자동으로 감사돼야 한다.**

### 7.6 사용자 피드백은 파이프라인에 주입된다

`factory/state/feedback.md` 에 사람이 뭔가 적어두면 `run.sh` 1단계가 그것을 읽어
**그 사이클의 기획 프롬프트와 검수 프롬프트에 그대로 끼워 넣고**
`factory/state/feedback-archive/<RUN_ID>.md` 로 옮긴 뒤 본문을 비운다(매 사이클 반복 주입 방지).
검수 프롬프트에는 이 문장이 붙는다 — *"이 피드백을 채점에 직접 반영해라. 특히 지목된 문제가
이번 게임에도 있으면 must_fix 로 적어라."*
아카이브는 현재 **46건**. 사람의 관찰이 자동 루프의 1급 입력이다.

### 7.7 게이트에는 세 등급이 있다 — 그리고 승격되지 못한 것들

게이트가 착지하는 층은 셋이고, **신뢰도와 비용이 다르다**:

| 등급 | 형태 | 성질 | 예 |
|---|---|---|---|
| ① **기계** | `qa.mjs` 항목 / 스크립트 exit code | 결정적·무료·우회 불가 | `layout.wide1280`, `image.notduplicate`, `publish-game.mjs` 의 80 하한 |
| ② **배점** | 검수 프롬프트의 점수 배분 | 판단이 들어가지만 수치로 남고 추이 관측 가능 | 비주얼 20점 중 분화 8점, fun 20점 |
| ③ **프롬프트 규범** | "~하지 마라" 조항 | 가장 싸게 추가되지만 **조용히 무시될 수 있다** | 직전 5작 축 금지, 금지어 3개 |

**정직하게 적어야 할 사실 — 정량 지표가 기계 게이트로 승격되는 비율은 낮다.**

- 디자인 캠페인은 CSS 선언 자카드 **47~78%** 라는 정량 지표를 발명해 원인을 특정했지만,
  그 측정 스크립트(`similarity.mjs`)는 세션 스크래치패드에 남았고
  계획에 있던 `factory/lib/design-similarity.mjs` (자카드 45% 자동 게이트)는 **만들어지지 않았다.**
  지금 그 자리를 지키는 것은 **검수 에이전트가 최근 3작 스크린샷을 눈으로 대조하는 ②등급**이다.
- `pick-slot.mjs` 의 `axis_history` / `axis_usage` / `recent_mascot_count` 도 **미구현**이다(§4.3).
  축 중복 회피는 현재 ③등급 — 기획 에이전트의 수동 grep 에 의존한다.
- 타이틀 원형 6종(8/20)은 **`factory/prompts/` 어디에도 반영되지 않았다.** `grep -rl "세계 진입형"` 은
  계획 문서 하나만 반환하고, `30-build.md` 는 여전히 (획일 규격인) `title-screen-spec.md` 만 참조한다.
  타이틀 서체 캠페인의 4단계(프롬프트 반영)도 미착수다.

반대로 **승격에 성공한 표본**은 꿀몇잔이다: 교사 지적 → ③등급 정성 질문(8/20) → ②·①등급 정량 봇 의무(8/29).

> **규칙**: 캠페인이 정량 지표를 발명했다면, 그 지표를 **저장소 안의 스크립트로 남겨라.**
> 스크래치패드에 있는 측정은 다음 사람에게 존재하지 않는 것과 같다.
> ③등급으로 끝난 게이트는 "적용됐다"가 아니라 **"적용될 것으로 기대된다"** 로 기록해라.

### 7.8 게이트는 획일화를 낳는다 — 재발 방지책의 반작용을 관측하라

이 공장에서 **네 번 연속으로 근본 원인이 "우리가 직접 쓴 규범 문장"** 이었다.

| 캠페인 | 진범 | 그 문장의 원래 목적 |
|---|---|---|
| 판형 (8/28) | 구 바이블의 "중앙 640px 컬럼 + 레터박스" 표준 | **사고 4(와이드 화면 레이아웃 붕괴)의 재발 방지책이었다** |
| 디자인 (8/29) | `20-art.md` 고정 스타일 3행 + `30-build.md` "게임 화면 폴리시" | 품질 하한을 보장하려는 스타일 규격 |
| 타이틀 (8/29) | `title-screen-spec.md` §2.2 복붙용 CSS 한 줄 | 타이틀 품질 균일화 |
| 독창성 (9/05) | **8/29 디자인 캠페인이 만든 축 10종 + "직전 5작 중복 금지" + "축당 정원 3작"** | **디자인 획일화(8/29)의 재발 방지책이었다** |

**9/05 재발이 특히 뼈아프다 — 진범이 §7.8 자신이 처방한 게이트였다.** 축을 고르게 하니
생산자는 "직전 5작에 없는 축"을 골랐고, 그 축을 이미 쓴 게임의 **친척**이 됐다. 사용자 표현:
*"심각한 문제, 독창적인 것을 원한다."* 획일화를 막으려고 만든 유한한 선택지가 곧
**가족 분류표**가 된 것이다. 처방: 축을 **참고 어휘 사전**으로 강등하고(`art_directions.status:
"vocabulary"`), 기본값을 **매 게임 고유 정체성 발명**으로 뒤집고, 게이트 판정을
"직전 N작 대조"에서 **"카탈로그 전체에서 가장 닮은 1작과도 계열이 다른가"** 로 바꿨다
(15-judge `D7`, 40-review `most_similar.same_family`).
**교훈: 다양성 게이트를 유한한 열거형으로 만들면 그 열거형이 새 템플릿이 된다.**
다양성은 "목록에서 안 겹치게 고르기"가 아니라 **"매번 새로 짓고, 전수 대조로 검증하기"** 여야 한다.

그리고 design-bible §3.2 의 **"juice 9기법 중 6개 이상"** 채점표는
구작 5작 중 4작이 **정답 경로에 화면 흔들림**을 넣게 만들었고(§5.5),
동시에 24/24 게임이 **파티클+점수팝업+shake 3종 세트**로 수렴하게 만들었다(§5.3).
*"「화려하게」는 체크가 안 되니 기법으로 센다"* 가 **기법 개수 채우기**로 퇴화한 것이다.

**이것은 버그가 아니라 게이트의 본성이다.** 검사 가능한 형태로 품질을 정의하면
생산자는 그 형태에 최적화하고, 그 형태가 곧 획일화가 된다.

**처방 — 게이트를 만들 때 짝으로 붙일 것:**
1. **하한 게이트에는 다양성 게이트를 짝지어라.** "juice 6개 이상"에는 "축의 재질로 번역됐는가"를,
   "판형 규격"에는 "직전 게시작과 같은 재배치 패턴만 반복하면 지적"을 붙인다(실제로 `40-review.md` 에 들어갔다).
2. **게이트를 폐기할 때 기계 검사는 남기고 규범만 교체해라.** design-bible 사고 4의 lesson 은
   *"단, 640px 컬럼 표준은 2026-08-28 판형 규범 교체로 대체됨 … **QA 초와이드 검증과 육안 의무화는 유지**"* 로
   **사후 개정**됐다. 사고 기록을 지우지 않고 덧쓴다.
3. **획일화는 캠페인이 아니라 정기 관측으로 잡아라.** 세 캠페인 모두 사용자가 먼저 알아챘다.
   이 공장에는 아직 "n작이 서로 얼마나 비슷한가"를 주기적으로 재는 자동 루프가 없다(§7.7).

### 7.9 레퍼런스도 루프다 (사람 승인 게이트 포함)

게임 10작마다(`SCOUT_EVERY=10`) 스카우트 에이전트가 새 레퍼런스 후보를 찾아 `references/pending/` 에 쌓는다.
**바로 반영되지 않는다** — 사람이 검토하고 `merge-references.mjs approve <파일>` 로 승인해야
`game-references.json`(현재 sites 143 · mechanics 28 · visual_refs 46 · art_directions 10축)에 병합된다.
스카우트는 게임 게시 이후에만 돌고, 실패해도 사이클을 죽이지 않는다(부가 작업이므로 `die()` 하지 않는다).

## 8. 모델 티어링

### 역할별 배정 원칙 (`factory/config.sh`)

| 티어 | Claude | GPT-5.6 | Grok |
|---|---|---|---|

- **판단이 어려운 단계(심사·빌드·검수)** → 상위 티어

- **수학 검산** → **다른 회사 모델** (교차 검증)

### 현재 배정

```
DESIGN_RUNNERS = grok_run, codex_smart_run, codex_run   # 3사·3티어 병렬
JUDGE          = codex sol
ART            = codex (이미지 생성)
BUILD          = grok        # 로컬 무샌드박스 → puppeteer/qa.mjs 직접 실행 가능
MATHCHECK      = codex sol   # 빌드와 다른 회사
REVIEW         = codex sol   # 빌드와 다른 회사
FIX            = grok        # puppeteer 실측이 필요하다
SCOUT          = grok        # 웹 접근 필요
CLAUDE         = 폴백 전용
```

배정에는 **능력 외의 제약**도 들어간다 — codex 샌드박스는 네트워크가 차단돼 puppeteer 를 못 돌린다.
그래서 실측이 필요한 단계(빌드·수정·QA)는 무샌드박스 러너가 맡는다.
클로드를 폴백으로 내린 결정도 근거가 실증적이다: 8/25 신작 3연작이 클로드 무사용으로 전부 게이트를 통과했다.

### 폴백 체계 (3중)

1. **`resolve_runner`** — 바이너리 부재 시 codex → grok → claude
2. **`stage_run`** — 폴백이 일어나면 **모델 인자를 버린다** (8/25 400 사고의 구조적 처방)
3. **결과 기반 재시도** — 빌드 단계는 실행 결과(rc / 402류 출력 / index.html 유무)를 보고 codex sol 로 1회 재시도 (§3.2)

타임아웃도 실측으로 조정된다: `T_REVIEW` 는 900초에서 **실제 타임아웃 1회 후 1200초로 상향**됐다.

## 9. 하위 에이전트 오케스트레이션

`docs/OPERATIONS.md` §3·§6·§7 의 규약.

### 9.1 오케스트레이터는 계획·검증만 한다

> 오케스트레이터(이 문서를 읽는 너)는 **계획·지시·검증만** 하고 실작업은 서브에이전트에 맡긴다.

실작업(코드 수정·캡처·이미지 판정·수학 검산)은 전부 서브에이전트가 하고,
오케스트레이터는 **작업지시서를 쓰고 결과를 실측으로 검증**한다.

### 9.2 파일 소유권 분리 (가장 자주 밟는 지뢰)

- **같은 파일에 두 에이전트를 동시에 투입 금지.** 게임 1편당 에이전트 1명.
  8/29에 실제 동시 편집 사고 1건(꽝도장) — hunk 단위 스테이징으로 수습했지만 원칙을 재확인했다.
- 병렬 아트 생성도 같은 규칙으로 설계돼 있다: 각 에이전트는 `factory/work/art-<id>.json` 만 쓰고,
  **`art.json` 은 건드리지 않는다.** 합치는 것은 `run.sh` 가 `jq -s` 로 한다.
- 병렬 서브에이전트는 **scratchpad 하위 디렉터리로 격리**한다 (파일명 충돌 사고 1회).
- git: 에이전트는 자기 게임 폴더만 `add`. 파이프라인과 동시 실행 시 `pull --rebase --autostash` 선행.
- **다른 프로세스의 크롬을 `pkill` 하지 마라** — 형제 puppeteer 를 죽인 사고 1회. PID 지정 kill.

### 9.3 작업지시서 표준 (핫픽스 패턴, OPERATIONS §7)

`/tmp/mgf-fix-<slug>.md` 에: 대상 파일 · 사용자 지적 **원문** · 원인 진단 ·
수정 방법 · **검증 항목(수치 기준)** · "진행 로그 append" · "git pull --rebase --autostash 선행" · 커밋 메시지.

- **수치 기준이 없는 지시는 검증이 불가능하다.** "자연스럽게" 대신 "무뇌봇 완주율 25% 이하", "QA 41/41", "겹침 0건".
- 장시간 작업은 *"진행 로그 파일에 append 하며 끝까지"* 를 명시한다 (중도 이탈 이력).
- 백그라운드 발진 + **PID 모니터**(`while kill -0 <PID>; do sleep 60; done`). macOS 에 `timeout` 이 없다.

### 9.4 실측 증거 의무 보고

서브에이전트의 최종 응답에는 **수치**가 있어야 한다. 예: 빌드는 봇 4종 완주율,
수리는 `고친 것 N / 못 고친 것 M / QA 치명적 결함 K`, 캠페인 수리는 `QA 41/41 + 재캡처 육안 + fps A→B`.
git 커밋 메시지에도 그대로 남는다 — *"겹쳐딱: 디자인 재스킨 — 축 I 직물·자수·펠트 (codex 구별 판정 통과, QA 41/41)"*.

## 10. 루프 설계 체크리스트 — 새 자동화를 붙일 때 물어라

새 단계·새 검사·새 캠페인을 파이프라인에 붙이기 전에 아래를 통과시켜라.
하나라도 "모르겠다"면 그건 아직 루프가 아니라 일회성 작업이다.

**신호와 측정**
1. 이 루프가 읽는 **신호**는 무엇인가? 어디에 어떤 형식으로 남는가? (로그·JSON 필드·git 이력)
2. 그 신호는 **자동으로 축적**되는가, 사람이 매번 만들어야 하는가?
3. 개입 전후를 비교할 **기준선 수치**가 있는가? (fun 6.8 → 12.4 처럼)

**판정**
4. 판정자가 **생산자와 다른가**? (다른 회사 모델 / 독립 스크립트 / 사람)
5. 판정 기준이 **이진**인가, 아니면 해석의 여지가 있는가? 해석형이면 근거 인용을 강제하는가?
6. 판정이 틀렸을 때(오탐) **교차 확인 경로**가 있는가?

**작용**
7. 이 게이트는 **가장 싼 단계**에 있는가? (기획에서 죽일 수 있는 것을 빌드 후에 죽이면 40분을 버린다)
8. 미달 시 **되돌아가는 경로**가 정의돼 있는가? 재시도 **횟수 상한**이 있는가?
9. **우회 경로가 없는가**? 사람이 손으로 하는 경로(부활 등)도 같은 게이트를 통과하는가?

**영속화**
10. 이번 사고에서 배운 것이 **다음 사이클에 자동으로 적용**되는가?
    (프롬프트 조항 / QA 항목 / 이력 필드 중 하나로 승격됐는가, 아니면 HANDOVER 에만 적혀 있는가?)
11. 이 게이트는 **몇 등급인가**(기계 / 배점 / 프롬프트 규범)? ③등급이라면 그대로 둘 이유가 있는가,
    아니면 아직 승격을 못 한 것인가? (§7.7 — 정직하게 구분해서 기록해라)
12. 감사에 쓴 **측정 스크립트가 저장소 안에 남았는가?** 스크래치패드에만 있으면 다음 사람에게는 없는 것이다.
13. 게이트가 지시하는 **자원이 실제로 존재하는지** 검증되는가? (§5.4 — 스펙은 조용히 실패한다)
14. 이 루프의 **상태를 감사하는 스크립트**가 있는가? (verify-catalog 처럼)
    그 감사는 **차단하는가 경고하는가**? 어느 쪽이 맞는지 의도적으로 골랐는가? (§7.5)

**부작용**
15. 이 게이트를 올리면 **병목이 어디로 이동**하는가? 그걸 관측할 준비가 돼 있는가? (§4.1)
16. **이 게이트가 만들어낼 획일화는 무엇인가?** 하한을 정의하면 생산자는 그 형태에 최적화한다.
    짝지을 다양성 게이트가 있는가? 그 다양성 게이트를 유한한 열거형으로 만들지는 않았는가?
    (§7.8 — 네 번 연속으로 근본 원인이 우리가 쓴 규범 문장이었고, 9/05 는 §7.8 자신의 처방이 진범이었다)
17. 실패한 산출물이 **보존**되는가? 나중에 부활 가능한 형태인가? (§6)
18. 이 루프가 **사이클 시간 예산**(2시간) 안에 들어오는가? 타임아웃은 실측값인가 추측인가?
19. 이 루프가 죽었을 때 **조용히 죽는가, 시끄럽게 죽는가?** (grok 402 는 4회차를 조용히 죽였다 — §3.2)
